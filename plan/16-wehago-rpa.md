# 위하고 T · 홈택스 · 위택스 원천세 자동화 RPA (자동화 전용 노트북)

> **2026-09-17 최종 정리.** 이지원천 로그인 사용자(세무사 사무소 직원)가 **'위하고 전송'**을 누르면
> **자동화 전용 노트북**이 세무사 전용 아이디로 위하고 T에서 **급여자료 입력**까지 자동 처리한 뒤 알림을 띄운다.
> 사용자가 위하고에 자동입력된 급여명세서를 확인하고 이상이 없으면 **'제작'** 하나로 위하고에서
> **원천세·지방세 마감·전자신고 파일 제작 → 홈택스·위택스 파일변환신고**까지 일괄 실행한다.
> 접수증·납부서가 회수되면 알림이 가고, 사용자가 **'발송 확정'**을 누른 뒤에만
> 사장님 포털 공개·납부안내 문자가 나간다. 확인 게이트는 **전송·제작·발송 확정 3개**, 모두 로그인 사용자 권한이다.
>
> - 위하고·홈택스·위택스 아이디/비밀번호는 **노트북에만 암호화 저장** — 이지원천 서버에는 저장하지 않는다.
> - **사원등록(입·퇴사·인적사항)은 자동화하지 않는다** — 민감정보이므로 사무소 사용자가 위하고에 직접 입력한다.
> - 같은 날 오전의 A안 (i)(세무사 PC 크롬 익스텐션·세션 재활용·크레덴셜 저장 X)은 본 문서로 대체한다. 약관 4벽 분석(§1)은 유지한다.

## §1. 약관 검토

결정 축은 **데이터 위치**:
- **A안 (설치형·로컬 완결)**: 위하고 raw 데이터가 세무사 사무소 기기를 벗어나지 않음. 이지원천은 세무사의 도구.
- **B안 (클라우드형·서버 경유)**: 위하고 raw 데이터가 이지원천 서버에 저장·처리되고 서버가 위하고에 접속.

### 1-1. B안이 T 약관·일반약관에서 동시에 막히는 4가지 벽 (유지)

| 벽 | 조항 | B안이 위반하는 이유 |
|----|------|-------------------|
| ① 회원 자격 | T 개별약관 제2조 3호 | 이지원천(주식회사 호미)은 세무사·회계사 아니라 T 회원 자격 없음. B안은 필연적으로 세무사 계정 대여 |
| ② 계정 대여 금지 | 일반약관 제5조 ①, 제28조 | 서버가 세무사 계정으로 위하고에 접근 = 실질적 계정 대여 |
| ③ 인증수단 관리 의무 | T 개별약관 제10조 ② 2호 (전자금융거래법 용어) | 크레덴셜을 서버에 두면 안전 관리 의무 위반. 홈택스 공동인증서까지 확장하면 정면 충돌 |
| ④ 재위탁 동의 | T 개별약관 제3조·제4조 | 수임처→세무사→더존→이지원천 4단계 재위탁 발생. 수임처마다 개별 동의 필요 → 영업 불가 |

### 1-2. 현재 구성이 4벽을 통과하는 논리

| 벽 | 현재 구성 | 평가 |
|----|----------|------|
| ① 회원 자격 | 아이디는 T 회원인 **세무사 사무소 소유** (자동화 전용 세무사 아이디). 이지원천은 위하고 아이디를 갖지 않음 | 통과 논리 유지 |
| ② 계정 대여 | 이지원천 **서버는 위하고·홈택스·위택스에 접속하지 않음**. 사무소 소유 노트북에서 사무소 소유 아이디로 접속 | 도구 사용 논리. 단 로그인까지 도구가 수행 → §1-4 |
| ③ 인증수단 관리 | 제3자 서버 보관 X. **회원 본인 기기에 암호화 보관** (Windows 자격 증명 관리자 + VeraCrypt 시스템 암호화, §8-2) | 브라우저 비밀번호 저장과 유사한 수준. 노트북 보안 조건 준수가 전제 |
| ④ 재위탁 | 위하고 원본 데이터(신고서 파일·위하고 계산값)는 서버 저장 X. 서버로 가는 것은 **상태와 대조 결과(일치/차이 항목)**뿐 | 급여대장은 이지원천 자체 자료, 접수증·납부서는 홈택스·위택스 결과물 (위하고 원본 아님) |

### 1-3. 현재 구성에서 유리하게 작용하는 조항 (유지)

- **T 개별약관 제11조** — 회원이 입력한 데이터의 지식재산권은 회원. 세무사가 자기 데이터를 자기 도구로 처리 → 정당
- **T 개별약관 제12조 ④** — 회원 업로드 방식에 대한 위하고 책임 없음. 자동화 업로드는 회원 자유
- **T 개별약관 제10조 ①·제12조 ①** — 위하고 T 자체가 스크래핑 사용을 약관에 명시·면책. 협상 카드 ("귀사도 스크래핑 사용")

### 1-4. 남은 쟁점 (변호사 검토 필수)

- **실행 주체 해석 — 가장 큰 쟁점.** 오전 A안 (i)(세무사 세션 재활용)과 달리 **로그인부터 제출까지 이지원천 소프트웨어가 수행**한다. "사무소 설치형 도구"(노트북·아이디·자격증명 모두 사무소 소유·관리, 실행은 사무소 직원·세무사의 버튼) 구조를 계약·화면 문구에 명확히 한다
- **로컬 암호화 저장 후 자동 로그인**이 T 개별약관 제10조 ② 2호 "인증수단 안전 관리"에 부합하는가
- **일반약관 제8조 ② "대리인" vs T 개별약관 제10조 ② 1호 "임·직원"** — 상충 시 개별약관 우선, 병존 해석 시 일반약관의 대리인 조항 살아있음. 후자가 유리
- **홈택스·위택스 이용약관**의 자동화·로그인 정보 저장 관련 조항 — 미검토
- 공동인증서 비밀번호 저장·자동 입력 — 2026-09-16 결정 히스토리대로 **저장·자동 입력을 범위에 포함**. 벽 ③(인증수단 관리)에 대한 논리: 인증서 파일·PW 모두 회원(세무사) 소유 노트북에만 존재, 서버·제3자 전송 없음, VeraCrypt 시스템 암호화 + DPAPI로 이중 암호화 → 로그인 PW·위택스 PW와 동일 취급. 다만 **전자서명법상 가입자 본인의 서명키 관리 의무**는 ID/PW와 층위가 달라 별도 질문이 필요하다 (세무사 명의 인증서를 도구가 사용하는 구조의 해석, 홈택스 이용약관의 자동화·인증서 조항 포함). **변호사 검토 필수**
- **명시적 임포트를 통한 위하고 원본 데이터 이관 (§12)** — 사용자가 트리거한 마스터 임포트에 한해 §1-2의 "원본 저장 X" 원칙을 벗지 않는다는 논리(도구 사용·자기 자료 이관)가 벽 ④(재위탁)에서 유효한지. 특히 원천세신고서 PDF·지급명세서 PDF를 서버가 보관하고 사장님 포털에 공개하는 경로의 재위탁 해석. **변호사 검토 필수**

## §2. 역할 분담

이지원천의 확인·신고·발송 확정 3단계는 모두 **로그인 사용자**(세무사 사무소 직원)가 담당한다. 세무사·직원 권한 분리는 두지 않는다. 관리자 권한은 노트북·에이전트 설정에만 적용된다.

| 주체 | 하는 일 | 하지 않는 일 |
|------|--------|-------------|

### 3-1. 자동화 방식

| 방식 | 평가 |
|------|------|
| **CDP 연결 (Playwright `connect_over_cdp`)** | **우선.** 노트북이 전용 기기라 크롬 실행 옵션의 UX 마찰이 작다. 새 크롬 실행보다 자동화 표시가 적다. `rpa-agent` 코드(서버 통신·실패 처리·수임처 대조·자격증명 저장) 재사용 |
| 크롬 익스텐션 (노트북 크롬) | **대안.** CDP가 감지될 때 전환. 페이지 이동 간 상태 유지·파일 전달 구현 부담 |
| 새 브라우저 실행 (Playwright `launch`) | **비권장 — 기술적 이유.** 자동화 표시로 감지·보안 프로그램 충돌 위험. 오전에 "약관 위반"으로 분류했으나 정확히는 "위반 소지"였고, 전용 아이디·노트북 로컬 저장 조건에서는 약관 우려가 완화됨 |
| 위하고 내부 API 직접 호출 | 비권장. 봇 감지가 가장 쉽고 비공식 API라 언제든 깨짐 |
| 공동인증서 비밀번호 자동 입력 | **채택 (2026-09-17).** 홈택스 로그인용 세무법인 공동인증서 PW를 노트북 자격 증명 관리자에 저장하고 에이전트가 인증서 선택창에서 자동 입력. ~~키보드보안(nProtect·DreamSecurity 계열) 회피 여부는 PoC 1에서 실측~~ → **2026-09-25 이지원에서 Playwright 자동 로그인 동작 확인** (인증서 선택·비밀번호 입력 포함). 벽 ③은 §1-4 논리로 커버, 변호사 검토 필수 |
| 반자동 (엑셀 다운로드 + 수동 업로드, 결과만 기록) | **최종 폴백** (§9) |

### 3-2. 로컬 브리지 — 불필요

위하고·홈택스·위택스가 모두 같은 노트북에 있으므로 신고 파일이 기기 밖으로 나가지 않는다. 오전 안의 LAN HTTP·공유폴더·USB 브리지는 **위하고를 다른 기기에서 돌리는 구성으로 되돌아갈 때만** 재검토한다.

### 4-1. 전송 (게이트 1) — 등록 검사

| 게이트 | 상태 |
|--------|------|
| 미승인 급여항목이 있는 거래처 차단 ("입력 확인" = 승인 완료) | 배포됨 |
| 자료 없는 거래처 차단 | 배포됨 |
| 사업자번호 없는 거래처 차단 (수임처 검색 불가) | 배포됨 |
| 같은 신고·거래처에 대기·진행 중 작업이 있으면 차단 | 배포됨 |
| **이번 달 입·퇴사가 있는 거래처는 "위하고 사원등록 완료" 확인 전까지 차단** | 신규 (이지원천의 입·퇴사 변동 데이터로 대상 자동 선별) |
| 반기납부 거래처는 신고 대상 월이 아니면 신고 단계에서 제외 (§4-7) | 신규 |

- 위하고에 올라가는 것은 직원별 급여명세서가 아니라 **22컬럼 급여대장 엑셀**(`payroll_excel.py`)이다. 흐름 안에서는 "급여자료"로 부른다
- 엑셀은 사용자 PC에 내려받지 않는다. **노트북이 서버 API로 직접 받는다** (공유폴더·USB 경유는 승인 우회·중복·파일 잔존 문제로 기각)

### 4-2. 위하고 자동입력 (게이트 1 ~ 게이트 2 사이)

게이트 1('위하고 전송') 직후 노트북이 실행하는 자동입력 단계다. **급여자료 입력까지만** 자동으로 하고 여기서 멈춘다 — 원천세·지방세 마감·제작은 게이트 2 이후(§4-4)로 미룬다.

1. 급여대장 엑셀 수신 → `%USERPROFILE%\.easyone-agent\work\` 임시 보관 (처리 후 즉시 삭제)
2. 로그인 상태 확인, 필요 시 노트북에 저장된 전용 아이디로 자동 로그인 (실패 1회 즉시 에이전트 정지 — 계정 잠금 방지)
3. 사업자번호로 수임처 검색 → 결과 정확히 1건 → 화면 상호·사업자번호를 작업 스냅샷과 대조 ((주)/주식회사·공백·하이픈 무시). 어긋나면 중단
4. **사원 존재 확인** — 엑셀의 사원(사원코드·이름)이 위하고 사원 목록에 모두 있는지 확인. 없으면 "위하고 미등록 사원: 홍길동"으로 실패 회신 (사무소 사용자의 사원등록 누락 대비 2차 안전망). 사원 인적사항은 서버로 가져오지 않는다
5. 급여자료 입력 → **대조 (인원·총지급액·비과세)** → 여기서 정지, 게이트 2 알림 발송

| 단계 | 대조 항목 (위하고 화면 vs 이지원천 승인값) | 불일치 시 |
|------|----------------------------------------|----------|
| 급여자료 입력 (자동) | 인원, 총지급액, 비과세 | 해당 거래처 중단, 게이트 2 진입 불가 |

- 한 거래처가 실패해도 다른 거래처는 계속 진행
- **단계 진행 기록** — 어느 단계까지 끝났는지 작업에 기록하고, 재실행 시 끝난 단계는 건너뛴다 (급여 중복 업로드 방지)
- **서버 전송 범위** — 대조는 노트북에서 하고 서버에는 "일치/불일치"와 **불일치일 때의 차이 항목만** 보낸다 (위하고 원본 값 전체를 서버에 두지 않음, §1-2 ④)
- 자동입력 대상은 근로소득 급여자료. 사업소득·일용근로소득의 별도 입력 화면 처리는 추가 실측 후 반영 (§9-2 촬영 목록·§11 후속 검토)

### 4-3. 알림 (로그인 사용자)

작업 3개 게이트 사이마다 이지원천 알림창이 로그인 사용자에게 뜬다. 알림 대상 = `requested_by_user_id`(요청자) + **같은 세무사 사무소의 로그인 중인 다른 사용자**(백업). 요청자가 부재 시 다른 사무소 사용자가 이어받는다.

| 시점 | 알림 목적 | 사용자 액션 |
|------|-----------|-------------|
| 자동입력 완료(§4-2) 후 | 위하고에 입력된 급여명세서 검토 요청 | 명세서 확인 → **'제작'** (게이트 2) |
| 홈택스·위택스 접수증 회수(§4-5) 후 | 접수증·납부세액·납부기한 검토 요청 | 검토 → **'발송 확정'** (게이트 3) |
| 어느 단계든 실패·불일치 | 실패 단계·차이 항목·수동 처리 안내 | 수동 처리, 재시도 필요 시 재전송 |

- 거래처별 표시: ✅ 완료 / ⚠️ 불일치(차이 항목) / ❌ 실패(단계·사유 + 수동 처리 안내)
- 로그아웃 상태였던 사용자도 놓치지 않도록 다음 접속 시 보여줄 알림 목록 유지

### 4-4. 제작 (게이트 2) — 위하고 마감·제작 + 홈택스·위택스 일괄

- **[제작] 버튼은 이지원천 로그인 사용자 누구든 클릭 가능** — 세무사·직원 권한 분리 없음
- 대상은 자동입력(§4-2) ✅인 거래처만 선택 가능
- 사용자 검토 대상은 **위하고에 자동입력된 급여명세서**(직원별 지급·공제·실지급). 원천세·지방세 합계는 위하고 마감이 아직 안 돌아 이 시점에는 계산 전 — 급여명세서가 맞으면 위하고 계산도 맞다는 전제로 진행 (제작 후 합계 대조로 재검증)
- **[제작] 클릭 하나로 아래를 순차 실행** (실행 중 실패 시 해당 거래처는 즉시 중단, 다른 거래처는 계속):

| 순서 | 시스템 | 조작 | 화면·조작 세부 (PoC 0, §9-2) | 대조·검증 |
|-----|--------|------|----------------------------|-----------|
| ⑨-a | 위하고 T | 원천세 마감 | 원천징수이행상황신고서 (`SWTA0101`) [조회] → [마감] → "마감 완료!" | 소득세 합계 vs 이지원천 승인값 |
| ⑨-b | 위하고 T | 사업소득 마감 | 거주자사업소득간이지급명세서 (`SWHM0103`) [마감]. "마감할 데이터가 존재하지 않습니다"는 건너뛰기 (실패 아님) | — |
| ⑨-c | 위하고 T | 원천세 전자신고 파일 제작 | 원천징수 전자신고 (`SWER0101`) 수임처 코드도움 → [제작(F4)] → **변환파일 비밀번호** 입력 → 파일 생성 | `C:\Douzone\Wehago\…` 저장 폴더 감시로 파일 수신 |
| ⑩-a | 위하고 T | 지방세 마감 | 지방소득세특별징수납부서 (`SWTA0112`) [마감(F3)]. "마감 오류리스트" 뜨면 **강제마감 금지** → 해당 거래처 중단 (§8-1) | 지방소득세 합계 vs 이지원천 승인값 |
| ⑩-b | 위하고 T | 지방세 전자신고 파일 제작 | 지방소득세특별징수전자신고 (`SWER0109`) [제작(F4)] → 변환파일 비밀번호 입력 → 파일 생성 | 저장 폴더 감시로 파일 수신 |
| ⑪ | 홈택스 | 파일변환신고 | 로그인(아이디 → 공동인증서 → 세무대리 관리번호, §9-2) → 세금신고 > 원천세 신고 > 일반신고 > **파일변환신고** → [파일선택] → [파일검증하기] → 변환파일 비밀번호 → 검증결과내역(형식·내용검증) | **제출 직전 원천세 합계를 이지원천 값과 재대조** → [제출하러 가기] → **일괄접수증 확인 후 성공 처리** |
| ⑫ | 위택스 | 특별징수 회계파일신고 | **홈택스 접수 성공 거래처만** → 로그인 → 신고 > 지방소득세 > 특별징수 > 특별징수신고 > **특별징수 회계파일신고** → [파일첨부] → 파일비밀번호 → [파일변환하기] → 서식검증 및 제출 → 제출결과확인 | 홈택스 실패 거래처는 지방세도 건너뛰고 함께 실패 표시 |

- 위하고 T에는 **[전송]이 없음** (PoC 0). 파일은 브라우저 다운로드가 아니라 위하고 로컬 모듈이 `C:\Douzone\Wehago\…`에 저장 → Playwright 다운로드 이벤트가 아니라 **저장 폴더 감시**로 수신 (정확한 경로는 실측)
- **변환파일 비밀번호**(영문 소문자·숫자 8~15자리)는 제작 시 입력하고 홈택스·위택스 제출 시 다시 입력 → 에이전트가 작업마다 생성해 노트북에만 보관, 제출 후 파일과 함께 삭제
- 원천세·지방소득세 신고 파일은 이지원천이 아니라 위하고 T [제작]으로 노트북에 생성 (이지원천에는 원천징수이행상황신고서 전자파일 생성 기능이 없음 — `04-excel-outputs.md` Phase 3 이후 항목)
- 홈택스 원천세 신고 후 지방소득세로 이어지는 연계 경로 — PoC 0 영상에서는 위택스에 따로 로그인해 파일을 올림. 연계 경로 유무는 추가 실측
- **재실행 안전** — ⑨~⑫ 각 단계별 진행을 `rpa_jobs`에 기록하고, 노트북 재기동 후 재실행 시 끝난 단계는 건너뛴다 (위하고 재마감·홈택스 중복 제출 방지)

### 4-5. 결과 수집 (게이트 2 이후 자동)

- 접수증·납부서(국세·지방세) PDF를 노트북이 회수 → 서버 `ClientFilingResult`(`source=RPA`, `published_at=NULL`)에 **비공개 상태로 등록**
- PDF가 해당 거래처·귀속월의 것인지 사업자번호로 대조 후 등록
- 납부서에서 **납부세액·전자납부번호·납부기한**을 추출해 칸에 채운다 (포털의 "얼마를 언제까지" 표시에 필수)
- 납부세액 0원이면 납부서가 없을 수 있음 — "납부서 없음"을 실패로 처리하지 않는다
- 이 단계에서는 **사장님 포털 공개·납부안내 문자 발송이 일어나지 않는다**. 로그인 사용자에게 게이트 3 알림 발송

### 4-6. 발송 확정 (게이트 3) — 포털 공개 · 납부안내 문자

- **'발송 확정' 버튼은 이지원천 로그인 사용자 누구든 클릭 가능** (게이트 2와 동일 권한)
- 대상은 §4-5에서 접수증·납부서 회수 ✅인 거래처만 선택 가능. 실패·불일치 거래처는 확정 대상에서 자동 제외
- 사용자가 접수증·납부세액·납부기한을 검토한 뒤 클릭 → 서버가 아래 두 개를 **동시에** 트리거:
  1. **사장님 포털(`12-owner-portal.md`)에 접수증·납부서 공개** — `ClientFilingResult.published_at`·`confirmed_by_user_id` 채움
  2. **납부안내 문자 발송** — 포털 링크(30일 수명, `plan.md` 결정 10) 동봉, 본문은 합계·기한만
- 이지원천 조회·다운로드는 게이트 3 전이라도 사무소 사용자에게 열려 있음 (내부 검토용). 사장님 포털·문자만 게이트로 막는다
- **사용자 PC 자동 저장은 불가** (웹은 사용자 PC에 파일을 몰래 쓸 수 없음) → 알림창의 **"접수증·납부서 받기" 버튼** (여러 거래처면 ZIP)
- 문자 발송 활성화는 `13-messaging-activation.md` 전제
- 확정 없이 30일이 지나면 알림 재발송, 60일 지나면 자동 확정 여부는 `13-messaging-activation.md`와 함께 결정 (초기에는 자동 확정 없음)

### 4-7. 사원등록 안내 (자동화 제외)

사원등록(주민번호 등 인적사항, 입사일·퇴사일)은 민감정보이므로 RPA가 건드리지 않는다.
전송 화면에서 대상 거래처에 안내한다:

> "이번 달 입사 2명(홍길동, 김철수)·퇴사 1명이 있습니다. 위하고 T 사원등록에서 직접 입력한 뒤 '사원등록 완료'를 체크하세요. 주민번호 등 인적사항은 자동화하지 않습니다."

### 4-8. 업무 예외

| 예외 | 대응 |
|------|------|
| **반기별 납부 승인 거래처** | 매월 신고 대상 아님. 거래처에 **신고 주기(매월/반기)** 를 두고 대상이 아닌 달은 게이트 2 진입에서 제외 |
| **연말정산 반영 월**, 중도퇴사자 정산 | 위하고 계산이 급여대장 금액과 달라지는 달. 초기에는 **자동화 제외 → 수동 처리** |
| **수정신고·기한후신고** | 초기 범위 제외, 정기신고만 자동화 |
| **납부세액 0원** | 신고는 하되 납부서 없음 허용 |
| **같은 거래처를 사무소 사용자가 위하고에서 동시 수정** | 전송 중 거래처를 이지원천 화면에 "위하고 반영 중"으로 표시 |

## §5. 작업 상태 (거래처 × 귀속월)

```
전송대기
  └─ 게이트 1 ('위하고 전송') ─→
급여자료입력 → 명세서검토대기
  └─ 게이트 2 ('제작') ─→
원천세마감·제작 → 지방세마감·제작 → 홈택스신고 → 위택스신고 → 결과수집완료(비공개)
  └─ 게이트 3 ('발송 확정') ─→
포털공개·문자발송 → 완료
어느 단계든 실패 → 실패(단계·사유) + 수동 처리 안내, 끝난 단계는 재실행하지 않음
```

## §7. API (`/api/v1/rpa`)

| 메서드·경로 | 인증 | 상태 |
|------------|------|------|
| `POST /agents` · `GET /agents` · `DELETE /agents/{id}` | 관리자(발급·폐기) / 사용자(목록) | 배포됨, 유지 |
| `POST /wehago-uploads` (게이트 1 — 위하고 자동입력 작업 등록) | 사용자 | 배포됨 — **입·퇴사 게이트 추가**, 작업 종류 `WEHAGO_PAYROLL_INPUT`으로 변경 |
| `GET /jobs?filing_id=` · `POST /jobs/{id}/cancel` | 사용자 | 배포됨, 유지 (게이트·단계 표시용 필드 추가) |
| `POST /agent/claim` | 에이전트 | 배포됨, 유지 (사무소당 1건·재시작·15분 초과 FAILED) |
| `GET /agent/jobs/{id}/payroll-excel` | 에이전트 | 배포됨, **유지** — 오전 A안 (i)의 제거 결정 철회 (노트북이 급여대장을 받는 경로) |
| `POST /agent/jobs/{id}/result` | 에이전트 | 배포됨 — 단계·대조 결과 필드로 확장 |
| `POST /productions` (게이트 2 — 위하고 마감·제작 + 홈택스·위택스 일괄 작업 등록) | **사용자** (권한 분리 없음) | 신설. 요청 본문에 자동입력 ✅ 거래처 목록. 서버가 `MONTHLY_PRODUCTION` 작업 생성 |
| `POST /agent/jobs/{id}/filing-result` (접수증·납부서 등록 → `ClientFilingResult` 비공개) | 에이전트 | 신설 |
| `POST /filing-results/{id}/publish` (게이트 3 — 발송 확정 → 포털 공개 + 문자 발송 트리거) | **사용자** | 신설 |

**만들지 않음**: 위하고 신고서 파일 업로드 API, 로그인 정보 저장·조회 API.

## §8. 안전장치

### 8-1. 업무 안전장치

| 위험 | 장치 |
|------|------|
| 엉뚱한 회사에 입력 | 사업자번호 검색 → 결과 1건 → 화면 상호·사업자번호를 스냅샷과 대조, 어긋나면 중단 |

### 8-3. 사이트별 세션 운영 원칙 (2026-09-25 결정)

**병렬 단위 = 사이트별 로그인 세션.** 위하고·홈택스·위택스는 각각 **크롬 1개(전용 프로필 + CDP 포트) = 작업 대기열 1줄**로 운영한다.

| 사이트 | 크롬 (CDP 포트) | 이 줄에서 순서대로 처리하는 작업 |
|------|------|------|
| 위하고 T | 9222 | 급여자료 입력 · 위하고 가져오기 · 원천세·지방세 마감·파일 제작 |
| 홈택스 | 9223 | **원천세 파일변환신고 + 증명원 발급** (한 줄) |
| 위택스 | 9224 | 지방세 특별징수 회계파일신고 |

- 세 줄은 서로 동시에 돈다. 한 줄 안에서는 한 건씩, **직원별로 번갈아** 처리한다 (2026-09-25 구현, `next_fair_job_id`): 대기 작업이 있는 직원 중 이 줄에서 마지막으로 작업이 시작된 지 가장 오래된 직원(처음이면 맨 앞)의 가장 먼저 요청한 작업을 가져간다. 한 직원이 30건을 몰아 넣어도 다른 직원 작업이 사이사이 끼어들고, 한 직원의 요청 순서는 그대로 지켜진다.
- **홈택스는 자동화 아이디를 2개로 나눌 수 없다** (사용자 확인) → 원천세 신고와 증명발급은 같은 세션을 번갈아 쓴다. 서버 claim 의 동시 실행 제한을 "작업 종류별"에서 "사이트 세션별"로 바꾸고, `MONTHLY_PRODUCTION` 의 홈택스 단계는 홈택스 줄에 선다 (`plan/17-certificate-issuance.md` §4-4 mutex 의 구체화).
- 크롬 창이 아니라 **크롬 프로그램을 따로 실행**한다 (`start-chrome.ps1 -Port … -ProfileDir …`). 같은 크롬의 새 창·탭은 쿠키를 공유해 분리되지 않는다. 에이전트는 사이트별 CDP 주소를 따로 받는다 (지금은 `EASYONE_CDP_URL` 하나 — 수정 필요). 다운로드 폴더도 크롬별로 분리.
- 이지원 RAM **16GB 권장** (크롬 3개 + 에이전트).

**로그인 유지·로그아웃**

1. 대기 작업이 있으면 로그아웃하지 않고 기존 로그인을 이어 쓴다.
2. **'로그인 연장' 버튼은 누르지 않는다.** 작업 중에는 요청이 계속 오가서 연장 팝업이 뜨지 않고, 할 일 없이 연장해 로그인을 붙잡아 두는 것은 사람이 하지 않는 패턴이다. 예외: 작업 진행 중에 연장 팝업이 뜨면 그때만 누른다 (신고 도중 세션이 끊기면 진행 위치를 잃는다).
3. 작업 없이 **30분**이 지나면 사이트별로 명시적으로 로그아웃한다. 사이트가 먼저 자동 로그아웃하면(위택스 세션 30분 등) 그대로 둔다. 에이전트 종료·퇴근 시에도 로그아웃.
4. 다음 작업이 오면 로그인 상태를 먼저 확인하고, 풀려 있으면 저장된 정보로 **자동 로그인** (홈택스: `plan/17-certificate-issuance.md` §3-9-7-4). 로그인 실패 1회에 에이전트 정지 (§8-1).

**동시 운영 실측 (이지원, 미실시)** — 크롬 3개를 띄워 위하고 입력·증명발급·위택스 로그인을 반나절 동시 실행하고 다음을 확인한다: 로그인 유지, 봇 탐지 문구, PC 전역 보안 프로그램(nProtect·AnySign) 충돌(필요하면 로그인 순간만 사이트 간 잠금), 창 포커스 가로채기(`bring_to_front` 최소화), 작업 중 연장 팝업 발생 여부.

### 8-4. 봇 탐지 대응 설계 (2026-09-25)

**원칙: 속이는 것이 아니라, 사무소 직원이 쓰는 환경·속도·패턴 그대로 돌린다.** 이지원은 세무사 본인 계정·본인 인증서·사무소 IP 로 본인 업무를 대신하는 도구다. 탐지를 "우회"할 대상은 봇처럼 보이는 흔적이지, 사이트의 보안 장치(캡차·추가인증·보안 프로그램)가 아니다. 세무대리 계정·공동인증서가 차단되면 사무소 업무 전체가 멈추므로, 들키지 않는 것보다 **걸렸을 때 즉시 멈추는 것**이 더 중요하다.

**조사한 기법과 채택 여부**

| 층위 | 대표 기법 | 채택 | 이유 |
|------|------|------|------|
| 브라우저 지문 | `navigator.webdriver`, `--enable-automation` 안내줄, headless UA, plugins·WebGL·언어 불일치 | **실제 설치 크롬 + CDP 부착(현행)** — 이 흔적이 원래 없다 | Playwright `launch`/headless 는 흔적이 남는다 |
| 지문 위장 | playwright-stealth·puppeteer-extra stealth 스크립트, 안티디텍트 브라우저(Multilogin 등), Camoufox | **미채택** | 진짜 크롬에 위장 스크립트를 덧씌우면 오히려 값이 서로 어긋나 더 잘 걸린다 |
| CDP 흔적 | `Runtime.enable` 부작용 탐지 → rebrowser-patches·patchright 로 패치 | **보류** — 실측에서 문제될 때만 | 관공서·위하고가 이 수준을 검사한다는 근거 없음. 패치는 Playwright 업데이트 부담 |
| 네트워크 | 프록시·IP 로테이션, TLS(JA3/JA4) 위장 | **미채택** — 사무소 고정 IP, 진짜 크롬 TLS | 세무대리 계정이 여러 IP 에서 접속하는 편이 더 이상하다 |
| 행동 | 키 입력 간격, 생각 시간, 마우스 이동, 스크롤 | **채택 (가볍게)** | 아래 행동 규칙 |
| 계정 패턴 | 로그인 빈도, 동시 세션, 새벽 작업, 처리량 | **채택** | §8-3 + 아래 속도 규칙 |
| 캡차·추가인증 | 캡차 풀이 서비스, OTP·QR 자동 처리 | **금지** | 보안 장치 무력화. 뜨면 사람에게 넘긴다 |

**이지원천 적용안**

1. **환경 — 현행 유지 + 보완**
   - 설치된 크롬(자동 업데이트 유지) + 사이트별 전용 프로필 + CDP 부착, 창 표시(headless 금지), UA·언어·시간대 변경 금지.
   - `start-chrome.ps1` 에 `--enable-automation`·`--headless` 류 옵션을 넣지 않는다 (현행 준수).
   - **보완 필요:** 증명원 자동 로그인 경로 `execute_phase1` 이 `p.chromium.launch()` 로 새 브라우저를 띄운다 → 운영 경로는 CDP 부착 크롬에서 로그인하도록 바꾼다 (`plan/17-certificate-issuance.md` §3-9-7-4).
2. **행동 — 사람 속도**
   - 아이디·비밀번호·검색어는 **한 글자씩 입력** (`press_sequentially`, 글자 간 50~150ms 무작위). 홈택스 PoC 의 `fill()` 은 바꾼다 (키보드보안이 키 이벤트를 요구할 수도 있다).
   - 클릭은 요소 클릭(`locator.click`, 브라우저가 실제 마우스 이벤트 발생). 단계 사이 0.5~2초 무작위 대기. 고정 `sleep` 대신 요소 상태를 기다린 뒤 짧은 무작위 대기.
   - 마우스 궤적 흉내·무작위 스크롤은 넣지 않는다 — 효과 근거가 약하고 실패 지점만 늘린다.
3. **속도·시간대 — 사람 업무량 범위**
   - 같은 사이트에서 작업과 작업 사이 **최소 5~15초 무작위 간격**.
   - 사이트별 **시간당 상한** (초안: 증명원 발급 60건/시간, 위하고 거래처 전환 60곳/시간 — 실측 후 조정). 넘으면 대기열에서 쉬었다 간다.
   - **업무 시간에만 실행** (초안 08:00~20:00, 홈택스 신고는 06:00~24:00 제한 안). 밤·새벽 대기 작업은 다음 날 아침 처리.
4. **탐지 신호 → 즉시 정지 (가장 중요)**
   - 캡차·"자동입력 방지"·추가인증(QR·OTP)·접속 차단·"비정상 접근" 문구, 예상 밖 로그아웃이 2회 연속이면 **해당 사이트 줄을 정지**하고 관리자에게 "사람 확인 필요"를 알린다. 자동 재시도·자동 풀이 금지.
   - 사람이 이지원에서 직접 해결한 뒤 [재개]를 눌러야 다시 돈다.

### 9-4. 후속 작업 — 금액 검증 확장 (2026-09-25 정리, 미착수)

§9-3 대조는 **지급액 계·비과세 합계**만 본다. 소득세·4대보험은 엑셀 값이 위하고에 **그대로 들어가므로**
(위하고는 업로드 때 다시 계산하지 않는다) 틀린 값이 들어와도 지금 대조로는 잡히지 않는다.

**(a) 비과세를 제출·미제출로 나눠 대조** — 위하고 합계 칸은 비과세를 지급명세서 작성여부로 나눈다
(식대 P01·보육 Q02 = 제출, 자가운전 H03 = 미제출). 지금은 합계만 비교해 사무소가 작성여부 X 코드로 잘못 등록해도 못 잡는다.

**(b) 원천세 신고서 총지급액 확인** — 신고서 총지급액은 미제출 비과세를 뺀 금액이다
(서도 2026-06: 12,800,000 − 자가운전 200,000 = 12,600,000). 이지원천 백엔드의 신고서 계산이 이렇게 하는지 확인 필요.

**(c) 소득세·지방소득세 검증** — 이지원천 계산의 현재 한계와 위하고 값 비교 방법.

이지원천 계산 (`services/tax_calc.py:64`, 간이세액표 `wage_tax_table.py:87`):
- 부양가족 **1명 고정**: `collect.py:784` 하드코딩. `PayrollEntry.dependents` 칸은 있지만 입력하는 곳이 없다
- 8~20세 자녀 **0명 고정**: 자녀 수 저장 칸이 없다
- 원천징수 비율 **100% 고정**: 80/120% 선택이 없다
- 거래처가 보낸 급여대장에 소득세 값이 있으면 그 값을 쓴다 (계산값과 다르면 `_calc_diffs`에 차이를 기록)

→ 부양가족이 있는 사원은 이지원천이 계산한 소득세가 실제보다 많을 수 있다. 위하고 사원등록에는 이 입력값이 있다
(사원 그리드 `Left_grid`: `num_20family`·`num_60family`·`yn_mateded`·`rate_adjust` 등, 필드 뜻은 실측 필요).

| 방법 | 방식 | 장단점 |
|------|------|--------|
| **① 입력값 맞추기 (권장)** | 위하고 사원등록의 부양가족·자녀·원천징수 비율을 이지원천 사원에 가져와(§12 가져오기 확장) 처음부터 같은 조건으로 계산. 에이전트는 업로드 전에 위하고 사원 그리드 값과 이지원천 값을 비교해 다르면 멈춘다 | 위하고 데이터를 바꾸지 않는다. 이지원천 `Employee`에 칸 추가·마이그레이션 필요 |
| ② 위하고 산출식 읽기 | 공제항목 금액 옆 [산출식>] 버튼이 위하고 계산값을 보여 주는지 실측. 보여 주면 저장 없이 읽어 비교 | 비파괴. 버튼 동작 미실측 |
| ③ 위하고 재계산과 비교 | 업로드 뒤 [재계산] → “소득세 재계산”만 체크 → 위하고가 계산한 소득세를 엑셀 값과 비교. 다르면 알리고, 엑셀 값으로 다시 올릴지 사무소가 결정 | 위하고가 사원등록 조건 그대로 계산하므로 가장 정확. 대신 저장된 값을 바꾸므로 되돌리려면 재업로드 필요 |

- 지방소득세는 소득세 × 10%, 10원 미만 절사로 양쪽 규칙이 같은지만 대조하면 된다
- 예외: 연말정산 환급·추징 월, 중도 퇴사자 정산, 사무소가 급여대장에 직접 적은 소득세 — 이 경우 불일치는 정상일 수 있어 “확인 필요”로만 알린다

**(d) 4대보험 입력 방식** — 거래처별로 고정액 + 연간 정산 / 실지급액 계산이 갈린다. 분석은 [`06-insurance.md`](06-insurance.md) §6.

```
 ④ 위하고 로그인 → 사업자번호로 수임처 검색 → 결과 정확히 1건 → 화면 상호·사업자번호를 폼 값과 대조 (§4-2 규칙 재사용). 어긋나면 실패
 ⑤ 사원 · 신고이력 · 지급명세서 임포트 (수임처 단위 트랜잭션)
        ▼
[등록 화면]
 ⑥ 완료 알림 (사원 M명, 신고이력 K건 등록됨) — 실패 시 사유
```

### 12-4. §1-2 정책 예외 조항

- **원칙 유지**: RPA 운영 중(§4-2·§4-4)에는 위하고 계산값을 서버에 반영하지 않는다 (대조 결과·차이 항목만 저장)
- **예외 (본 §12)**: 사용자가 **명시적으로 트리거한 임포트**에 한해 위하고 원본 데이터(마스터·신고이력·지급명세서)를 서버에 저장한다
- **예외 성립 근거**
  1. 도구 사용 논리 유지 — 세무사가 **자기 데이터를 자기 도구로 이관**하는 행위
  2. 저장 데이터는 사용자 자신의 수임처 자료 — 재위탁 사슬이 확장되지 않음 (수임처→세무사→이지원천은 이미 §1-2 ④에 정리됨)
  3. 목적이 명확 — 매칭 엔진 시드(`05-master-import.md`)와 사장님 포털 과거 이력 조회
  4. 임포트 후 사장님 포털에 공개하는 원본 PDF는 발송 확정 게이트(§4-6)와 동일 로직으로 별도 검토 게이트를 두어 무단 공개 방지
- **범위 밖**: RPA 운영 중의 원본 저장은 예외에 포함하지 않음. 임포트 작업 완료 후에는 §1-2 원칙으로 복귀

### 12-5. 안전장치

| 위험 | 장치 |
|------|------|
| 같은 수임업체 중복 임포트 | 대기·진행 중 임포트 작업 중복 등록 차단, 마지막 임포트 시각(`Client.wehago_synced_at`)으로 재실행 여부 판단 |
| 이지원천에 이미 있는 수임처 덮어쓰기 | 사업자번호 unique 검사, 이미 있으면 등록 폼에서 "이미 등록됨 — 재임포트로 갱신하시겠습니까?" 확인 |
| 이지원천 사원 마스터 덮어쓰기 | 사원코드 기준 upsert. **이지원천이 더 최신인 필드는 위하고 값으로 덮지 않고 diff 리포트** (특히 급여 정보) |
| 대량 임포트 중단 | 수임처 단위 트랜잭션 — 부분 완료 상태를 `rpa_jobs`에 기록, 재실행 시 완료 수임처는 건너뛰기 |
| 위하고 세션 만료·계정 잠금 | 로그인 실패 1회 정지 (§8-1 규칙 재사용). 대량 작업 시 rate-limit 실측 필요 (§12-7) |
| 잘못된 수임처 임포트 (개별) | 사업자번호 검색 결과 정확히 1건 + 화면 상호 대조 (§4-2와 동일) |
| 임포트된 PDF 무단 공개 | 초기 `published_at=NULL`, 사장님 포털 공개는 관리자·사용자의 별도 확정 클릭 (§4-6 로직 재사용) |
| PDF 다운로드 파일 잔존 | 서버 등록 후 노트북에서 즉시 삭제 (§4-2 규칙과 동일) |
| 성능 (수임처 100+ 사무소) | 초기 세팅은 **야간·주말 실행** 권장, 관리자 알림창에 진행률·예상 종료 시각 표시 |

### 12-6. 데이터 모델·API 추가

**`rpa_jobs.kind`** 확장
- `WEHAGO_MASTER_IMPORT_ALL` (초기 세팅, 대상 수임처 리스트·옵션이 JSON 페이로드)
- `WEHAGO_CLIENT_IMPORT` (개별, 상호·사업자번호·옵션)

**`Client`** 추가 필드
- `wehago_synced_at` (마지막 임포트 시각)
- `wehago_import_status` (NONE / IN_PROGRESS / DONE / FAILED)

**`ClientFilingResult`** 확장
- `source`에 `WEHAGO_IMPORT` 값 추가 (기존 `RPA`, 신설과 병존)
- 임포트 레코드는 `published_at=NULL`로 시작, 별도 확정 게이트로만 공개

**API 신설** (`/api/v1/rpa`)
| 메서드·경로 | 인증 | 용도 |
|------------|------|------|
| `POST /imports/master-all` | 관리자 | 초기 임포트 작업 등록 (대상 수임처 리스트·옵션) |
| `POST /imports/clients` | 사용자 | 개별 수임업체 임포트 (수임업체 등록과 원자적) |
| `GET /imports/{job_id}/progress` | 사용자 | 진행률·수임처별 상태 조회 |
| `POST /agent/imports/{job_id}/client-result` | 에이전트 | 수임처 단위 결과 회신 (마스터·사원·신고이력·PDF 함께) |

### 12-7. 실측 필요 (PoC 6 · §9와 연동)

- 위하고 T 세무대리인 화면의 **수임처 목록 조회** — 페이지네이션·검색·필터, 대량 조회 시 rate-limit
- 각 수임처의 **사원 목록 조회** 화면 — 컬럼(주민번호 표시 여부·복사 가능 여부·마스킹 여부), 엑셀 다운로드 가능 여부
- **원천세 신고이력 조회** 화면 — 귀속월 리스트, 접수번호·납부기한 표시, PDF 다운로드 경로 (홈택스 접수증과의 관계)
- **지급명세서 발행 이력** 화면 — 근로/사업/일용/기타 각 종류의 발행 이력, PDF 다운로드
- 같은 아이디로 임포트 중 다른 창에서 로그인 시 세션 끊김 여부 (§9-1과 동일 확인, 임포트 중단 리스크)
