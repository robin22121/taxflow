# 위하고 T · 홈택스 · 위택스 원천세 자동화 RPA (자동화 전용 노트북)

> **2026-09-17 최종 정리.** 이지원천 로그인 사용자(세무사 사무소 직원)가 **'위하고 전송'**을 누르면
> **자동화 전용 노트북**이 세무사 전용 아이디로 위하고 T에서 **급여자료 입력**까지 자동 처리한 뒤 알림을 띄운다.
> 사용자가 위하고에 자동입력된 급여명세서를 확인하고 이상이 없으면 **'제작'** 하나로 위하고에서
> **원천세·지방세 마감·전자신고 파일 제작 → 홈택스·위택스 파일변환신고**까지 일괄 실행한다.
> 접수증·납부서가 회수되면 알림이 가고, 사용자가 **'발송 확정'**을 누른 뒤에만
> 사장님 포털 공개·납부안내 문자가 나간다. 확인 게이트는 **전송·제작·발송 확정 3개**, 모두 로그인 사용자 권한이다.
>
> - 위하고·홈택스·위택스 아이디/비밀번호는 **노트북에만 암호화 저장** — 이지원천 서버에는 저장하지 않는다.
> - **사원등록(입·퇴사·인적사항)은 자동화하지 않는다** — 민감정보이므로 사무소 사용자가 위하고에 직접 입력한다.
> - 같은 날 오전의 A안 (i)(세무사 PC 크롬 익스텐션·세션 재활용·크레덴셜 저장 X)은 본 문서로 대체한다. 약관 4벽 분석(§1)은 유지한다.

## §1. 약관 검토

결정 축은 **데이터 위치**:
- **A안 (설치형·로컬 완결)**: 위하고 raw 데이터가 세무사 사무소 기기를 벗어나지 않음. 이지원천은 세무사의 도구.
- **B안 (클라우드형·서버 경유)**: 위하고 raw 데이터가 이지원천 서버에 저장·처리되고 서버가 위하고에 접속.

### 1-1. B안이 T 약관·일반약관에서 동시에 막히는 4가지 벽 (유지)

| 벽 | 조항 | B안이 위반하는 이유 |
|----|------|-------------------|
| ① 회원 자격 | T 개별약관 제2조 3호 | 이지원천(주식회사 호미)은 세무사·회계사 아니라 T 회원 자격 없음. B안은 필연적으로 세무사 계정 대여 |
| ② 계정 대여 금지 | 일반약관 제5조 ①, 제28조 | 서버가 세무사 계정으로 위하고에 접근 = 실질적 계정 대여 |
| ③ 인증수단 관리 의무 | T 개별약관 제10조 ② 2호 (전자금융거래법 용어) | 크레덴셜을 서버에 두면 안전 관리 의무 위반. 홈택스 공동인증서까지 확장하면 정면 충돌 |
| ④ 재위탁 동의 | T 개별약관 제3조·제4조 | 수임처→세무사→더존→이지원천 4단계 재위탁 발생. 수임처마다 개별 동의 필요 → 영업 불가 |

### 1-2. 현재 구성이 4벽을 통과하는 논리

| 벽 | 현재 구성 | 평가 |
|----|----------|------|
| ① 회원 자격 | 아이디는 T 회원인 **세무사 사무소 소유** (자동화 전용 세무사 아이디). 이지원천은 위하고 아이디를 갖지 않음 | 통과 논리 유지 |
| ② 계정 대여 | 이지원천 **서버는 위하고·홈택스·위택스에 접속하지 않음**. 사무소 소유 노트북에서 사무소 소유 아이디로 접속 | 도구 사용 논리. 단 로그인까지 도구가 수행 → §1-4 |
| ③ 인증수단 관리 | 제3자 서버 보관 X. **회원 본인 기기에 암호화 보관** (Windows 자격 증명 관리자 + VeraCrypt 시스템 암호화, §8-2) | 브라우저 비밀번호 저장과 유사한 수준. 노트북 보안 조건 준수가 전제 |
| ④ 재위탁 | 위하고 원본 데이터(신고서 파일·위하고 계산값)는 서버 저장 X. 서버로 가는 것은 **상태와 대조 결과(일치/차이 항목)**뿐 | 급여대장은 이지원천 자체 자료, 접수증·납부서는 홈택스·위택스 결과물 (위하고 원본 아님) |

### 1-3. 현재 구성에서 유리하게 작용하는 조항 (유지)

- **T 개별약관 제11조** — 회원이 입력한 데이터의 지식재산권은 회원. 세무사가 자기 데이터를 자기 도구로 처리 → 정당
- **T 개별약관 제12조 ④** — 회원 업로드 방식에 대한 위하고 책임 없음. 자동화 업로드는 회원 자유
- **T 개별약관 제10조 ①·제12조 ①** — 위하고 T 자체가 스크래핑 사용을 약관에 명시·면책. 협상 카드 ("귀사도 스크래핑 사용")

### 1-4. 남은 쟁점 (변호사 검토 필수)

- **실행 주체 해석 — 가장 큰 쟁점.** 오전 A안 (i)(세무사 세션 재활용)과 달리 **로그인부터 제출까지 이지원천 소프트웨어가 수행**한다. "사무소 설치형 도구"(노트북·아이디·자격증명 모두 사무소 소유·관리, 실행은 사무소 직원·세무사의 버튼) 구조를 계약·화면 문구에 명확히 한다
- **로컬 암호화 저장 후 자동 로그인**이 T 개별약관 제10조 ② 2호 "인증수단 안전 관리"에 부합하는가
- **일반약관 제8조 ② "대리인" vs T 개별약관 제10조 ② 1호 "임·직원"** — 상충 시 개별약관 우선, 병존 해석 시 일반약관의 대리인 조항 살아있음. 후자가 유리
- **홈택스·위택스 이용약관**의 자동화·로그인 정보 저장 관련 조항 — 미검토
- 공동인증서 비밀번호 저장·자동 입력 — 2026-09-16 결정 히스토리대로 **저장·자동 입력을 범위에 포함**. 벽 ③(인증수단 관리)에 대한 논리: 인증서 파일·PW 모두 회원(세무사) 소유 노트북에만 존재, 서버·제3자 전송 없음, VeraCrypt 시스템 암호화 + DPAPI로 이중 암호화 → 로그인 PW·위택스 PW와 동일 취급. 다만 **전자서명법상 가입자 본인의 서명키 관리 의무**는 ID/PW와 층위가 달라 별도 질문이 필요하다 (세무사 명의 인증서를 도구가 사용하는 구조의 해석, 홈택스 이용약관의 자동화·인증서 조항 포함). **변호사 검토 필수**
- **명시적 임포트를 통한 위하고 원본 데이터 이관 (§12)** — 사용자가 트리거한 마스터 임포트에 한해 §1-2의 "원본 저장 X" 원칙을 벗지 않는다는 논리(도구 사용·자기 자료 이관)가 벽 ④(재위탁)에서 유효한지. 특히 원천세신고서 PDF·지급명세서 PDF를 서버가 보관하고 사장님 포털에 공개하는 경로의 재위탁 해석. **변호사 검토 필수**
- **사업소득 위하고 업로드에 RRN 평문 포함 — 사용자 승인 완료 (2026-09-28, §13-3)**. 사업소득 엑셀 템플릿은 주민등록번호가 매칭·자동등록 키라 §4-2(근로소득은 사원코드로 매칭, RRN 미포함)와 다르게 RRN을 담아야 한다. 사용자가 "예외 인정함"으로 승인 — 노출 경로(경로 A: 서버가 인증된 세무사 세션으로 다운로드 제공 / 경로 B: 노트북이 임시파일로 잠깐 들고 있다가 즉시 삭제) 중 어느 쪽으로 확정할지는 §13-3에서 계속 논의.

### 1-5. 두더지잡기 경고

T 개별약관 제10조 ① 은 "개별 기관의 스크래핑 관련 정책 변경" 을 명시. 더존조차 UI 업데이트로 대응 중. 이지원천도 같은 부담 — 셀렉터를 에이전트 코드 한 곳에 모으고, **셀렉터 실패 시 즉시 알림 + 수동 처리 안내**로 수정 사이클을 짧게 유지한다.

## §2. 역할 분담

이지원천의 확인·신고·발송 확정 3단계는 모두 **로그인 사용자**(세무사 사무소 직원)가 담당한다. 세무사·직원 권한 분리는 두지 않는다. 관리자 권한은 노트북·에이전트 설정에만 적용된다.

| 주체 | 하는 일 | 하지 않는 일 |
|------|--------|-------------|
| **사무소 사용자** (이지원천 로그인 사용자) | 급여명세서 확인·승인 / 입·퇴사 사원을 위하고에 직접 등록 후 "사원등록 완료" 체크 / **'위하고 전송'** 클릭 (게이트 1) / 위하고 자동입력된 급여명세서 검토 → **'제작'** 클릭 (게이트 2) / 접수증·납부서 검토 → **'발송 확정'** 클릭 (게이트 3) / 접수증·납부서 다운로드 | — |

```
[직원 PC — 개별 아이디]                    [이지원천 서버 (NHN)]

                                                  │ (사무실 방화벽 개방 X)
[자동화 전용 노트북 — 세무사 전용 아이디]         │
 ├ Windows 전용 계정 + VeraCrypt 시스템 암호화    │
 ├ Windows 자격 증명 관리자: 위하고·홈택스·위택스 ID/PW + 홈택스 공동인증서 PW (암호화)
 ├ 에이전트 (Python) ─────────────────────────────┘

 └ 크롬 (--remote-debugging-port, 에이전트 전용 프로필)
      ├ 위하고 T
      ├ 홈택스
      └ 위택스
```

### 3-1. 자동화 방식

| 방식 | 평가 |
|------|------|
| **CDP 연결 (Playwright `connect_over_cdp`)** | **우선.** 노트북이 전용 기기라 크롬 실행 옵션의 UX 마찰이 작다. 새 크롬 실행보다 자동화 표시가 적다. `rpa-agent` 코드(서버 통신·실패 처리·수임처 대조·자격증명 저장) 재사용 |
| 크롬 익스텐션 (노트북 크롬) | **대안.** CDP가 감지될 때 전환. 페이지 이동 간 상태 유지·파일 전달 구현 부담 |
| 새 브라우저 실행 (Playwright `launch`) | **비권장 — 기술적 이유.** 자동화 표시로 감지·보안 프로그램 충돌 위험. 오전에 "약관 위반"으로 분류했으나 정확히는 "위반 소지"였고, 전용 아이디·노트북 로컬 저장 조건에서는 약관 우려가 완화됨 |
| 위하고 내부 API 직접 호출 | 비권장. 봇 감지가 가장 쉽고 비공식 API라 언제든 깨짐 |
| 공동인증서 비밀번호 자동 입력 | **채택 (2026-09-17).** 홈택스 로그인용 세무법인 공동인증서 PW를 노트북 자격 증명 관리자에 저장하고 에이전트가 인증서 선택창에서 자동 입력. ~~키보드보안(nProtect·DreamSecurity 계열) 회피 여부는 PoC 1에서 실측~~ → **2026-09-25 이지원에서 Playwright 자동 로그인 동작 확인** (인증서 선택·비밀번호 입력 포함). 벽 ③은 §1-4 논리로 커버, 변호사 검토 필수 |
| 반자동 (엑셀 다운로드 + 수동 업로드, 결과만 기록) | **최종 폴백** (§9) |

### 3-2. 로컬 브리지 — 불필요

위하고·홈택스·위택스가 모두 같은 노트북에 있으므로 신고 파일이 기기 밖으로 나가지 않는다. 오전 안의 LAN HTTP·공유폴더·USB 브리지는 **위하고를 다른 기기에서 돌리는 구성으로 되돌아갈 때만** 재검토한다.

### 3-3. 서버 통신·인증

- 노트북 → 서버 HTTPS 폴링 (5초). 서버는 노트북에 접속하지 않는다
- 에이전트 토큰 `X-Agent-Token` (서버에는 SHA-256 해시만, 발급 시 1회 노출, 분실 시 즉시 폐기). 오전 문서의 "JWT + 익스텐션 등록 토큰" 방식은 대체

### 3-4. 설치 방식 선택지 — 사무소 기존 PC 안의 가상 PC (A안, 2026-09-25 검토 · PoC 7 대기)

이지원은 특정 노트북이 아니라 **Windows 한 대에서 도는 에이전트 소프트웨어**다(§3-3, 나가는 폴링만). 그래서 전용 노트북 외에 사무소에서 항상 켜 두는 PC 안에 **게스트 Windows(가상 PC)** 를 띄워 이지원으로 쓰는 방식을 설치 선택지로 둔다. `rpa-agent` 코드·서버 API·토큰·`rpa_jobs` 재실행 로직은 바꾸지 않는다.

```
[사무소 기존 PC (호스트) — 직원이 평소대로 사용]
 ├ 직원 화면: 엑셀 · 위하고(직원 개별 아이디) · 카톡 …
 └ 가상 PC (게스트 Windows) = 이지원
      ├ 크롬 + CDP: 위하고 T · 홈택스 · 위택스 (세무사 전용 아이디)
      ├ 보안 프로그램 · 세무사 공동인증서
      ├ rpa-agent (서버로 HTTPS 폴링)
      └ 자격 증명 관리자 + VeraCrypt 시스템 암호화 (§8-2 그대로)
```

- 가상 PC는 화면·키보드·로그인 세션이 따로라 **직원이 호스트를 쓰는 중에도 인증서 창·크롬 자동화가 방해받지 않는다** (직원 PC 익스텐션안과의 차이).
- 약관 논리(§1-2) 동일 — 사무소 소유 기기 안, 사무소 아이디, 이지원천 서버는 사이트에 접속하지 않음.

**구성 조건**

| 항목 | 조건 |
|------|------|
| 호스트 PC | **항상 켜 두는 데스크톱** (대표 PC·프린터 서버 역할 PC 등). 집에 가져가는 노트북 불가. BIOS 가상화(VT-x/AMD-V) 켜기 |
| 호스트 사양 | 아래 "사양과 속도" 표 |
| 가상화 프로그램 | 호스트 Windows **Pro → Hyper-V**(내장), **Home → VMware Workstation Pro**(2024-11부터 상업용 무료). VirtualBox 는 확장팩 상업 라이선스 제한 확인 필요 |
| 게스트 Windows | **별도 정품 라이선스 필요** (호스트 라이선스 공유 불가). Windows 11 **Home FPP/스토어 구매로 충분** — Hyper-V·VeraCrypt 조건은 게스트 에디션과 무관. OEM(DSP)은 하드웨어 귀속이라 비권장, 저가 해외 키 금지 |
| 자동 기동 | 호스트 부팅 시 가상 PC 자동 시작 (Hyper-V 자동 시작 동작 / VMware·VirtualBox 는 서비스·작업 스케줄러). 게스트는 §8-2 대로 VeraCrypt + Windows 자동 로그온 → 재부팅 후 **VeraCrypt 사전부팅 PW 1회만 사람이 입력** (가상 PC 콘솔에서, 관리자). 노트북과 절차는 같지만 **호스트가 재부팅될 때마다 같이 재부팅**되므로 입력 빈도가 노트북보다 잦다 → 호스트 Windows 업데이트 재부팅 시간을 정해 월 1~2회로 줄인다 |
| 화면 접속 | 가상 PC 콘솔 **기본 세션** 사용. Hyper-V 확장 세션·RDP 는 원격 세션으로 보고 보안 프로그램이 막거나 창을 닫으면 화면이 사라질 수 있음 → 원격지원은 게스트 안의 기존 세션 공유형 도구로 |
| 설치 | 크롬·보안 프로그램·에이전트까지 넣은 **사전 세팅 이미지**를 원격지원으로 배포, 인증서·계정 등록만 현장(원격)에서. 이미지 약 20~30GB |

**사양과 속도** — 호스트가 느리면 가상 PC도 느려지지만, 이지원 작업 시간은 대부분 **의도된 사람 속도 대기(§8-4, 단계 사이 0.5~2초·작업 사이 3~15초)와 사이트 응답 대기**라 CPU 차이는 체감이 작다. 병목은 **메모리와 디스크**다.

| 항목 | 최소 | 권장 | 부족할 때 증상 |
|------|------|------|------|
| 메모리 (호스트 전체) | 16GB (가상 PC에 6GB) | 16GB 이상 | 크롬 3개(§8-3 사이트별 프로필) + 보안 프로그램이 스왑 → 페이지 로딩 지연·타임아웃 실패, 호스트 직원 PC도 버벅임. **8GB PC 는 불가** |

### 3-5. 현재 개발·검증 중간 단계 — 맥북 한 대 구성, "데모버전" (2026-09-28, 2026-09-29 명명)

**이 §3-5 단계를 "데모버전"이라고 부른다.** §3의 최종 아키텍처(분리된 자동화 전용 노트북)는
"이지원 버전"이라 부르며, 데모버전으로 프로젝트가 완성된 뒤 착수할 나중 작업이다
(`plan/08-action-items.md` 백로그). "데모버전으로 진행"이라는 지시는 곧 이 §3-5 방식(한 기기,
이지원천·위하고·홈택스 전부 수동 로그인 세션 재사용)을 그대로 쓰라는 뜻이다.

§3~§3-4가 설명하는 최종 아키텍처(자동화 전용 노트북 또는 가상 PC 분리, 세무사 전용 아이디, VeraCrypt 암호화)는 **아직 구축 전**이다. 최종 아키텍처 구축 이전 중간 단계로, 기능 구현·검증은 **현재 사용 중인 맥북 PC 한 대**에서 진행한다.

- **이지원천 실행** — 로컬 개발 서버(프론트·백엔드)를 이 맥북에서 띄운다.
- **위하고 T 자동화 입력** — 이 맥북에서 현재 로그인돼 있는 위하고 T 세션을 그대로 사용해 자동화 입력(SmartA 급여자료입력 등, §4-2)을 구현·검증한다.
- **홈택스 신고서 입력·납부서 출력** — 이 맥북에서 현재 로그인돼 있는 홈택스 세션을 그대로 사용해 신고서 입력 및 납부서 출력(§4-4) 구현을 진행한다.

즉 §3 다이어그램에서 분리돼 있는 "위하고·홈택스·위택스를 쓰는 자동화 전용 노트북"과 "이지원천을 쓰는 직원 PC"가 이 단계에서는 **같은 기기**다. 전용 노트북/가상 PC 분리(§3-4), Windows 자격 증명 관리자·VeraCrypt 암호화(§8-2), 세무사 전용 아이디를 통한 약관 논리(§1-2)는 이 중간 단계에는 적용되지 않으며, **최종 배포 시점에 §3 본 아키텍처로 전환**해야 갖춰진다. 이 절은 그 전환 전까지의 임시 상태를 기록해 둔 것이다.

**⚠️ 예외 — 위하고 T [제작(F4)]은 맥에서 지원 안 됨 (2026-09-29 실측 확정).** SWER0101(원천징수 전자신고)에서 [제작(F4)]을 누르면 위하고가 "맥에서는 제작을 할 수 없다"는 안내를 띄운다. 국세청 암호화 정책상 전자신고 파일 제작에 Windows 전용 모듈이 필요한 것으로 보인다(§9-2 PoC 0 원본 영상도 애초에 Lenovo T14·Windows 11에서 촬영됨 — 우연이 아니었다). SWER0109(지방소득세 전자신고)도 같은 제약일 가능성이 높다(미확인).
이 제약 때문에 마감(SWTA0101·SWHM0103·SWTA0112)까지는 맥에서 실측·자동화가 가능하지만, **전자신고 파일 제작(⑨-c·⑩-b)은 맥북 중간 단계에서 끝까지 검증할 수 없다** — 반드시 Windows 11 PC(또는 최소 Windows 10)로 실측해야 한다. 최종 배포 아키텍처(§3)가 원래도 Windows 자동화 노트북을 전제했으므로 장기적으로는 문제가 안 되지만, 지금 맥북 중간 단계의 범위(§3-5 목록)에서 "위하고 T 자동화 입력"은 마감까지만이고 제작은 제외해야 정확하다.

### 3-6. 로그인 시 "데모버전/이지원 버전" 선택 — 기획 (2026-09-29)

**배경.** 데모버전(§3-5)과 이지원 버전(§3)은 실은 **같은 job 큐 폴링 아키텍처**를 쓴다
(2026-09-29 로컬 검증: 이지원천이 `RpaJob`을 큐에 넣으면 별도 에이전트 프로세스가 서버에
폴링→claim→위하고 실행→결과 회신 — 이 메커니즘 자체는 데모/이지원 버전 구분이 없다). 다른 건
**에이전트가 어디서 도는지, 로그인을 누가/어떻게 하는지**뿐이다. 지금까지는 이 차이를 코드
밖에서(터미널로 스크립트를 직접 돌리는 방식으로) 다뤘는데, 사용자가 **로그인 화면에서 명시적으로
선택**하게 만들어서 헷갈림을 없앤다 — 오늘 실제로 "위하고 전송대기중, 변동없음"에서 원인 파악에
시간이 걸렸던 게, 로컬에 에이전트가 안 떠 있다는 걸 화면이 알려주지 않아서였다.

**UI.**
- 로그인 화면에 "데모버전 / 이지원 버전" 선택(토글 또는 라디오) 추가. 기본값은 마지막 선택을
  기억(브라우저 저장).
- **데모버전** 선택 후 로그인하면 배너로 안내: "데모 모드 — 이 PC에 위하고 T·홈택스가 로그인돼
  있고, 로컬 에이전트가 떠 있어야 자동화가 동작합니다." + 에이전트 실행 명령어 안내/복사 버튼
  (`bash rpa-agent/scripts/start-chrome.sh` 등).
- **이지원 버전** 선택 후에는 그런 안내 없이, 이지원 노트북의 에이전트 상태(마지막 폴링 시각 등,
  기존 `rpa_agents` 테이블 활용)를 보여주는 정도.

**핵심 설계 질문 — 이 선택이 실제로 무엇을 바꾸는가.**
프론트엔드(브라우저)는 사용자의 로컬 PC에서 프로세스를 실행할 방법이 없다 — 에이전트를 실제로
띄우는 건 항상 사람이 터미널에서 하는 일이다. 그래서 이 선택이 바꿀 수 있는 건:
1. **UI 안내 문구/배너** — 데모버전이면 "로컬 에이전트를 직접 띄우세요" 안내, 이지원 버전이면
   에이전트 상시 가동을 전제로 한 상태 표시. (즉시 구현 가능, 리스크 낮음)
2. (확장) **작업 대기 상태 표시** — "위하고 전송" 눌렀을 때 데모버전이면 "로컬 에이전트가 잡아갈
   때까지 대기 중"이라고 명확히 보여주고, 일정 시간(예: 2분) 안 잡아가면 "에이전트가 안 켜져
   있는 것 같습니다" 같은 타임아웃 안내를 띄운다 — `rpa_jobs.created_at`과 폴링 여부로 판단 가능.

**결정 (2026-09-29):**
1. 모드는 **영구 저장하지 않는다** — 매 로그인마다 사용자가 다시 선택한다. (User/TaxOffice
   스키마에 모드 필드 추가 불필요, 로그인 폼 상태로만 존재)
2. 데모버전 배너는 **명령어 텍스트 안내 수준으로 확정** — 브라우저가 로컬 스크립트를 대신 실행할
   수 없으므로 그 이상의 친절한 유도는 추가하지 않는다.
3. **"이지원 노트북 등록 여부"는 서버가 `rpa_agents` 테이블로 판단한다.** 에이전트 설치 시 토큰이
   발급되고(`token_hash`) `tax_office_id`로 그 사무소에 귀속된다.
   - **등록됨** = 해당 `tax_office_id`에 `revoked_at IS NULL`인 `rpa_agents` 행이 하나 이상 존재.
     → "이지원 버전" 선택 시 정상 상태 화면(에이전트 목록) 노출.
   - **미등록** = 행 자체가 없음 → "이지원 버전" 선택 시 "아직 등록된 이지원 노트북이 없습니다"
     안내(설치 가이드 링크 등)로 대체 — 옵션 자체를 숨기지 않고 선택은 항상 가능하게 하되, 상태로
     구분한다.
   - **등록됐지만 꺼져 있음** = 행은 있으나 `last_seen_at`이 오래됨(폴링 주기 기준 임계값, 예 2~3분
     초과) → "노트북 꺼져 있음/오프라인" 상태로 별도 표시. (등록 없음과 오프라인을 같은 화면에서
     구분해 보여줘야 문의가 줄어든다.)

**아직 하지 않은 것 (구현 범위 밖):** 로그인 API 응답에 모드/에이전트 상태 포함 여부, 프론트
로그인 화면 실제 컴포넌트, 오프라인 판정 임계값(초 단위) 확정. 착수 시점에 구현한다.

```
        ▼
```

### 4-1. 전송 (게이트 1) — 등록 검사

| 게이트 | 상태 |
|--------|------|
| 미승인 급여항목이 있는 거래처 차단 ("입력 확인" = 승인 완료) | 배포됨 |
| 자료 없는 거래처 차단 | 배포됨 |
| 사업자번호 없는 거래처 차단 (수임처 검색 불가) | 배포됨 |
| 같은 신고·거래처에 대기·진행 중 작업이 있으면 차단 | 배포됨 |
| **이번 달 입·퇴사가 있는 거래처는 "위하고 사원등록 완료" 확인 전까지 차단** | 신규 (이지원천의 입·퇴사 변동 데이터로 대상 자동 선별) |
| 반기납부 거래처는 신고 대상 월이 아니면 신고 단계에서 제외 (§4-7) | 신규 |
| **소득유형(근로/사업/기타/일용)별 원자적 전송 — 자동화 안 된 유형이 섞여 있으면 거래처 전체 차단** | 신규 (2026-09-28 결정) |

- 위하고에 올라가는 것은 직원별 급여명세서가 아니라 **22컬럼 급여대장 엑셀**(`payroll_excel.py`)이다. 흐름 안에서는 "급여자료"로 부른다
- 엑셀은 사용자 PC에 내려받지 않는다. **노트북이 서버 API로 직접 받는다** (공유폴더·USB 경유는 승인 우회·중복·파일 잔존 문제로 기각)

**2026-09-28 결정 — 소득유형별 원자적 전송 (사용자 확정)**

원천징수이행상황신고서는 거래처+귀속월 단위로 근로(A01)·일용(A03)·사업(A25)·기타(A42) 소득을 **전부 합산한 신고서 한 장**이다(§13-3, `WhtFormPreview` A01~A42 합산 미러링). ②제작(게이트2)은 그 시점에 위하고에 들어가 있는 모든 소득을 통째로 마감·신고하므로, 소득유형 하나라도 위하고에 덜 들어간 채 제작하면 그 소득분이 빠진 불완전한 신고서가 만들어진다. 따라서:

- **①전송은 소득유형별 선택 전송이 아니라, 거래처 단위 원자적(all-or-nothing) 전송이다.** 그 거래처에 데이터가 있는 소득유형은 전부 한 번에 같이 전송돼야 하고, 데이터가 없는 유형은 "자료없음"으로 자동 체크되어 함께 전송(=처리할 것 없음으로 넘어감) 처리한다.
- **차단 조건 확장**: 기존 "미승인 자료 있으면 차단"은 이미 소득유형 구분 없이 전체 엔트리를 본다(`allEntries` 기준, 정상). 여기에 **"자동화가 아직 없는 소득유형에 실제 데이터가 있으면 그 거래처 전체를 차단"** 을 추가한다 — 지금은 근로소득(WAGE)만 `wehago.py::upload_payroll`로 자동화돼 있고, 사업소득(BUSINESS)은 §13-3 경로 B로 구현 중, 기타(OTHER)·일용(DAILY)은 자동화가 전혀 없다. 사업소득 자동화가 완성되면 그 차단만 해제한다.
- **표시**: 전송 모달에 거래처별로 근로/사업/기타/일용 4칸을 보여주되, 유형별로 "선택"하는 체크박스가 아니라 **상태 표시**다 — 자료없음 / N건 승인완료 / N건 미승인 / 자동화 미지원(자동화 없는데 데이터 있음). 거래처 전체가 "전송 가능"인지 아닌지 하나의 판정만 있고, 부분 선택은 없다.

**2026-09-30 결정 — 소득유형별 "전송 완료" 판정에 명세서 추가입력 포함 (사용자 확정)**

근로소득은 급여자료입력(SWSA0101) 하나만 끝나면 원천징수이행상황신고서 계산에 바로 반영되지만, **일용·사업·기타소득은 국세청에 별도로 지급명세서(간이지급명세서)를 제출해야 하는 소득**이라 자료입력 화면 하나로는 신고 요건이 끝나지 않는다. 소득유형별 "전송 완료" 판정 기준을 다음과 같이 구분한다:

| 소득유형 | 위하고 자료입력 화면 | 전송 완료 판정에 추가로 필요한 것 |
|---------|---------------------|-----------------------------------|
| 근로소득 | 급여자료입력 (SWSA0101) | 없음 — 자료입력만으로 완료 |
| 일용소득 | 일용직 급여자료입력 | **명세서(간이지급명세서) 추가입력까지 완료** |
| 사업소득 | 사업소득자료입력 (SWBU0102) | **명세서(간이지급명세서) 추가입력까지 완료** |
| 기타소득 | 기타소득자료입력 | **명세서(간이지급명세서) 추가입력까지 완료** |

- 일용·사업·기타소득은 자료입력 화면에 지급 데이터를 넣는 것과, 국세청 제출용 지급명세서(간이지급명세서) 화면에 데이터를 넣는 것이 **서로 다른 화면·별도 작업**이다. 지금까지 §4-2 자동입력 범위는 자료입력만 다뤘는데, 이 결정 이후로는 해당 소득유형에 대해 **명세서 추가입력까지 자동입력이 끝나야** "전송 완료"(게이트 2 알림 발송 가능 상태)로 인정한다.
- ⑨-b `close_business_income_report`(SWHM0103, 사업소득 간이지급명세서 [마감], §4-4)는 게이트 2(제작) 단계의 "마감" 자동화다. 여기서 새로 요구하는 게이트 1(전송) 단계의 "명세서 추가입력"은 마감 이전에 명세서 자체에 데이터를 채우는 별도 단계이며, 아직 자동화 범위(§4-2)에 없다 — 추가해야 한다.
- 일용·기타소득은 자료입력 화면 자동화 자체가 아직 코드에 없다(§4-1 "자동화 미지원" 상태, `plan/08-action-items.md` 참고). 이 결정은 향후 자동화 구현 시 적용할 완료 기준이며, 지금 당장 새 자동화를 만드는 작업 지시는 아니다.

### 4-2. 위하고 자동입력 (게이트 1 ~ 게이트 2 사이)

게이트 1('위하고 전송') 직후 노트북이 실행하는 자동입력 단계다. **급여자료 입력까지만** 자동으로 하고 여기서 멈춘다 — 원천세·지방세 마감·제작은 게이트 2 이후(§4-4)로 미룬다.

1. 급여대장 엑셀 수신 → `%USERPROFILE%\.easyone-agent\work\` 임시 보관 (처리 후 즉시 삭제)
2. 로그인 상태 확인, 필요 시 노트북에 저장된 전용 아이디로 자동 로그인 (실패 1회 즉시 에이전트 정지 — 계정 잠금 방지)
3. 사업자번호로 수임처 검색 → 결과 정확히 1건 → 화면 상호·사업자번호를 작업 스냅샷과 대조 ((주)/주식회사·공백·하이픈 무시). 어긋나면 중단
4. **사원 존재 확인** — 엑셀의 사원(사원코드·이름)이 위하고 사원 목록에 모두 있는지 확인. 없으면 "위하고 미등록 사원: 홍길동"으로 실패 회신 (사무소 사용자의 사원등록 누락 대비 2차 안전망). 사원 인적사항은 서버로 가져오지 않는다
5. 급여자료 입력 → **대조 (인원·총지급액·비과세)** → 여기서 정지, 게이트 2 알림 발송

| 단계 | 대조 항목 (위하고 화면 vs 이지원천 승인값) | 불일치 시 |
|------|----------------------------------------|----------|
| 급여자료 입력 (자동) | 인원, 총지급액, 비과세 | 해당 거래처 중단, 게이트 2 진입 불가 |

- 한 거래처가 실패해도 다른 거래처는 계속 진행
- **단계 진행 기록** — 어느 단계까지 끝났는지 작업에 기록하고, 재실행 시 끝난 단계는 건너뛴다 (급여 중복 업로드 방지)
- **서버 전송 범위** — 대조는 노트북에서 하고 서버에는 "일치/불일치"와 **불일치일 때의 차이 항목만** 보낸다 (위하고 원본 값 전체를 서버에 두지 않음, §1-2 ④)
- 자동입력 대상은 근로소득 급여자료. 사업소득·일용근로소득·기타소득의 별도 입력 화면 처리는 추가 실측 후 반영 (§9-2 촬영 목록·§11 후속 검토) — **단, §4-1 "2026-09-30 결정"에 따라 이 세 소득유형은 자료입력 화면뿐 아니라 명세서(간이지급명세서) 추가입력 화면까지 자동입력해야 "전송 완료"로 판정한다.**

### 4-3. 알림 (로그인 사용자)

작업 3개 게이트 사이마다 이지원천 알림창이 로그인 사용자에게 뜬다. 알림 대상 = `requested_by_user_id`(요청자) + **같은 세무사 사무소의 로그인 중인 다른 사용자**(백업). 요청자가 부재 시 다른 사무소 사용자가 이어받는다.

| 시점 | 알림 목적 | 사용자 액션 |
|------|-----------|-------------|
| 자동입력 완료(§4-2) 후 | 위하고에 입력된 급여명세서 검토 요청 | 명세서 확인 → **'제작'** (게이트 2) |
| 홈택스·위택스 접수증 회수(§4-5) 후 | 접수증·납부세액·납부기한 검토 요청 | 검토 → **'발송 확정'** (게이트 3) |
| 어느 단계든 실패·불일치 | 실패 단계·차이 항목·수동 처리 안내 | 수동 처리, 재시도 필요 시 재전송 |

- 거래처별 표시: ✅ 완료 / ⚠️ 불일치(차이 항목) / ❌ 실패(단계·사유 + 수동 처리 안내)
- 로그아웃 상태였던 사용자도 놓치지 않도록 다음 접속 시 보여줄 알림 목록 유지

### 4-4. 제작 (게이트 2) — 위하고 마감·제작 + 홈택스·위택스 일괄

- **[제작] 버튼은 이지원천 로그인 사용자 누구든 클릭 가능** — 세무사·직원 권한 분리 없음

- **[제작] 클릭 하나로 아래를 순차 실행** (실행 중 실패 시 해당 거래처는 즉시 중단, 다른 거래처는 계속):

| ⑪ | 홈택스 | 파일변환신고 | 로그인(아이디 → 공동인증서 → 세무대리 관리번호, §9-2) → 세금신고 > 원천세 신고 > 일반신고 > **파일변환신고** → [파일선택] → [파일검증하기] → 변환파일 비밀번호 → 검증결과내역(형식·내용검증) | **제출 직전 원천세 합계를 이지원천 값과 재대조** → [제출하러 가기] → **일괄접수증 확인 후 성공 처리** |
| ⑫ | 위택스 | 특별징수 회계파일신고 | **홈택스 접수 성공 거래처만** → 로그인 → 신고 > 지방소득세 > 특별징수 > 특별징수신고 > **특별징수 회계파일신고** → [파일첨부] → 파일비밀번호 → [파일변환하기] → 서식검증 및 제출 → 제출결과확인 | 홈택스 실패 거래처는 지방세도 건너뛰고 함께 실패 표시 |

- 위하고 T에는 **[전송]이 없음** (PoC 0). 파일은 브라우저 다운로드가 아니라 위하고 로컬 모듈이 `C:\Douzone\Wehago\…`에 저장 → Playwright 다운로드 이벤트가 아니라 **저장 폴더 감시**로 수신 (정확한 경로는 실측)
- **변환파일 비밀번호**(영문 소문자·숫자 8~15자리)는 제작 시 입력하고 홈택스·위택스 제출 시 다시 입력 → 에이전트가 작업마다 생성해 노트북에만 보관, 제출 후 파일과 함께 삭제
- 원천세·지방소득세 신고 파일은 이지원천이 아니라 위하고 T [제작]으로 노트북에 생성 (이지원천에는 원천징수이행상황신고서 전자파일 생성 기능이 없음 — `04-excel-outputs.md` Phase 3 이후 항목)
- 홈택스 원천세 신고 후 지방소득세로 이어지는 연계 경로 — PoC 0 영상에서는 위택스에 따로 로그인해 파일을 올림. 연계 경로 유무는 추가 실측
- **재실행 안전** — ⑨~⑫ 각 단계별 진행을 `rpa_jobs`에 기록하고, 노트북 재기동 후 재실행 시 끝난 단계는 건너뛴다 (위하고 재마감·홈택스 중복 제출 방지)

### 4-5. 결과 수집 (게이트 2 이후 자동)

- 접수증·납부서(국세·지방세) PDF를 노트북이 회수 → 서버 `ClientFilingResult`(`source=RPA`, `published_at=NULL`)에 **비공개 상태로 등록**
- PDF가 해당 거래처·귀속월의 것인지 사업자번호로 대조 후 등록
- 납부서에서 **납부세액·전자납부번호·납부기한**을 추출해 칸에 채운다 (포털의 "얼마를 언제까지" 표시에 필수)
- 납부세액 0원이면 납부서가 없을 수 있음 — "납부서 없음"을 실패로 처리하지 않는다
- 이 단계에서는 **사장님 포털 공개·납부안내 문자 발송이 일어나지 않는다**. 로그인 사용자에게 게이트 3 알림 발송

### 4-6. 발송 확정 (게이트 3) — 포털 공개 · 납부안내 문자

- **'발송 확정' 버튼은 이지원천 로그인 사용자 누구든 클릭 가능** (게이트 2와 동일 권한)
- 대상은 §4-5에서 접수증·납부서 회수 ✅인 거래처만 선택 가능. 실패·불일치 거래처는 확정 대상에서 자동 제외
- 사용자가 접수증·납부세액·납부기한을 검토한 뒤 클릭 → 서버가 아래 두 개를 **동시에** 트리거:
  1. **사장님 포털(`12-owner-portal.md`)에 접수증·납부서 공개** — `ClientFilingResult.published_at`·`confirmed_by_user_id` 채움
  2. **납부안내 문자 발송** — 포털 링크(30일 수명, `plan.md` 결정 10) 동봉, 본문은 합계·기한만
- 이지원천 조회·다운로드는 게이트 3 전이라도 사무소 사용자에게 열려 있음 (내부 검토용). 사장님 포털·문자만 게이트로 막는다
- **사용자 PC 자동 저장은 불가** (웹은 사용자 PC에 파일을 몰래 쓸 수 없음) → 알림창의 **"접수증·납부서 받기" 버튼** (여러 거래처면 ZIP)
- 문자 발송 활성화는 `13-messaging-activation.md` 전제
- 확정 없이 30일이 지나면 알림 재발송, 60일 지나면 자동 확정 여부는 `13-messaging-activation.md`와 함께 결정 (초기에는 자동 확정 없음)

### 4-7. 사원등록 안내 (자동화 제외)

사원등록(주민번호 등 인적사항, 입사일·퇴사일)은 민감정보이므로 RPA가 건드리지 않는다.
전송 화면에서 대상 거래처에 안내한다:

> "이번 달 입사 2명(홍길동, 김철수)·퇴사 1명이 있습니다. 위하고 T 사원등록에서 직접 입력한 뒤 '사원등록 완료'를 체크하세요. 주민번호 등 인적사항은 자동화하지 않습니다."

## §5. 작업 상태 (거래처 × 귀속월)

```
전송대기
  └─ 게이트 1 ('위하고 전송') ─→
급여자료입력 → 명세서검토대기
  └─ 게이트 2 ('제작') ─→
원천세마감·제작 → 지방세마감·제작 → 홈택스신고 → 위택스신고 → 결과수집완료(비공개)
  └─ 게이트 3 ('발송 확정') ─→
포털공개·문자발송 → 완료
어느 단계든 실패 → 실패(단계·사유) + 수동 처리 안내, 끝난 단계는 재실행하지 않음
```

### 8-3. 사이트별 세션 운영 원칙 (2026-09-25 결정)

**병렬 단위 = 사이트별 로그인 세션.** 위하고·홈택스·위택스는 각각 **크롬 1개(전용 프로필 + CDP 포트) = 작업 대기열 1줄**로 운영한다.

| 사이트 | 크롬 (CDP 포트) | 이 줄에서 순서대로 처리하는 작업 |
|------|------|------|
| 위하고 T | 9222 | 급여자료 입력 · 위하고 가져오기 · 원천세·지방세 마감·파일 제작 |
| 홈택스 | 9223 | **원천세 파일변환신고 + 증명원 발급** (한 줄) |
| 위택스 | 9224 | 지방세 특별징수 회계파일신고 |

- 세 줄은 서로 동시에 돈다. 한 줄 안에서는 한 건씩, **직원별로 번갈아** 처리한다 (2026-09-25 구현, `next_fair_job_id`): 대기 작업이 있는 직원 중 이 줄에서 마지막으로 작업이 시작된 지 가장 오래된 직원(처음이면 맨 앞)의 가장 먼저 요청한 작업을 가져간다. 한 직원이 30건을 몰아 넣어도 다른 직원 작업이 사이사이 끼어들고, 한 직원의 요청 순서는 그대로 지켜진다.
- **홈택스는 자동화 아이디를 2개로 나눌 수 없다** (사용자 확인) → 원천세 신고와 증명발급은 같은 세션을 번갈아 쓴다. 서버 claim 의 동시 실행 제한을 "작업 종류별"에서 "사이트 세션별"로 바꾸고, `MONTHLY_PRODUCTION` 의 홈택스 단계는 홈택스 줄에 선다 (`plan/17-certificate-issuance.md` §4-4 mutex 의 구체화).
- 크롬 창이 아니라 **크롬 프로그램을 따로 실행**한다 (`start-chrome.ps1 -Port … -ProfileDir …`). 같은 크롬의 새 창·탭은 쿠키를 공유해 분리되지 않는다. 에이전트는 사이트별 CDP 주소를 따로 받는다 (지금은 `EASYONE_CDP_URL` 하나 — 수정 필요). 다운로드 폴더도 크롬별로 분리.
- 이지원 RAM **16GB 권장** (크롬 3개 + 에이전트).

**로그인 유지·로그아웃**

1. 대기 작업이 있으면 로그아웃하지 않고 기존 로그인을 이어 쓴다.
2. **'로그인 연장' 버튼은 누르지 않는다.** 작업 중에는 요청이 계속 오가서 연장 팝업이 뜨지 않고, 할 일 없이 연장해 로그인을 붙잡아 두는 것은 사람이 하지 않는 패턴이다. 예외: 작업 진행 중에 연장 팝업이 뜨면 그때만 누른다 (신고 도중 세션이 끊기면 진행 위치를 잃는다).
3. 작업 없이 **30분**이 지나면 사이트별로 명시적으로 로그아웃한다. 사이트가 먼저 자동 로그아웃하면(위택스 세션 30분 등) 그대로 둔다. 에이전트 종료·퇴근 시에도 로그아웃.
4. 다음 작업이 오면 로그인 상태를 먼저 확인하고, 풀려 있으면 저장된 정보로 **자동 로그인** (홈택스: `plan/17-certificate-issuance.md` §3-9-7-4). 로그인 실패 1회에 에이전트 정지 (§8-1).

**동시 운영 실측 (이지원, 미실시)** — 크롬 3개를 띄워 위하고 입력·증명발급·위택스 로그인을 반나절 동시 실행하고 다음을 확인한다: 로그인 유지, 봇 탐지 문구, PC 전역 보안 프로그램(nProtect·AnySign) 충돌(필요하면 로그인 순간만 사이트 간 잠금), 창 포커스 가로채기(`bring_to_front` 최소화), 작업 중 연장 팝업 발생 여부.

### 8-4. 봇 탐지 대응 설계 (2026-09-25)

**원칙: 속이는 것이 아니라, 사무소 직원이 쓰는 환경·속도·패턴 그대로 돌린다.** 이지원은 세무사 본인 계정·본인 인증서·사무소 IP 로 본인 업무를 대신하는 도구다. 탐지를 "우회"할 대상은 봇처럼 보이는 흔적이지, 사이트의 보안 장치(캡차·추가인증·보안 프로그램)가 아니다. 세무대리 계정·공동인증서가 차단되면 사무소 업무 전체가 멈추므로, 들키지 않는 것보다 **걸렸을 때 즉시 멈추는 것**이 더 중요하다.

**조사한 기법과 채택 여부**

| 층위 | 대표 기법 | 채택 | 이유 |
|------|------|------|------|
| 브라우저 지문 | `navigator.webdriver`, `--enable-automation` 안내줄, headless UA, plugins·WebGL·언어 불일치 | **실제 설치 크롬 + CDP 부착(현행)** — 이 흔적이 원래 없다 | Playwright `launch`/headless 는 흔적이 남는다 |
| 지문 위장 | playwright-stealth·puppeteer-extra stealth 스크립트, 안티디텍트 브라우저(Multilogin 등), Camoufox | **미채택** | 진짜 크롬에 위장 스크립트를 덧씌우면 오히려 값이 서로 어긋나 더 잘 걸린다 |
| CDP 흔적 | `Runtime.enable` 부작용 탐지 → rebrowser-patches·patchright 로 패치 | **보류** — 실측에서 문제될 때만 | 관공서·위하고가 이 수준을 검사한다는 근거 없음. 패치는 Playwright 업데이트 부담 |
| 네트워크 | 프록시·IP 로테이션, TLS(JA3/JA4) 위장 | **미채택** — 사무소 고정 IP, 진짜 크롬 TLS | 세무대리 계정이 여러 IP 에서 접속하는 편이 더 이상하다 |
| 행동 | 키 입력 간격, 생각 시간, 마우스 이동, 스크롤 | **채택 (가볍게)** | 아래 행동 규칙 |
| 계정 패턴 | 로그인 빈도, 동시 세션, 새벽 작업, 처리량 | **채택** | §8-3 + 아래 속도 규칙 |
| 캡차·추가인증 | 캡차 풀이 서비스, OTP·QR 자동 처리 | **금지** | 보안 장치 무력화. 뜨면 사람에게 넘긴다 |

**이지원천 적용안**

1. **환경 — 현행 유지 + 보완**
   - 설치된 크롬(자동 업데이트 유지) + 사이트별 전용 프로필 + CDP 부착, 창 표시(headless 금지), UA·언어·시간대 변경 금지.
   - `start-chrome.ps1` 에 `--enable-automation`·`--headless` 류 옵션을 넣지 않는다 (현행 준수).
   - **보완 완료 (2026-09-25):** 증명원 자동 로그인 경로 `execute_phase1` 이 `p.chromium.launch()` 로 새 브라우저를 띄우던 것을 떠 있는 크롬에 CDP 로 붙어 로그인 상태 확인 → 풀렸을 때만 로그인하도록 바꿨다. 브라우저·로그인은 닫지 않고 다음 작업이 이어 쓴다 (§8-3). 공동인증서 로그인 단계는 아직 없음 (`plan/17-certificate-issuance.md` §3-9-7-4).
2. **행동 — 사람 속도, 사이트별 차등 (2026-09-25 사용자 결정)**
   - **위하고는 사설 업체라 신중하게, 홈택스·위택스는 다른 업체들도 스크래핑·자동화를 흔히 하므로 신속성 우선.**

     | 사이트 | 단계 사이 대기 | 작업과 작업 사이 | 글자 입력 간격 |
     |------|------|------|------|
     | 위하고 | 0.5~2초 | 5~15초 | 50~150ms |
     | 홈택스·위택스 | **0.5~1초** | **3~7초 (최대 7초)** | 30~80ms |

     구현: `rpa-agent/easyone_agent/pace.py`(`PACE`), `rpa/certificate-agent/certificate_agent/pace.py`(홈택스, 같은 값 유지).
   - 아이디·비밀번호·검색어는 **한 글자씩 입력** (`press_sequentially`). 홈택스 로그인의 `fill()` 은 교체 완료 (키보드보안이 키 이벤트를 요구할 수도 있다).
   - 클릭은 요소 클릭(`locator.click`, 브라우저가 실제 마우스 이벤트 발생). 고정 `sleep` 대신 요소 상태를 기다린 뒤 짧은 무작위 대기.
     `issue_flow.py` 의 1~5초 고정 대기는 대부분 화면 렌더 대기라 홈택스 실측 없이 줄이지 않는다 — 요소 대기로 바꾸면 발급 1건당 시간을 더 줄일 수 있다 (후속).
   - 마우스 궤적 흉내·무작위 스크롤은 넣지 않는다 — 효과 근거가 약하고 실패 지점만 늘린다.
3. **속도·시간대 — 사람 업무량 범위**
   - 같은 사이트에서 작업과 작업 사이 무작위 간격 (위 표).
   - 사이트별 **시간당 상한** (초안: 증명원 발급 60건/시간, 위하고 거래처 전환 60곳/시간 — 실측 후 조정). 넘으면 대기열에서 쉬었다 간다.

4. **탐지 신호 → 즉시 정지 (가장 중요)**
   - 캡차·"자동입력 방지"·추가인증(QR·OTP)·접속 차단·"비정상 접근" 문구, 예상 밖 로그아웃이 2회 연속이면 **해당 사이트 줄을 정지**하고 관리자에게 "사람 확인 필요"를 알린다. 자동 재시도·자동 풀이 금지.
   - 사람이 이지원에서 직접 해결한 뒤 [재개]를 눌러야 다시 돈다.
   - 신호 문구 목록은 `wehago.py` 로그인 실패 사유 표·`poc1_login_check.py` 의 목록을 한곳으로 모아 세 사이트 공통으로 쓴다.

**구현 순서 (제안)**: ① 탐지 신호 → 사이트 줄 정지·알림·재개 ② 입력·대기 규칙 공통 함수(`human_type`·`think`) ③ 작업 간격·시간당 상한·업무 시간 (서버 claim 에서 판단) ④ `execute_phase1` 의 `launch` 제거 ⑤ `Runtime.enable` 흔적은 §8-3 동시 운영 실측 때 함께 확인 후 판단.

### 9-4. 후속 작업 — 금액 검증 확장 (2026-09-25 정리, 미착수)

§9-3 대조는 **지급액 계·비과세 합계**만 본다. 소득세·4대보험은 엑셀 값이 위하고에 **그대로 들어가므로**
(위하고는 업로드 때 다시 계산하지 않는다) 틀린 값이 들어와도 지금 대조로는 잡히지 않는다.

**(a) 비과세를 제출·미제출로 나눠 대조** — 위하고 합계 칸은 비과세를 지급명세서 작성여부로 나눈다
(식대 P01·보육 Q02 = 제출, 자가운전 H03 = 미제출). 지금은 합계만 비교해 사무소가 작성여부 X 코드로 잘못 등록해도 못 잡는다.

**(b) 원천세 신고서 총지급액 확인** — 신고서 총지급액은 미제출 비과세를 뺀 금액이다
(서도 2026-06: 12,800,000 − 자가운전 200,000 = 12,600,000). 이지원천 백엔드의 신고서 계산이 이렇게 하는지 확인 필요.

**(c) 소득세·지방소득세 검증** — 이지원천 계산의 현재 한계와 위하고 값 비교 방법.

이지원천 계산 (`services/tax_calc.py:64`, 간이세액표 `wage_tax_table.py:87`):
- 부양가족 **1명 고정**: `collect.py:784` 하드코딩. `PayrollEntry.dependents` 칸은 있지만 입력하는 곳이 없다
- 8~20세 자녀 **0명 고정**: 자녀 수 저장 칸이 없다
- 원천징수 비율 **100% 고정**: 80/120% 선택이 없다
- 거래처가 보낸 급여대장에 소득세 값이 있으면 그 값을 쓴다 (계산값과 다르면 `_calc_diffs`에 차이를 기록)

→ 부양가족이 있는 사원은 이지원천이 계산한 소득세가 실제보다 많을 수 있다. 위하고 사원등록에는 이 입력값이 있다
(사원 그리드 `Left_grid`: `num_20family`·`num_60family`·`yn_mateded`·`rate_adjust` 등, 필드 뜻은 실측 필요).

| 방법 | 방식 | 장단점 |
|------|------|--------|
| **① 입력값 맞추기 (권장)** | 위하고 사원등록의 부양가족·자녀·원천징수 비율을 이지원천 사원에 가져와(§12 가져오기 확장) 처음부터 같은 조건으로 계산. 에이전트는 업로드 전에 위하고 사원 그리드 값과 이지원천 값을 비교해 다르면 멈춘다 | 위하고 데이터를 바꾸지 않는다. 이지원천 `Employee`에 칸 추가·마이그레이션 필요 |
| ② 위하고 산출식 읽기 | 공제항목 금액 옆 [산출식>] 버튼이 위하고 계산값을 보여 주는지 실측. 보여 주면 저장 없이 읽어 비교 | 비파괴. 버튼 동작 미실측 |
| ③ 위하고 재계산과 비교 | 업로드 뒤 [재계산] → “소득세 재계산”만 체크 → 위하고가 계산한 소득세를 엑셀 값과 비교. 다르면 알리고, 엑셀 값으로 다시 올릴지 사무소가 결정 | 위하고가 사원등록 조건 그대로 계산하므로 가장 정확. 대신 저장된 값을 바꾸므로 되돌리려면 재업로드 필요 |

- 지방소득세는 소득세 × 10%, 10원 미만 절사로 양쪽 규칙이 같은지만 대조하면 된다
- 예외: 연말정산 환급·추징 월, 중도 퇴사자 정산, 사무소가 급여대장에 직접 적은 소득세 — 이 경우 불일치는 정상일 수 있어 “확인 필요”로만 알린다

**① 입력값 맞추기 — 계산 로직·데이터 칸은 구현 완료 (2026-09-28, 마이그레이션 `a1b2c3d4e5f6`).**
`Employee`에 `dependents_count`(부양가족수, 기본 1)·`children_count`(8~20세 자녀수, 기본 0)·
`withholding_rate_adjust`(조정율 80/100/120%, 기본 100) 추가. `wage_tax_table.lookup_wage_tax`·
`tax_calc.calculate_withholding_tax`가 `rate_adjust`를 받아 별표2 비고 6호대로 최종 세액에 곱하도록
확장했고, `collect.py`가 하드코딩된 `dependents=1` 대신 매칭된 Employee 값을 쓰도록 바꿨다

- 노트북 설치 가이드·패키징 (작업 스케줄러 등록)
- **§12 위하고 데이터 임포트** — 서버: 작업 종류(`WEHAGO_MASTER_IMPORT_ALL`·`WEHAGO_CLIENT_IMPORT`) 추가, `Client.wehago_synced_at`·`wehago_import_status`, `ClientFilingResult.source=WEHAGO_IMPORT`, 임포트 API 4종(§12-6). 에이전트: 위하고 수임처 목록·사원 목록·신고이력·지급명세서 PDF 수집 흐름. 프론트: 관리자 초기 임포트 화면, 수임업체 등록 폼 "위하고에서 가져오기" 옵션, 진행률 표시. **PoC 6 선행 필수**

**정리 대상**
- `rpa-agent/easyone_agent/wehago.py`의 `launch_persistent_context` 부분 — CDP 연결로 교체
- `rpa/poc-security/` (pywinauto SmartA용): 대상이 위하고 T·홈택스·위택스로 바뀌어 불일치. **삭제 권장** (별도 확인 후)

## §11. 후속 검토

- **변호사 검토 (유료화 전 필수)** — §1-4, 특히 "실행 주체"와 "로컬 암호화 저장 후 자동 로그인"을 명시적으로 질문
- **모니터링** — 셀렉터 실패 즉시 알림, 사무소 사용자에게 수동 처리 안내
- **확장** — 연말정산 반영 월·수정신고·기한후신고
- **위하고 §4-2 자동입력 화면 세분화** — 근로·사업·일용 3종 화면 실측 후 표에 추가 (T 개별약관 §6 81·89·118호)
- **부가세·종소세 릴레이** (`15-filing-relay.md`) — 같은 노트북 구조 재사용
- **4대보험 EDI** (`06-insurance.md`) — 업무대행기관 공동인증서 로그인이 필요. 홈택스와 동일하게 인증서 PW를 노트북 자격 증명 관리자에 저장·자동 입력하는 구조 재사용
- **더존 협상 카드** — T 개별약관 제10조 ①·제12조 ① ("스크래핑 방식") 근거로 자동화 정당성 협상 가능
- **§12 임포트 스코프 확대** — 사업·일용·기타소득 지급명세서, 4대보험 자격 이력, 위하고 부속 서류(원천징수부 등)까지 이관 범위 확대 (첫 릴리즈 후 세무사 요구 청취)

## §12. 위하고 → 이지원천 데이터 임포트 (초기 세팅 · 신규 수임업체)

> 2026-09-17 결정. 이지원천을 처음 도입하는 사무소가 위하고에 이미 쌓아둔 자산 (수임업체 마스터·사원 마스터·과거 원천세신고서·지급명세서)을 재입력 없이 그대로 이관할 수 있게 한다. 이후에도 수임업체를 신규 등록할 때 사용자가 지정한 (상호·사업자번호) 1건만 같은 방식으로 추가 임포트한다.
>
> 이 기능은 §1-2 원칙("위하고 원본 데이터 서버 저장 X")의 **명시적 예외** — 예외 성립 근거는 §12-4, 벽 ④(재위탁) 해석은 §1-4 변호사 검토에 포함.

### 12-1. 트리거

| 트리거 | 대상 | 실행자 | 연결 화면 |
|--------|------|-------|-----------|
| **초기 세팅 임포트** | 위하고에 등록된 수임업체 중 관리자가 고른 부분집합 (전체 선택 가능) | 관리자 | 관리자 대시보드 "위하고 초기 임포트" |
| **신규 수임업체 임포트** | 사용자가 지정한 (상호·사업자번호) 1건 | 사용자 | 수임업체 등록 폼 "위하고에서 가져오기" 체크박스 |

- 수임업체 아이디로 로그인해 소유·관리하는 수임처 중에서만 가져옴 (권한 밖 데이터는 위하고가 반환하지 않음)
- 세무사 사무소가 위하고에 등록된 모든 수임처를 이지원천으로 옮기지 않을 수 있으므로 **초기 세팅에서도 선택 UI 필수** (수임처 100+ 사무소 대비)

### 12-2. 데이터 스코프

| 단계 | 위하고 원본 | 이지원천 저장 위치 | 초기 세팅 | 신규 추가 |
|-----|------------|-------------------|----------|----------|
| A. 수임업체 마스터 | 상호, 사업자번호, 대표자, 업태·종목, 주소, 신고 주기(매월/반기), 담당 세무사 | `Client` | 필수 | 필수 |
| A. 사원 마스터 | 사원코드, 이름, **주민번호**, 입사일·퇴사일, 소득구분(근로/사업/일용/기타), 부서·직급 | `Employee` (`rrn_encrypted`) | 필수 | 필수 |
| B. 원천세신고서 이력 | 귀속월, 인원, 총지급액, 소득세, 지방소득세, 납부기한, 접수번호 | `ClientFilingResult` (`source=WEHAGO_IMPORT`, `published_at=NULL`) | 최근 N개월 (기본 12) | 사용자 옵션 |
| C. 지급명세서 원본 PDF | 근로 간이·연간 우선, 사업·일용·기타는 옵션 | `ClientFilingResult` 첨부 | 근로만 기본 | 사용자 옵션 |

- **주민번호**: 노트북 → 서버 API 전송 구간은 TLS, 서버에서 기존 `Employee.rrn_encrypted` 필드에 암호화 저장 (`10-privacy-security.md` §2.2 규칙). 임포트 데이터는 AI 파싱 파이프라인 **미경유** — LLM에 절대 전달하지 않음
- **초기 세팅의 신고이력 기간**은 관리자가 조정 가능 (기본 12개월, 최대 5년)
- 지급명세서 종류 우선순위: 근로 간이(분기) → 근로 연간 → 사업 간이 → 일용 → 기타. 후순위는 실측 후 확대 (§9-2 후속 촬영 목록과 연동)

**초기 세팅 임포트**
```
[관리자 대시보드]
 ① "위하고 초기 임포트" → 위하고 로그인 상태 확인 → 수임처 목록 미리보기
 ② 대상 수임처 선택 + 신고이력 기간 + PDF 임포트 여부 → 실행
        │ 서버: WEHAGO_MASTER_IMPORT_ALL 작업 등록 (선택 대상·옵션 스냅샷)
        ▼
[자동화 노트북]
 ③ 위하고 로그인 → 수임처 목록에서 대상 하나씩 반복
 ④ 수임처마다: 마스터 → 사원 목록 → 신고이력(N개월) → 지급명세서 PDF(옵션)
        │ 서버: 수임처 단위 결과 API 전송 (성공/실패/차이) — 진행률 실시간 반영
        ▼
[관리자 대시보드]
 ⑤ 진행률 (M/N 수임처 완료), 실패·스킵 목록, 재실행 버튼
```

**신규 수임업체 임포트**
```
[수임업체 등록 폼]
 ① 상호·사업자번호 입력
 ② "위하고에서 사원·신고이력 가져오기" 체크 (+ 신고이력 기간·PDF 옵션)

        │ 서버: Client 레코드 생성(빈 상태) + WEHAGO_CLIENT_IMPORT 작업 등록

[등록 화면]
```

### 12-4. §1-2 정책 예외 조항

- **원칙 유지**: RPA 운영 중(§4-2·§4-4)에는 위하고 계산값을 서버에 반영하지 않는다 (대조 결과·차이 항목만 저장)
- **예외 (본 §12)**: 사용자가 **명시적으로 트리거한 임포트**에 한해 위하고 원본 데이터(마스터·신고이력·지급명세서)를 서버에 저장한다
- **예외 성립 근거**
  1. 도구 사용 논리 유지 — 세무사가 **자기 데이터를 자기 도구로 이관**하는 행위
  2. 저장 데이터는 사용자 자신의 수임처 자료 — 재위탁 사슬이 확장되지 않음 (수임처→세무사→이지원천은 이미 §1-2 ④에 정리됨)
  3. 목적이 명확 — 매칭 엔진 시드(`05-master-import.md`)와 사장님 포털 과거 이력 조회
  4. 임포트 후 사장님 포털에 공개하는 원본 PDF는 발송 확정 게이트(§4-6)와 동일 로직으로 별도 검토 게이트를 두어 무단 공개 방지
- **범위 밖**: RPA 운영 중의 원본 저장은 예외에 포함하지 않음. 임포트 작업 완료 후에는 §1-2 원칙으로 복귀

### 12-5. 안전장치

| 위험 | 장치 |
|------|------|
| 같은 수임업체 중복 임포트 | 대기·진행 중 임포트 작업 중복 등록 차단, 마지막 임포트 시각(`Client.wehago_synced_at`)으로 재실행 여부 판단 |
| 이지원천에 이미 있는 수임처 덮어쓰기 | 사업자번호 unique 검사, 이미 있으면 등록 폼에서 "이미 등록됨 — 재임포트로 갱신하시겠습니까?" 확인 |
| 이지원천 사원 마스터 덮어쓰기 | 사원코드 기준 upsert. **이지원천이 더 최신인 필드는 위하고 값으로 덮지 않고 diff 리포트** (특히 급여 정보) |
| 대량 임포트 중단 | 수임처 단위 트랜잭션 — 부분 완료 상태를 `rpa_jobs`에 기록, 재실행 시 완료 수임처는 건너뛰기 |
| 위하고 세션 만료·계정 잠금 | 로그인 실패 1회 정지 (§8-1 규칙 재사용). 대량 작업 시 rate-limit 실측 필요 (§12-7) |
| 잘못된 수임처 임포트 (개별) | 사업자번호 검색 결과 정확히 1건 + 화면 상호 대조 (§4-2와 동일) |
| 임포트된 PDF 무단 공개 | 초기 `published_at=NULL`, 사장님 포털 공개는 관리자·사용자의 별도 확정 클릭 (§4-6 로직 재사용) |
| PDF 다운로드 파일 잔존 | 서버 등록 후 노트북에서 즉시 삭제 (§4-2 규칙과 동일) |
| 성능 (수임처 100+ 사무소) | 초기 세팅은 **야간·주말 실행** 권장, 관리자 알림창에 진행률·예상 종료 시각 표시 |

### 12-6. 데이터 모델·API 추가

**`rpa_jobs.kind`** 확장
- `WEHAGO_MASTER_IMPORT_ALL` (초기 세팅, 대상 수임처 리스트·옵션이 JSON 페이로드)
- `WEHAGO_CLIENT_IMPORT` (개별, 상호·사업자번호·옵션)

**`Client`** 추가 필드
- `wehago_synced_at` (마지막 임포트 시각)
- `wehago_import_status` (NONE / IN_PROGRESS / DONE / FAILED)

**`ClientFilingResult`** 확장
- `source`에 `WEHAGO_IMPORT` 값 추가 (기존 `RPA`, 신설과 병존)
- 임포트 레코드는 `published_at=NULL`로 시작, 별도 확정 게이트로만 공개

**API 신설** (`/api/v1/rpa`)
| 메서드·경로 | 인증 | 용도 |
|------------|------|------|
| `POST /imports/master-all` | 관리자 | 초기 임포트 작업 등록 (대상 수임처 리스트·옵션) |
| `POST /imports/clients` | 사용자 | 개별 수임업체 임포트 (수임업체 등록과 원자적) |
| `GET /imports/{job_id}/progress` | 사용자 | 진행률·수임처별 상태 조회 |
| `POST /agent/imports/{job_id}/client-result` | 에이전트 | 수임처 단위 결과 회신 (마스터·사원·신고이력·PDF 함께) |

### 12-7. 실측 필요 (PoC 6 · §9와 연동)

- 위하고 T 세무대리인 화면의 **수임처 목록 조회** — 페이지네이션·검색·필터, 대량 조회 시 rate-limit
- 각 수임처의 **사원 목록 조회** 화면 — 컬럼(주민번호 표시 여부·복사 가능 여부·마스킹 여부), 엑셀 다운로드 가능 여부
- **원천세 신고이력 조회** 화면 — 귀속월 리스트, 접수번호·납부기한 표시, PDF 다운로드 경로 (홈택스 접수증과의 관계)
- **지급명세서 발행 이력** 화면 — 근로/사업/일용/기타 각 종류의 발행 이력, PDF 다운로드
- 같은 아이디로 임포트 중 다른 창에서 로그인 시 세션 끊김 여부 (§9-1과 동일 확인, 임포트 중단 리스크)

### 13-1. 사원등록(인사) — §9-4(c)·§10-0·§12 관련 핵심 발견

[사원등록(인사)](https://wehagohelp.zendesk.com/hc/ko/articles/7538024920601) 화면이 §4-2 "사원 존재 확인"과 §12 사원 마스터 임포트의 실제 대상이다.

- **사원 Code는 등록 후 변경 불가.** 코드 체계(숫자/문자)는 `[인사환경설정] > 인사 > 근로소득설정 > 사원/종교인사원 코드 체계`에서 사무소가 정한다. 퇴사자가 재입사하면 기존 코드를 보존하고 **새 코드**를 부여해야 한다 — §10-0의 "서도 사원코드 1~4 불일치" 같은 사고가 재입사자 처리에서 반복될 수 있으므로, §4-2 사원 대조 로직에 "재입사자는 새 코드"를 전제로 넣을 것.
- **§9-4(c) "80/120% 원천징수 비율 선택 없음" 문제 — 필드 위치 확정.** 사원등록 공제등록 탭의 `간이세액표조정 시작월/조정율`(1.120%, 2.80%, 공란·3이면 100%)이 그 값이다. 조정 신청 자체는 근로소득관리 > [소득세 원천징수조정신청서및현황] 메뉴에서 별도 서식으로 낸다. §12 임포트로 이 필드를 가져오면 이지원천 `Employee`에 조정율 컬럼을 추가해 §9-4(c) 방법①(입력값 맞추기)을 구현할 수 있다.
- **§9-4(c) "부양가족 1명·자녀 0명 고정" 문제 — 필드 구조 확정.** 부양가족 탭: `연말정산관계`(0.본인~8.위탁아동), `기본공제`(0.부/2.배우자/3.20세이하/4.60세이상/5.장애인/6.기초생활/7.자녀장려금), `세대`(0.세대원/1.세대주/2.세대주의 배우자), `부녀/한부모/장애인/경로우대`, `출산입양/자녀`(8~20세는 주민번호로 자동 체크). 이 구조 그대로 `Employee`에 반영하면 정확한 소득세 계산이 가능해진다.
- **외국인 근로자 관련 필드가 사원등록에 이미 있다** — `단일세율적용여부`(19%), `거주지국`/`거주구분`, `체류자격`(사업장가입자자격취득신고서에 반영), `국외근로적용여부`(비과세 100/500만원). E-9 등 외국인 근로자를 다루는 [`21-worker-contract.md`](21-worker-contract.md)와 교차 확인 필요.
- **§12 사원 마스터 수집의 대안 발견 — 파서 검증 완료 (2026-09-28)** — 사원등록 더보기(기능모음)의 **"사원자료 엑셀변환"**(선택 사원 정보를 엑셀로 다운로드 폴더에 자동 저장)을 쓰면, 그리드를 Playwright로 긁는 대신 위하고가 만든 엑셀을 그대로 파싱할 수 있다. 실제 다운로드 파일(`서도_사원등록_20260928.xlsx`, 49열)을 `rpa-agent/easyone_agent/wehago_employees.py`의 `parse_employee_export`로 직접 검증 — 4명 전원 사원코드·사원명·주민번호·입사일이 정확히 파싱됐고, 필요한 8개 필드(사원코드·사원명·주민번호·입사일·퇴사일·부서·직급·직종) 외 계좌번호·연락처·보험료·주소는 설계대로 가져오지 않는다. **파싱 로직은 실전 준비 완료 — 남은 건 `wehago.py::export_employees`의 Playwright 트리거·다운로드 감시 부분뿐** (§10-0 미완 목록과 동일, SmartA 진입 경로 실측 필요).
- 두루누리신청여부, 중소기업취업감면, 생산직등여부/연장근로비과세, 학자금상환공제 등도 모두 사원등록의 필드다 — §8-1 "위하고 계산이 이지원천과 다름" 대조 시 차이 원인으로 우선 확인할 목록.

### 13-2. 근로소득관리 — §9-2 소득 종류별 화면 확인

- **근로소득(급여자료입력)**: 구분 코드 전체 목록 확정 — `1.급여/2.급여+상여/3.상여/4.요약/5.추급/6.추상` (`23-세무사세팅.md` §5-3의 "2.급여+상여" 고정값과 일치). 재계산·수당공제등록·연말정산(1·2월에만)·상여소득세 산출내역 등 부가 기능 다수. ([참고](https://wehagohelp.zendesk.com/hc/ko/articles/7426905746585))
- **일용근로소득(§9-2 실측 목록 1번 해결)**: `일용직사원등록`(마스터, 급여지급방법·요율 설정) → `일용직급여자료입력`(월별) 또는 `일용직급여일괄입력`(분기별, 이 탭의 지급명세서(제출집계표)에서 마감하면 전자신고 가능) 중 사무소가 `[인사환경설정] > 원천징수이행상황신고서 설정 > 일용직 급여 입력방법`(1.월별/2.일괄)으로 고른 쪽을 쓴다. 마감 후 `일용근로소득지급명세`로 이어지나 이 게시글은 공식 가이드 미제공.
- 은행별이체명세·월별급상여수당지급현황·회계전표처리는 조회·회계 연동용 리포트라 자동화 스코프 밖으로 제외.

**2026-09-28 실측 — 일용직 화면 구조·SmartA 코드 확정 (라이브 스크린샷)**

- SmartA 화면 코드: **일용직사원등록 = `SWSA0107`**. 같은 화면 안에 "일용직사원등록 | 일용직급여자료입력" 탭 2개가 공존한다(사업소득자등록/자료입력과 같은 구조).
- `일용직사원등록` 더보기(⋮) 메뉴: 설정(주민번호 별표 사용설정·일용직 사원코드 자동 채번 설정), 기타(사회보험요율갱신 F3·급여지급방법일괄변경 F7·데이터 정렬), 편집(계정과목 일괄등록 Shift+F6). **엑셀 업로드 메뉴 없음.**
- `일용직급여자료입력` 조회조건: 귀속년월·지급년월·현장·부서·프로젝트·구분(0.전체). 그리드: Code·사원명·주민번호·근무·지급액·마감. 우측에 "만근공수"(월 만근무 시 정상지급액에 금액 입력) 안내와 일자별 근무 그리드(근무시간 정상/연장 구분).
- `일용직급여자료입력` 더보기(⋮) 메뉴에 **사업소득자료입력과 동일하게 "엑셀서식내려받기/엑셀서식 불러오기"가 있다** (기능모음이 아니라 "엑셀" 섹션) — 일용소득 자동화도 §13-3과 같은 엑셀 업로드 패턴으로 갈 수 있다는 뜻. 그 밖에 계산(지급액/소득세재계산 F4·사회보험재계산 Ctrl+A), 연동(사원정보갱신 F3), 편집(소액부징수 Ctrl+M), 기타(월복사 F7·일/구간복사 Shift+N·다른사원복사 Shift+F7·비과세 수당등록)도 확인.
- **`일용직사원등록` 필수 입력 확인 (사용자 실측)**: **입사년월일을 입력해야 좌측 명단 그리드에 반영된다** — 근로소득 사원등록과 마찬가지로 필수값 하나만 빠져도 저장이 그리드에 안 뜨는 패턴(§4-2 "사원 존재 확인" 설계 시 참고). 자동화 코드가 일용직 사원을 등록·조회할 때 이 필드 누락을 실패 사유로 잡아야 한다.
- **§12 사원 마스터 임포트 스코프 확인 (사용자 확인, 정정 반영)**: `export_employees`(§12, SWPM0108 "사원자료 엑셀변환")는 **정규 근로소득 사원만** 대상. **사업소득자는 위하고 쪽에 대응하는 "가져오기"·"내려받기" 화면 자체가 없다** — §12 임포트 확장 시 사업소득자는 범위에서 제외하거나 다른 방법(그리드 직접 스크래핑 등)을 따로 찾아야 한다. **일용직은 별도의 다운로드 경로가 있다**(정정, 2026-09-28) — 정확한 화면·셀렉터는 추가 실측 필요, `일용직사원등록`(SWSA0107)의 더보기(⋮) 메뉴에는 "엑셀" 섹션이 없었으므로(§13-2 위 항목) 다른 경로일 가능성.

### 13-3. 사업소득관리 — §4-2·§9-2 "사업소득 화면" 확정

사업소득은 급여자료입력과 **완전히 다른 화면 계열**이다 — RPA가 근로소득과 별도 모듈로 다뤄야 한다.

- `사업소득자등록`(마스터, 거주자만·비거주자는 기타소득자등록) → `사업소득자료입력`(월별, 세율 기본 3%/지방소득세 0.3% 자동 계산, 마감 가능) → 마감 데이터가 **원천징수이행상황신고서의 "사업소득 매월징수"란에 자동 반영**된다(근로소득과 같은 신고서 한 장에 합산). `사업소득지급명세서(연간집계표)`가 별도 전자신고 대상. ([참고](https://wehagohelp.zendesk.com/hc/ko/articles/7440703802905))
- 연말정산 대상 사업소득은 소득구분 3종(940906.보험설계/940907.음료배달/940908.방판·외판)만 해당 — 나머지는 자동으로 연말정산 제외.

**2026-09-28 실측 (서도 더미 수임처, 라이브 스크린샷) — 화면 구조 확정**

- 진입: 전체메뉴 → "사업소득관리 / 기타(이자/배당)소득관리" 카테고리. 하위 12개 메뉴 중 자동화 대상은 `사업소득자등록`·`사업소득자료입력` (나머지는 조회·신고서·집계표류 — §12 임포트나 신고 단계에서 참고할 수 있으나 §4-2 자동입력 범위 밖).
- `사업소득자료입력` 화면: 근로소득 급여자료입력(SmartA SWSA0101)과 레이아웃이 다르다.
  - 상단 조회조건: **지급년월**(년.월 — 급여자료입력처럼 귀속연월 하나만) + **구분**(드롭다운, 기본값 "0. 전체" — 옵션 전체 목록 미확인) + [조회]
  - 좌측 그리드: `Code`·`소득자명`·`주민(외국인)번호`·`소득구분` — 급여자료입력의 사원 그리드와 같은 자리, 즉 **여기 표시되려면 먼저 `사업소득자등록`에 등록돼 있어야 한다** (급여자료입력이 사원등록을 전제하는 것과 동일 구조)
  - 우측 "기타 관리 항목": 소득구분·상호·사업장등록번호·전화번호·계정과목·영수일자·연말적용 — 사업소득자 1명 선택 시 채워지는 상세 정보로 추정
  - 우측 하단 "소득 지급 내역" 그리드: 귀속년월·지급년월일·지급총액·**세율(%)**·학자금상환액·소득세·지방소득세·(잘림, 차인지급액 추정) — **지급 건을 이 그리드에 행 단위로 추가하는 방식으로 보인다** (급여자료입력의 "엑셀 불러오기(Ctrl+U)" 같은 일괄 업로드 버튼이 툴바에 안 보임 — `[입력순 ▾]`·`[완료]`·`[경비/보험료 재계산]`·`[TIP]` 뿐)
  - 좌측 하단 총계: 인원[건수]·지급액·학자금상환액·소득세·지방소득세·고용보험료·차인지급액
  - 확인한 화면은 등록된 사업소득자가 0명이라 "데이터가 없습니다" 상태만 봤다 — **실제 입력 동작(그리드 직접 입력인지, 엑셀 업로드가 다른 곳에 있는지, 사업소득자등록부터 먼저 해야 하는지)은 아직 실측 전**

**2026-09-28 실측 2 — 우측 상단 더보기(⋮) 메뉴 확인**

급여자료입력의 `추가기능(⋮)`(`button#collect`)에 해당하는 메뉴가 사업소득자료입력에도 있다. 구성:

- **기능모음**: **엑셀서식 내려받기 / 엑셀서식 불러오기** — 급여자료입력처럼 사무소 파일을 헤더 이름 매칭으로 올리는 게 아니라, **위하고 양식을 먼저 내려받아 채운 뒤 다시 올리는 구조**로 보인다 (실제 템플릿 컬럼 구성은 미확인)

**2026-09-30 — 거주자사업소득간이지급명세서(SWHM0103) 마감도 실기 검증 완료.** 같은 날 사용자가 이 화면도 Chrome Recorder로 녹화해 공유 → `close_business_income_report` 수정 → 전 구간(새로불러오기 확인 → 마감 확인(enter) 모달 → "마감이 완료되었습니다.") 자동 실행 성공까지 확인했다. 새로 밝혀진 사실 2가지:

1. **화면 진입에 같은 id 버그가 있었다.** SWHM0103도 SWBU0102와 같은 "사업소득관리..." 카테고리라 `_open_closing_menu`의 `a#SWHM0103.text_link` 검색이 안 맞는다 — `_open_business_category_menu`(텍스트 기반, SWBU0102와 공용) 신규 추출해 재사용.
2. **[새로불러오기]가 조회 다음·마감 전에 반드시 필요했다.** 기존 코드엔 이 단계가 아예 없어 조회 직후 바로 [마감]을 눌렀는데, 실제로는 [새로불러오기] → "OO월 사원 및 사업소득자료입력에 입력된 소득을 모두 불러 오시겠습니까?" 확인 → [확인]을 먼저 해야 사업소득자료입력(SWBU0102)에 이미 입력된 소득이 이 화면 그리드로 들어온다. **지금까지 "마감할 데이터가 존재하지 않습니다"가 계속 떴던 진짜 원인으로 보인다.** 단, 이미 최신 상태(직전에 불러왔거나 재실행)면 확인창 없이 그냥 넘어가는 것도 확인 — 방어적으로 짧은 타임아웃 뒤 스킵 처리.

부가로 이미 마감된 달을 다시 실행하면(버튼이 [마감해제]로 바뀐 상태) 새로 마감하지 않고 "이미 마감되어 있습니다 (건너뜀)"을 돌려주도록 방어 코드 추가 (close_wht_return과 동일 원칙).

**남은 것**: `backend/app/api/rpa.py`의 `AUTOMATED_INCOME_TYPES`에 `IncomeType.BUSINESS`를 추가하고 job kind·다운로드 엔드포인트·게이트 배관(§4-1 일반화 설계, 이전에 한 번 구현했었으나 동시 세션 작업 중 유실됨 — 재작업 필요)을 다시 연결하면 실제 전송 흐름에서 켜진다. "구분" 드롭다운의 전체 옵션 목록은 여전히 급하지 않음(대조 로직엔 영향 없음).

**정정 (2026-09-28) — 엑셀 생성기는 이미 구현·완료돼 있었다.** `backend/app/services/smarta_business_xls.py`의 `generate_smarta_business_xls`가 위 14컬럼 헤더·안내문·소득구분 40종 목록·`CODE_TO_INCOME_TYPE` 매핑(위 분석과 완전히 동일)까지 이미 만들어져 있고, `decrypt_rrn`으로 RRN도 이미 채운다. **RRN 정책 예외는 사용자 승인 완료** ("예외 인정함", 2026-09-28) — §1-4에 반영.

다만 이 함수는 RPA(노트북 Playwright 업로드)가 아니라 **"통합 다운로드"**(`filings.py`의 zip 다운로드 엔드포인트, 급여대장·4대보험·사업소득 파일을 한 번에 묶어 세무사 사무소가 내려받는 기능)에 연결되어 있고, 지금은 **의도적으로 주석 처리**되어 급여대장만 나간다 (`filings.py:1284` "당분간 급여대장만 내려준다 — 4대보험·사업소득은 복구 시 아래 주석 해제"). 헬퍼(`_business_entries_for_filing`)도 이미 있어 주석만 풀면 동작한다.

**이 발견으로 자동화 경로가 두 갈래로 갈린다 — 결정 필요**

| 경로 | 방식 | RRN 노출 지점 | 남은 작업 |
|------|------|--------------|----------|
| **A. 통합 다운로드 복구 (가벼움)** | 이지원천이 파일을 만들면 **세무사 사무소가 직접 위하고에 업로드** — RPA 아님 | 서버가 인증된 세무사 세션으로 다운로드 응답에 실어 보냄 (§4-2 급여대장 자체가 아니라, 4대보험 리포트 등 기존 다운로드들과 같은 성격) | `filings.py:1284~1296` 주석 해제 + 실제 위하고에 업로드해보고 검증 |
| **B. 완전 RPA (무거움)** | 노트북이 SWBU0102 화면에서 더보기→엑셀서식 불러오기까지 Playwright로 자동 클릭 | 노트북이 잠깐 로컬 임시파일로 들고 있다가 업로드 직후 삭제 (§4-2 급여대장과 동일 패턴) | `wehago.py`에 신규 메서드, 실제 DOM 셀렉터 캡처 필요 (더보기 팝오버·업로드 다이얼로그) |

경로 A는 사실상 이미 다 만들어져 있어 **바로 검증 가능**하고, 경로 B는 §4의 "위하고 전송" 자동화 흐름에 완전히 통합되지만 셀렉터 실측이 더 필요하다. 둘 다 하되 A를 먼저 살리고, B는 §9 PoC 계열로 나중에 진행하는 것이 합리적으로 보인다 — 사용자 확인 필요.

**2026-09-30 — 사용자 공유 공식 FAQ 대조 확인.** 사용자가 위하고 공식 "사업소득자료입력 및 사업소득지급명세서" FAQ(귀속월≠지급월인 연말 케이스, 연말정산여부, 영수일자 처리)를 공유 → 기존 `upload_business_income`/`smarta_business_xls.py` 구현과 대조한 결과 **3가지 모두 이미 기존 구현과 정확히 일치** — 코드 변경 불필요, 문서 확인만 완료.

### 13-3-1. 일용소득관리(SWSA0107) — 실기 검증 (2026-09-30, 서도 김태호 실기)

화면 진입·기간 조회·[완료] 토글까지는 실기로 끝까지 검증됐지만, **엑셀서식 불러오기로 실제 급여 데이터를 반영하는 것은 원인 불명으로 실패** — 자동화를 계속 진행하기 전에 위하고 쪽 확인이 필요한 상태로 남겨둔다.

**확인된 것(정상 동작)**

1. **메뉴 진입에 카테고리 클릭이 필요 없다** — 사업소득(§13-3)과 달리 `일용직 급여자료입력`은 기본 카테고리에 있어 `_open_smarta` 직후 바로 `get_by_text(..., exact=True)`로 클릭 가능.
2. **귀속년월·지급년월이 별도 칸 둘 다 필수다.** 처음엔 지급년월 하나만 있는 줄 알고 귀속년월만 채웠다가 "입력하신 조회조건 중에 누락된 부분이 있습니다" 에러가 났다. 두 칸 다 `#SearchMain div.item`의 0/1번째, 매번 달력을 다시 클릭해 채워야 한다(한쪽만 조건부로 스킵하면 다른 쪽 값이 깨지는 현상 실기 확인 — 원인 미상, 그래서 항상 무조건 재입력).
3. **[완료] 흐름이 사업소득과 다르다.** [완료] → "해당 월의 데이터를 완료하시겠습니까?" → [확인]까지는 같지만, **이 화면은 그 뒤에 별도의 "완료되었습니다." 성공 팝업이 없다** — [확인]을 누르면 버튼이 그 자리에서 바로 [완료해제]로 바뀐다. 사업소득과 똑같이 성공 팝업을 기다리게 짜 놨다가 30초 타임아웃으로 실패했었다 — 버튼 토글 대기로 수정.
4. **DJ Bank 등 은행상품 광고 팝업이 로그인 splash 처리를 빠져나간다.** `_dismiss_splash`가 찾는 `div.LUX_basic_dialog`가 아니라 `div[id^=common_pop_dialog]` 구조라 안 닫히고, 메인화면 "전체" 탭 클릭 자체를 막아 수임처 검색이 통째로 실패했다 — `_SPLASH_DIALOG` 셀렉터에 이 패턴을 추가해 해결(전역 수정이라 다른 화면 진입에도 도움이 됨).
5. **일용직사원등록 FAQ 확인**: 공식 FAQ에 "입사일자가 없거나 조회월이 입사일자 이전/퇴사일 이후면 그 사원이 검색되지 않는다"는 항목이 있다 — 새 일용직 사원을 등록할 때 입사년월일을 반드시 채워야 한다(이번 테스트 계정은 이미 채워져 있어 이 문제는 아니었지만, 향후 신규 사원 자동등록 시나리오에서 반드시 지켜야 할 전제조건).

**미해결 — 엑셀서식 불러오기가 데이터를 반영하지 않는다**

- API(`POST /smarta/swsa0107/excel/`)는 매번 `{"resultMsg":"SUCCESS","status":"COMPLETE","resultCode":"S001"}`을 반환하고 UI 팝업도 "엑셀 불러오기가 완료되었습니다."를 보여주지만, 이후 `GET /smarta/swsa0107/salary/page/`로 재조회하면 해당 사원의 `cnt_workday`·`sum_dutyall`·`am_dapay`·`yn_gongsu` 등이 전부 0/"0"으로 남아 있다 — **그리드도, 서버가 실제로 응답하는 값도 데이터가 없다.**
- 다음을 전부 확인·교정했지만 재현됐다: (a) 원본 다운로드 서식(`ilyongjig_excel_2022.xls`)과 컬럼·헤더 문구·셀 서식 1:1 일치, (b) 원본의 18개 헤더 병합(세로 2~3행, "근무시간"/"지급액"만 가로 2칸)까지 `xlwt.write_merge`로 동일하게 재현, (c) "만근공수"(일자=99) 방식뿐 아니라 **평범한 일자(예: 2일) 방식도 똑같이 반영 안 됨** — 만근공수 특유의 문제가 아니라 이 계정/화면의 엑셀 업로드 경로 자체의 문제로 보인다, (d) 대상 사원의 입사년월일은 조회월과 같은 달로 유효, (e) [완료]/[완료해제] 잠금 상태는 매 테스트 전 해제 확인, (f) "기존 데이터 삭제하고 불러오기"/"추가불러오기" 두 옵션 다 시도, (g) RRN 하이픈 제거·13자리 숫자 형식 확인.
- 반면 **수동 그리드 입력은 이전 세션 데이터(02일 정상 8시간/200,000원 등)가 실제로 남아 있어 정상 동작함이 이미 확인된 상태** — 화면·계정 자체는 정상이고 엑셀 업로드 경로만 문제.
- **안전장치 추가**: `upload_daily_income`이 엑셀 업로드 팝업의 "완료" 문구만 믿지 않도록, 팝업 확인 직후 재조회 응답(`salary/page`)을 가로채 `cnt_workday`/`sum_dutyall`/`am_dapay`/`cnt_dapay`/`yn_gongsu` 중 하나라도 반영됐는지 직접 검증하고, 전부 0이면 `WehagoError`를 던지고 **[완료] 처리로 넘어가지 않는다** — "성공" 팝업만 믿고 빈 데이터를 완료 처리해버리는 조용한 실패를 막기 위함.
- **다음에 이어갈 때**: (1) 위하고 고객센터에 이 계정/화면으로 직접 문의하거나, (2) 사용자가 직접 브라우저에서 같은 파일을 수동으로 업로드해 재현되는지 확인하거나, (3) 엑셀 업로드를 포기하고 급여자료입력처럼 **그리드 직접 입력**(사용자가 실제로 쓰는 방식이기도 함) 방식으로 `upload_daily_income`을 다시 짜는 방향 중 사용자 판단이 필요하다.

### 13-5. 새로 발견된 항목 — 자동화 범위 확인 필요 (사용자 확인 대상)

아래는 §1~§12 어디에도 없던 항목이라 **자동화 포함 여부를 먼저 확인**해야 한다. plan에는 사실만 기록하고 스코프 결정은 보류한다.

- **주민세(종업원분)** — 지방소득세와는 **별개로**, 급여총액의 0.5%를 원천징수의무자가 매월 별도 신고·납부해야 하는 지방세다(단, 최근 1년 월평균 급여총액이 1억 3,500만원 이하면 면제). 현재 §4-4 "제작" 흐름은 원천세·지방소득세만 처리하고 이 항목은 다루지 않는다. **거래처 규모에 따라 실제로 누락되고 있을 수 있어 세무사 확인이 필요하다.** ([참고](https://wehagohelp.zendesk.com/hc/ko/articles/7507139128089))
- **퇴직소득이 있는 달의 원천징수이행상황신고서** — `퇴직소득자료입력`에 입력된 값이 근로소득과 **같은** 원천징수이행상황신고서에 합산 반영된다. 현재 RPA는 근로소득(급여자료입력)만 자동입력하므로, 퇴사자가 있는 달에는 사무소가 `퇴직소득자료입력`을 별도로(수동) 채워야 §4-4의 신고서 합계가 맞는다 — §4-8 예외 표에 추가할지 확인 필요.

### 13-6. 4대보험·기초정보 — 다른 문서로 라우팅

- 4대보험 관련 공식 가이드(사업장가입자격취득/상실신고서, 사업장가입신고서, 근로내용확인신고서, 두루누리신청서, 보수총액신고서 등 4개 서브섹션)는 [`06-insurance.md`](06-insurance.md) §4에 반영했다.
- 사무소 초기 세팅 관련 공식 가이드(회사등록, 인사환경설정, 사회보험/기초코드등록, 부서·현장·프로젝트등록)는 [`23-세무사세팅.md`](23-세무사세팅.md) §5-0에 반영했다.

## §14. 완전 자동화 로드맵 — 남은 소득유형 (Phase 4+, 제품 론칭 후 확장)

> 2026-09-28 결정. 이지원천의 최종 강점은 **원천징수이행상황신고서 완결 자동화**다. 원천징수이행상황신고서(별지21호, §13-4/`wht-form-21-code-system` 메모리)는 근로·사업·기타소득뿐 아니라 퇴직·연금·이자·배당·법인원천까지 A01~A99 전 코드를 다룬다. 지금은 근로소득(일용 포함 예정)·사업소득만 자동화 범위이고, 나머지는 **제품 론칭 후 가장 나중에** 부가 확장 기능으로 넣는다 — 초기 고객(10인 미만 영세사업장, [[feedback-default-heavy-small-biz]])은 이 항목들이 아예 없는 경우가 대부분이라 우선순위가 낮다.

### 14-2. 카테고리별 확장 개요 (우선순위 순 — 낮은 공수부터)

> **일용근로소득(A03)은 이 로드맵 대상이 아니다 (2026-09-28 정정)** — 영세사업장 고객에게 흔한 현재 진행 업무라 Phase 4+로 미루지 않는다. §13-2에서 화면(SWSA0107)·엑셀 업로드 패턴(사업소득과 동일 구조)까지 이미 확인됐고, `upload_business_income`과 거의 같은 방식으로 재사용 가능해 보이므로 **지금 진행 중인 작업 트랙**(§13-3 경로 B 다음 순서)에서 바로 이어간다. 아래 §14 목록은 그 외 "론칭 후 가장 나중에" 넣을 항목만 다룬다.

1. **퇴직소득 (A20/A21/A22)** — 가장 낮은 추가 공수로 보인다. `IncomeType.RETIREMENT`·A20/A22 코드 매핑이 이미 있고, 위하고 쪽도 `퇴직소득자료입력`이 근로소득과 **같은 신고서**에 합산되는 구조라 §4-4 "제작" 흐름에 자연스럽게 끼워 넣을 수 있다(§13-5에서 이미 "퇴직소득 있는 달은 사무소가 수동 입력" 예외로 다뤄짐). 필요한 일: (a) 퇴직소득세 계산 로직(근속연수공제·환산급여·특별공제, `tax_calc.py`가 현재 0 반환) 실제 구현, (b) 위하고 `퇴직소득자료입력` 화면 실측·업로드 자동화, (c) 연금계좌(A21)/그 외(A22) 구분 — 위하고 사원등록에 퇴직금 관련 필드가 있는지 확인 필요.
2. **중도퇴사자 정산 (A02 세분류)** — 근로소득의 기존 A01 흐름에서 파생되므로 새 소득유형이 아니라 "이번 달 퇴사자가 있으면 A02로 표시 + 연말정산식 정산 계산"만 추가하면 된다. 다만 §4-8이 이미 "연말정산 반영 월·중도퇴사자 정산은 자동화 제외"로 정책 결정을 해둔 영역이라, 이 결정을 바꿀지부터 확인 필요.
3. **기타소득 세분류 — 종교인소득 (A43/A44)** — `plan/24-wehago-official-guide-catalog.md`에 이미 위하고 공식 가이드 7건이 저장돼 있다(Phase 4+ 후보로 미리 분류해 둠). 종교인 대상 고객이 실제로 있을 때 우선순위를 올릴 항목.
4. **연금소득 (A45~A48)** — `IncomeType`에 카테고리 자체를 새로 만들어야 하는 첫 항목. 공적연금(매월/연말정산) vs 연금계좌 구분, 별도 세율 체계 조사부터 시작.
5. **이자/배당소득 (A50/A60) + 부표 C01~C40** — 완전히 새로운 영역. 대부분 금융기관이 원천징수의무자라 세무사 사무소 고객(중소 개인/법인사업자)에게 발생 빈도가 낮을 것으로 추정 — 우선순위 최하위 후보.
6. **법인원천 (A80) + 부표 C71~C90** — 외국법인 국내원천소득 등 특수 케이스. 영세사업장 고객군에서 발생 빈도가 극히 낮아 후순위.
7. **기타(이자/배당)소득관리·종교인소득관리** 관련 이미 스크래핑해 둔 위하고 공식 가이드는 `plan/24-wehago-official-guide-catalog.md`에 저장돼 있다 — 착수 시 재활용.

### 14-3. 공통 선행 작업

- **세법 준수 체크리스트** (2026-09-28 사용자 제안) — 소득유형별로 (세부항목 → 현재 코드 위치 → 법령/공식서식 근거 → 마지막 확인일 → 상태)를 표로 관리. 이번 세션에서 발견한 A01/A02 버그·국민연금 상하한 불일치 사례가 첫 항목이 될 수 있다. 세법이 매년 바뀌므로(예: 국민연금 상하한 2026.7.1 개정) "마지막 확인일" 없이는 체크리스트 자체가 거짓 안심을 줄 위험 — 만들 때 이 점을 반영. 별도 문서로 만들지, plan/16에 통합할지는 사용자 결정 필요.
- 각 신규 소득유형 착수 전 **§9(PoC) 방식대로 실측 우선** — 이번 세션에서 배운 교훈(스크린샷만으로는 부족, 실제 HTML·성공/실패 메시지·값 형식까지 확인해야 안전하게 자동화 가능)을 그대로 적용.
