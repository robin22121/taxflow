## §1. A/B 프레임과 B안 4벽

결정 축은 **데이터 위치**:
- **A안 (설치형·로컬 완결)**: 위하고 raw 데이터가 세무사 PC 를 벗어나지 않음. 이지원천은 세무사의 도구.
- **B안 (클라우드형·서버 경유)**: 위하고 raw 데이터가 이지원천 서버에 저장·처리됨.

### 1-1. B안이 T 약관·일반약관에서 동시에 막히는 4가지 벽

| 벽 | 조항 | B안이 위반하는 이유 |
|----|------|-------------------|
| ① 회원 자격 | T 개별약관 제2조 3호 | 이지원천(주식회사 호미)은 세무사·회계사 아니라 T 회원 자격 없음. B안은 필연적으로 세무사 계정 대여 |
| ② 계정 대여 금지 | 일반약관 제5조 ①, 제28조 | 서버가 세무사 계정으로 위하고에 접근 = 실질적 계정 대여 |
| ③ 인증수단 관리 의무 | T 개별약관 제10조 ② 2호 (전자금융거래법 용어) | 크레덴셜을 서버에 두면 안전 관리 의무 위반. 홈택스 공동인증서까지 확장하면 정면 충돌 |
| ④ 재위탁 동의 | T 개별약관 제3조·제4조 | 수임처→세무사→더존→이지원천 4단계 재위탁 발생. 수임처마다 개별 동의 필요 → 영업 불가 |

### 1-2. A안 (i) 가 4벽을 통과하는 이유

- **① 계정 대여 없음** — 세무사 본인이 이미 로그인한 세션 재활용. 이지원천은 세무사 계정으로 새로 로그인하지 않음
- **② 서버가 위하고에 접근하지 않음** — 익스텐션이 세무사 브라우저 안에서 조작. 서버는 감사 로그만
- **③ 크레덴셜 저장 X** — 세션 재활용이라 위하고·홈택스 크레덴셜 어디에도 저장 안 함
- **④ 위하고 raw 데이터가 이지원천 서버에 저장 안 됨** — 재위탁 4단계 원천 회피. 기존의 **수임처→세무사→이지원천 재위탁 관계**는 이지원천 프로젝트 자체 이용약관·개인정보 처리 방침으로 이미 다뤄지고 있는 것 (이번 위하고 접점이 새로 만드는 문제가 아님)

### 1-3. A안에서 유리하게 작용하는 조항

- **T 개별약관 제11조** — 회원이 입력한 데이터의 지식재산권은 회원. 세무사가 자기 데이터를 자기 도구로 처리 → 정당
- **T 개별약관 제12조 ④** — 회원 업로드 방식에 대한 위하고 책임 없음. 자동화 업로드는 회원 자유
- **T 개별약관 제10조 ①·제12조 ①** — 위하고 T 자체가 스크래핑 사용을 약관에 명시·면책. 협상 카드 ("귀사도 스크래핑 사용")

### 1-4. 남은 쟁점 (변호사 검토 시 명시)

- **실행 주체 해석** — 자동화 스크립트가 세무사 본인의 도구인가, 이지원천의 대리 행위인가. A안에서는 도구 논리가 유리하지만 다툼 여지 남음
- **일반약관 제8조 ② "대리인" vs T 개별약관 제10조 ② 1호 "임·직원"** — 상충 시 개별약관 우선, 병존 해석 시 일반약관의 대리인 조항 살아있음. 후자가 유리

### 1-5. 두더지잡기 경고

T 개별약관 제10조 ① 은 "개별 기관의 스크래핑 관련 정책 변경" 을 명시. 더존조차 UI 업데이트로 대응 중. 이지원천도 같은 부담 — **익스텐션 방식이 JS 셀렉터 수정 사이클 짧은 게 상대적으로 우세**.

## §2. 이지원천 서버 역할 재정의

**서버가 계속 하는 것**:
- 세무사 사무실 자체 자료 저장 (기존 SaaS, 재위탁 관계는 이지원천 자체 약관으로 이미 처리)
- 감사 로그 (누가·언제·어느 거래처 대상 자동화 실행, 결과 상태)
- rpa_agents·rpa_jobs 관리 (상태·시각·요약만, **파일 원본 없음**)
- 익스텐션·에이전트 배포·업데이트

**서버가 하지 않는 것**:
- 위하고 raw 파일 저장 (급여 엑셀·신고서 XML 등)
- 위하고·홈택스 크레덴셜 저장
- 세무사 PC ↔ 노트북 사이 파일 매개

## §3. 아키텍처

### 3-1. 자동화 방식 후보

**후보 A. Chrome 익스텐션 (Manifest V3)** — 권장 시작점

```
[세무사 크롬]
├─ tab: 이지원천 웹앱
│    ↕ window.postMessage / externally_connectable
├─ 이지원천 익스텐션 (service worker + content scripts)
│    ├─ 이지원천 웹앱 ↔ 위하고 탭 브릿지
│    ├─ 로컬 브리지 (노트북 향 파일 전송)
│    └─ chrome.tabs.sendMessage → 위하고 탭
└─ tab: 위하고 T (세무사 이미 로그인)
     └─ content script (host_permissions: wehago.com)
```

- 세션 재활용 (세무사 로그인 그대로)
- 크레덴셜 저장 X
- UI 변경 대응: JS 셀렉터 수정만
- 배포: Chrome Web Store 또는 사내 CRX
- 리스크: 위하고의 익스텐션 조작 봇 탐지 → PoC 로 검증

**후보 B. CDP attach**

```
[세무사 PC]
├─ Chrome (--remote-debugging-port=9222)
│   └─ 위하고 탭 (세무사 로그인)
├─ 로컬 에이전트 (Python + pychrome, PyInstaller EXE)
│   ├─ CDP 로 크롬 attach → 위하고 탭 조작
│   ├─ 이지원천 웹앱과 로컬 IPC (localhost WebSocket)
│   └─ 로컬 브리지 (노트북 향)
```

- 세션 재활용 유지
- 크레덴셜 저장 X
- 리스크: 크롬을 특정 옵션으로 실행 필요 (UX 마찰), CDP 감지

**선택은 §8 PoC 결과에 따름.** 배포·UI 변경 대응 편의성에서 A 우세이므로 A 먼저.

### 3-2. 로컬 브리지 (세무사 PC ↔ 별도 노트북)

원천세 신고서 파일을 세무사 PC 에서 노트북 (홈택스 트랙) 으로 전달. 이지원천 서버 우회.

| 방식 | 흐름 | 위치 |
|------|------|------|
| **A. LAN HTTP** | 노트북 로컬 HTTP 서버, 익스텐션/에이전트가 POST | 주력 |
| B. Windows 공유폴더 (SMB) | 세무사 PC 폴더 공유, 노트북이 폴링 | 보조 |
| C. WebRTC P2P | 익스텐션 ↔ 노트북 앱 P2P (시그널링만 서버) | 후속 검토 |
| D. USB 수동 | 세무사가 USB 로 옮김 | 폴백 |

**주력 A + 폴백 D.** 초기 온보딩 시 사무소 LAN 세팅 확인 필요 (노트북 IP 고정, 방화벽 예외).

### 3-3. 이지원천 웹앱 ↔ 익스텐션 데이터 전달

세무사가 이지원천 웹앱에서 이미 보고 있는 데이터를 익스텐션이 위하고에 붓는 구조. **서버가 새로 파일 만들어 익스텐션에 넘기지 않음** — 이게 A안 (i) 의 핵심.

세 옵션:
1. `window.postMessage` — 이지원천 웹앱과 익스텐션 content script 가 같은 페이지에서 메시지 교환
2. `chrome.runtime.sendMessage` + `externally_connectable` — 웹앱이 직접 익스텐션 service worker 에 명령
3. 이지원천 웹앱에 익스텐션 SDK 로드 → 함수 호출 인터페이스

PoC 단계에서 옵션 2 가 가장 깔끔할 것으로 예상. 확정은 익스텐션 구현 시.

## §4. 데이터 흐름

### 4-1. 급여 업로드 (이지원천 → 위하고)

```
[세무사 PC 크롬 안에서 완결]
1. 세무사가 이지원천 웹앱에서 3월 급여 확정 (기존 SaaS 흐름)
2. 세무사가 "위하고 T 전송" 클릭
3. 이지원천 웹앱 → 익스텐션 명령
   { action: "wehago_upload", client_id, period, data: {...} }
   (데이터는 웹앱이 이미 세무사 브라우저에 로드해둔 것)
4. 익스텐션이 위하고 탭 form 에 데이터 입력·업로드
5. 익스텐션이 위하고 응답 확인
6. 익스텐션 → 이지원천 서버: 상태 로그만 (데이터 없이)
   POST /rpa/jobs/{id}/status { status: "SUCCEEDED" }
7. 이지원천 웹앱 대시보드에 결과 표시
```

**핵심**: 4번의 데이터가 서버에서 새로 뽑혀서 익스텐션에 전달되는 게 아님. 세무사가 이미 이지원천 화면에서 보고 있는 자기 데이터를 익스텐션이 위하고로 옮기는 흐름. 서버는 이 과정에서 급여 엑셀 파일을 만들지 않음.

### 4-2. 원천세 신고 (위하고 → 노트북 → 홈택스)

```
[세무사 PC 크롬]
1. 세무사가 위하고에서 급여·원천세 신고서 확정 (위하고 안에서)
2. 세무사가 이지원천 웹앱에서 "원천세 신고" 클릭
3. 이지원천 서버가 노트북 에이전트에 작업 등록 (rpa_jobs, PENDING, 파일 없음)
4. 이지원천 웹앱 → 익스텐션 명령
5. 익스텐션이 위하고에서 신고서 파일 다운로드
   → 세무사 PC 로컬 폴더 저장 (%USERPROFILE%\.easyone\downloads\)
6. 익스텐션이 로컬 브리지로 노트북에 파일 POST
   POST http://<노트북IP>:port/receive-file (LAN 안)
[별도 노트북]
7. 노트북 에이전트가 파일 수신 → 홈택스 로그인 (공동인증서) → 자동 신고
8. 노트북 → 이지원천 서버: 상태 로그 (파일 원본 없이)
9. 이지원천 웹앱 대시보드에 결과·접수증 요약 표시
   (접수증 raw PDF 는 노트북 로컬 or 세무사 PC 로컬, 서버 X)
```

**세션 재활용 이중 로그인 회피**: 5번의 위하고 다운로드는 세무사가 이미 로그인한 세션 그대로 사용 → 이중 로그인 문제 원천 소거.

## §5. 데이터 모델

`backend/app/models/rpa.py`, 마이그레이션 `a1c3e5f7b9d2` 유지. **파일 저장 컬럼 신설 X.**

- `business_number`·`business_name` 스냅샷 (엉뚱한 회사에 업로드 방지 대조용)
- `requested_by_user_id`, `agent_id`, `claimed_at`, `finished_at`, `result_message`
- **파일 컬럼 없음**

| 자격증명 유출 | **저장 X** — 위하고·홈택스 크레덴셜 서버·로컬 어디에도 X |
| 위하고 raw 데이터 서버 저장 | **저장 X** — A안 (i) 원칙, 재위탁 4단계 원천 회피 |
| 자동화 중 세무사 조작 개입 | 익스텐션: 같은 세션이라 큰 영향 없음. CDP: 배너로 자제 요청 |
| 로컬 브리지 파일 유출 | LAN 안에서만 통신, 노트북 처리 완료 후 즉시 삭제 (`finally` 블록) |
| 감사·추적 | 자동화 액션 서버 로그 (사용자·시간·거래처·작업 종류·결과) — 개인정보 raw 는 없이 |
| 토큰 유출·PC 분실 | `DELETE /agents/{id}` 즉시 폐기 |
| 세무사 이지원천 로그아웃 | 익스텐션·에이전트 무력화 (JWT 만료로 서버 통신 실패) |
| 익스텐션 변조 | 로컬 저장소에 세션 토큰 저장 X. 요청마다 이지원천 JWT 재사용 |

## §8. PoC 계획

### 사전 준비
- 파트너 세무사의 위하고 T **테스트용 더미 수임처** (실제 거래처 데이터 없음)
- 파트너 노트북 1대 (홈택스용) — LAN 세팅 확인

### PoC A. Chrome 익스텐션 (~1일)

1. 최소 스캐폴딩: `manifest.json` (V3), content script, popup — 30분
2. 위하고 도메인에서 DOM 읽기 (`document.querySelector`) — 15분
3. 침습도 단계 테스트:
   - ① 값 읽기 (안전)
   - ② input 필드 프로그램 입력 (`nativeInputValueSetter` + input/change 이벤트 dispatch)
   - ③ 조회 버튼 자동 클릭 (저장·제출 절대 X)
   - ④ 급여자료 필드 자동 입력 시도
4. 봇 탐지 흔적 확인: 네트워크 (`bot`·`captcha`·`challenge` 요청), `navigator.webdriver`, mutation observer, 이벤트 리스너 dump
5. 이지원천 웹앱 ↔ 익스텐션 메시지 전달 검증 (`window.postMessage` or `externally_connectable`)

**판정**: 4단계 통과 + 5단계 데이터 전달 성공 → 후보 A 확정.

### PoC B. CDP attach (~반나절, A 실패 시)

1. 크롬을 `--remote-debugging-port=9222` 로 실행
2. Python `pychrome` 또는 `undetected-chromedriver` 로 attach
3. PoC A ①~④ 와 동일 시나리오
4. 봇 탐지 흔적 확인
5. 이지원천 웹앱과 로컬 에이전트 IPC (localhost WebSocket)

**판정**: A/B 비교 → 봇 탐지·UX·개발성 우세한 쪽 확정.

### PoC C. 로컬 브리지 LAN HTTP (~반나절, A/B 통과 후 병행)

1. 노트북에 최소 로컬 HTTP 서버
2. 세무사 PC 익스텐션/에이전트가 `fetch("http://<노트북IP>:port/receive", { method: "POST", body: file })`
3. 노트북 방화벽 예외·포트 개방 확인
4. 파일 수신 후 로컬 저장·검증

**판정**: 성공 시 LAN HTTP 확정. 실패 시 SMB → USB 순 폴백.

### 진행 순서
1. **PoC A 먼저** (봇 탐지 리스크 우선 소거)
2. A 통과 → PoC C 진행 (로컬 브리지 검증)
3. A 실패 → PoC B 진행 (CDP)
4. A·B 모두 실패 → 자동화 스코프 축소 (수동 업로드 + 결과 회신만 자동화) 검토

## §10. 미확정 — 실측 대상

### 10-1. 위하고 봇 탐지 강도 (PoC A/B)
- 익스텐션 이벤트가 자동화로 감지되는가
- CDP 세션이 감지되는가
- 감지 시 대응 (계정 잠금 / CAPTCHA / 조용한 데이터 차단)

### 10-2. 위하고 UI 실측
- 급여자료 업로드: 메뉴 경로, 귀속연월·지급일·급여구분 선택 위치
- 컬럼 매칭 저장 여부
- 22컬럼 병합 헤더·합계행 처리
- 재업로드·마감월 동작
- 원천징수이행상황신고서 화면: 파일 export 형식 (XML/엑셀), 다운로드 경로
- 성공·실패 메시지 판독

### 10-3. 위하고의 원천세 신고 [제작] vs [전송]
- T 개별약관 §6 데이터 목록 (110, 111, 112호) 만으로는 판별 불가
- 파트너 세무사에게 화면 확인 요청: **"원천징수 전자신고 메뉴에 신고서 파일을 저장하는 버튼(제작)만 있는지, 국세청에 바로 전송하는 버튼(전송)까지 있는지?"**
- 답에 따라 별도 노트북 홈택스 트랙의 필요성 재검토 (전송까지 되면 노트북 트랙 필요 없을 수도)

### 10-4. T edge 약관
- 수임처 접점 계획 있으면 추가 검토

### 10-5. T 개별약관 §6 데이터 항목과 위하고 실제 메뉴 매칭
스코프 핵심 항목:
- 81호 (급여대장/명세)
- 89호 (사업소득자료입력)
- 105호 (소득자별근로소득원천징수부)
- **110호 (원천징수이행상황신고서)** ← 홈택스 신고 대상
- 111호 (원천징수 전자신고), 112호 (원천징수 전자신고관리대장)
- 78호 (국세청 연말정산 간소화입력)
- 118호 (일용근로소득지급명세)

각 항목이 실제 위하고 메뉴 어디에 존재하는지 실측 매핑.
