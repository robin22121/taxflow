# 사업주 포털 (거래처 사장님용 무료 화면)

> 2026-09-08 설계. 세무사 대상 유료 모델은 유지하고, 거래처 대표자가 쓰는 무료 화면을
> 번들로 얹는 B2B2C 구조. 개인사업자 직접 과금(B2C 피벗)은 **검토 후 기각** — §1 참고.
>
> **2026-09-10 개정** — 접근 모델을 월간 티켓(30일 만료)에서 **거래처 단위 상설 링크 +
> PIN 게이트**로 전환. 데이터 모델에 §5.3(상설 토큰·PIN)·§5.4(`ClientFilingResult`) 추가.
> 개정 범위: §3.1, §3.2, §3.6, §4.1, §4.3, §4.4, §4.5, §5, §6.

---

## 1. 배경 — 왜 B2C 피벗이 아니라 무료 번들인가

개인사업자(미용실·음식점 등)를 직접 고객으로 삼는 방향을 검토했으나 다음 이유로 기각했다.

| 사유 | 내용 |
|------|------|
| **세무사법 리스크** | 원천징수이행상황신고서 제출 대행은 세무대리 행위. 사업주 대신 전자신고 시 무자격 세무대리 소지. 이를 피해 "작성만 하고 본인이 제출"로 가면 사업주가 느끼는 가치가 소멸 |
| **유닛 이코노믹스** | 세무사 1곳 = 거래처 30~100곳. 같은 영업 한 번에 30배 효율. B2C는 CAC 대비 ARPU가 10~20배 악화 |
| **수요 강도 부재** | 사장님은 이미 세무사에게 월 10만원을 내고 원천세를 포함해 위임 중. 대체재가 이미 싸고, 그 대체재가 곧 우리 고객 |
| **채널 자기잠식** | 사업주 직접 과금 시 세무사 눈에 "내 고객에게 돈 받는 업체"가 됨 |

**결론**: 과금은 세무사에게 유지, 사업주 화면은 **무료 번들**. 세무사의 신규 수임 영업 무기로
포지셔닝한다 — 급여명세서 자동 교부([`01-workflow-roadmap.md`](01-workflow-roadmap.md) §Phase 1)와
동일한 논리. *"저희 사무소에 맡기시면 사장님 전용 화면을 드립니다."*

## 2. 기존 결정과의 관계 — "거래처 직접 연결 폐기"와 양립

[`01-workflow-roadmap.md`](01-workflow-roadmap.md) §Phase 1에 다음 폐기 결정이 있다.

> **폐기**: 거래처 ↔ 이지원천 직접 연결 방식 (상담 대응 불가, 오류 수정 커뮤니케이션 어려움, 신뢰 관계 문제)

본 설계는 이 결정을 **유지**한다. 차이는 다음과 같다.

| | 폐기된 방식 | 사업주 포털 |
|---|---|---|
| 소통 주체 | 거래처 ↔ 이지원천 (세무사 우회) | 거래처 ↔ **세무사** (기존 카톡 유지) |
| 화면 역할 | 대화·문의·수정 요청 | **자료 제출 + 결과 확인**, 그 둘뿐 |
| 질문 발생 시 | 이지원천이 응대 → 불가능 | "담당 세무사에게 문의" → 기존 카톡으로 이동 |
| 세무사 위치 | 배제 | 유일한 접점이자 통제자 |

**원칙: 화면에 입(mouth)을 달지 않는다.** 넣는 창구와 받는 창구만 만들고 대화는 전부
세무사 카톡으로 보낸다. 폐기 사유 3가지가 발생하지 않는다.

기존 수집 채널 4순위("거래처 직접 입력 — 알림톡 토큰 URL → 웹폼")와
[`09-design.md`](09-design.md) B4(공개 입력 폼 채팅 스타일, 구현완료)가 이 포털의 씨앗이다.
**신규 개발이 아니라 1회용 폼의 수명을 늘리는 작업**이다.

## 3. 화면 구성 · 전달 · 상태 확인

### 3.1 홈 — "지금 내가 뭘 해야 하나"

```
하늘식품 · 담당 조명신 세무사

  ● 4월 급여자료를 알려주세요        [입력하기]
     마감 5월 3일
  ─────────────────────────────
  3월  신고완료 · 납부 1,240,300원   [접수증]
  2월  신고완료 · 납부 1,180,500원   [접수증]
  ─────────────────────────────
  🔒 급여 상세 · 급여명세서 보기
```

사장님이 원하는 정보는 두 가지뿐 — **내가 할 일이 남았나 / 얼마 내야 하나**.
이 둘은 게이트 없이 보인다. 직원별 급여액처럼 새어 나가면 곤란한 것만 자물쇠 뒤에 둔다(§4.3.1).

### 3.2 급여 입력 — 기존 B4 폼 재사용

전월 명단 + "전월과 동일" 원탭 CTA.

**단 금액은 게이트 뒤에 둔다**(§4.3.1). 게이트 앞 폼은 **명단만** 보여주고, "전월과 동일"
버튼은 금액을 화면에 드러내지 않고도 누를 수 있게 한다 — 사장님이 확인해야 할 것은
"이 사람들 그대로인가"이지 금액 숫자가 아니다. 금액을 바꾸거나 확인하려면 PIN을 넣는다.

### 3.3 직원 등록 — 본 포털의 핵심 가치

```
  + 새 직원이 들어왔어요
  − 그만둔 직원이 있어요
```

세무사무소의 실제 사고 1위는 급여 금액 오류가 아니라 **입·퇴사 통보 누락**이다.
통보가 늦어 4대보험 자격취득 신고(입사일로부터 14일 이내)를 놓치고, 과태료 항의를 세무사가 받는다.

[`01-workflow-roadmap.md`](01-workflow-roadmap.md) Phase 3의 입·퇴사 정보는 현재
"AI 후속 질문"으로 캐내는 **사후 추적** 구조인데, 본 화면이 이를 **사전 통보**로 바꾼다.
데이터 모델은 §5 참고.

> 주민번호는 이 화면에서 받지 않는다. 기존 **개별 보안 입력 URL**(Phase 1)로 분리.

### 3.4 보관함 — Phase 2 산출물의 소비처

접수증·납부서·급여명세서 PDF를 월별로 축적. Phase 2에서 에이전트가 추출해 알림톡으로
발송하는 자료들인데, 알림톡은 스크롤하면 사라진다. 보관함이 있으면 그 자료가 자산이 되고
거래처 락인이 된다.

### 3.5 절대 넣지 않을 것

| 금지 | 이유 |
|------|------|
| 세무사에게 묻는 채팅·문의 기능 | §2 폐기 결정의 핵심. 기존 카톡을 대체하면 신뢰 관계 훼손 |
| 세액 계산 내역 상세 | "왜 이번 달은 더 많죠?" 문의 폭증 → 세무사 업무가 **늘어남** |
| 원천징수이행상황신고서 원문 | 사장님은 못 읽고, 오해하고, 오해는 세무사가 수습 |
| 절세 팁·세무 조언 | 세무상담 주체가 되는 순간 세무사법 리스크 재발생 |
| 아이디·비밀번호 로그인 | 사장님은 로그인하지 않는다. 만드는 순간 이탈 (§4) |

### 3.6 사장님에게 어떻게 전달되는가

포털은 앱도 아니고 사장님이 주소를 외워 찾아오는 사이트도 아니다.
1차 진입점은 **알림톡으로 배달되는 링크**다. 다만 §4.3 개정으로 링크가 상설이 되었으므로,
사장님이 그 링크를 카톡 즐겨찾기에 두면 **알림톡 없이도 재방문할 수 있다.**
알림톡은 여전히 "이번 달 자료를 보낼 때가 됐다"는 신호로 매달 나간다.

| 순위 | 경로 | 비고 |
|------|------|------|
| 1 | **알림톡** — 세무사가 대시보드에서 "이번 달 자료 요청" 클릭 → 등록된 거래처 번호로 일괄 발송 | [`01-workflow-roadmap.md`](01-workflow-roadmap.md) §1.2 [1][2] 기존 흐름 재사용 |
| 2 | **SMS 폴백** — 카톡 미사용·채널 차단으로 알림톡 실패 시 자동 문자 전환 | Aligo 알림톡+SMS 폴백 |
| 3 | **세무사 수동 전달** — 대시보드에서 링크 복사 → 세무사가 직접 카톡 전송 | 번호 변경·발송 실패 시 최후 수단 |

**선행 조건 — 상세는 [`13-messaging-activation.md`](13-messaging-activation.md) 참고**

- [ ] **Aligo 발신 허용 IP 등록** — 현재 `-101 IP 인증오류`로 문자 발송 불가.
      콘솔에 vm-node IP 등록만 하면 해소(5분). **이것만 되면 포털 1단계는 문자로 검증 가능**
- [ ] **알림톡 채널·발신프로필·템플릿 등록** — 현재 `KAKAO_ALIMTALK_PROVIDER=stub`.
      드라이버 코드는 있으나 카카오 계정·템플릿 미등록. 리드타임 2~4주

> **포털이 알림톡 심사를 쉽게 만든다.** 알림톡은 심사된 템플릿 문구와 정확히 일치해야 하는데,
> 현재 확인요청·후속질문 메시지는 동적 목록이라 템플릿화가 불가능하다. 상세 내용을 포털로 옮기면
> 메시지가 "알림 + 링크"로 단순해져 정형 템플릿 3종으로 수렴한다
> ([`13-messaging-activation.md`](13-messaging-activation.md) §3.4).

### 3.7 세무사가 무엇을 확인할 수 있는가

사장님 화면의 상태는 **세무사 대시보드에서 4단계로 노출**한다.

| 상태 | 의미 | 근거 데이터 |
|------|------|------------|
| **발송됨** | 알림톡/SMS 전송 성공 | Aligo 결과 코드 |
| **열람함** | 링크 최초 진입 | §4.5 열람 로그 |
| **입력중** | 일부 입력 후 이탈 | 폼 부분 저장 |
| **제출완료** | 자료 제출 완료 | 기존 `CollectionSession` |

**이 구분이 세무사에게 주는 즉각적 가치가 크다.** "사장님 자료 아직 안 주셨어요"라고
연락할 때, *링크는 봤는데 입력을 안 한 것*과 *링크를 아예 못 받은 것*은 대응이 완전히 다르다.
현재 카톡 방식으로는 이 구분이 불가능하다.

[`09-design.md`](09-design.md) B2의 워크플로우 진행률 스트립(초대발송→수신→검증→승인→신고)에
**'열람' 상태를 끼워넣는 방식**으로 구현한다. 신규 화면이 아니라 기존 스트립의 세분화다.

> **미리보기 기능**: 세무사 계정에서 "사장님 화면 미리보기"를 제공한다. 실제 알림톡 발송 없이
> 해당 거래처 데이터로 렌더링해 세무사가 무엇이 보이는지 확인할 수 있게 한다.
> 수임 상담 시 *"이런 화면을 드립니다"* 시연용 영업 도구를 겸한다.

## 4. 인증·보안 모델

### 4.1 결정 사항 (2026-09-08 → **2026-09-10 개정**)

**개정 요지**: 월간 티켓(30일 만료)을 폐기하고 **거래처 단위 상설 링크 + PIN 게이트**로
전환한다. 사유는 §4.3.1.

- **OTP 없음** — 유지. 어떤 화면에도 SMS 본인인증을 두지 않는다
- **거래처 단위 상설 링크** — 만료 없음. 매월 재발급하지 않고 같은 URL을 계속 쓴다
  (구: "토큰 수명 30일 · 매월 신규 발급" — 폐기)
- **민감 구역은 PIN 게이트 뒤로** — 직원별 급여액·급여명세서·전월 프리필은
  세무사가 발급한 4~6자리 PIN 입력 후 열람
  (구: "프리필에 전월 금액 무조건 표시" — 폐기)
- **대표자 생년월일을 PIN으로 쓰지 않는다** — 사유는 §4.3.2
- **장기 세션 쿠키 없음** — 유지. PIN 통과 상태는 브라우저 세션 한정(탭 종료 시 소멸)

### 4.2 신원은 우리가 확인하지 않는다 — 세무사로부터 상속

```
거래처 사장님 ──(수임 계약 시 확인)──► 세무사 ──(거래처 등록)──► 이지원천
      신원 확인 주체 = 세무사                        신원 상속
```

세무사는 수임 시 이미 사업자등록증·대표자·휴대폰 번호를 확인했다. 우리는 사장님이 누구인지
**새로 확인하는 게 아니라 세무사가 확인해 둔 신원을 이어받는다.** 따라서 통신사 본인인증이나
공동인증서 같은 본인확인 절차가 필요 없다.

포털에는 전자서명이 필요한 행위(신고 제출)가 없으므로 공동인증서도 불필요하다.

이 구조는 [`10-privacy-security.md`](10-privacy-security.md) G2의 위탁사슬을 그대로 유지한다:
**거래처(처리자) → 세무사 → 이지원천(수탁자)**. 포털이 생겨도 사슬이 바뀌지 않으며,
사장님과 직접 계약 관계를 맺지 않는다.

### 4.3 접근 모델 — 거래처 상설 링크 + PIN 게이트

#### 4.3.1 2구역 구조

```
세무사가 거래처 등록 → 상설 링크 1개 발급 (만료 없음)
      ↓
사장님이 카톡에 저장해두고 매달 재방문
      ↓
┌─ 공개 구역 (링크만으로 진입, 마찰 0) ──────────┐
│  · 이번 달 제출 폼 — 직원 명단만, 금액 없음    │
│  · 월별 예상 납부세액                          │
│  · 접수증·납부서 PDF, 가상계좌                 │
└────────────────────────────────────────────┘
      ↓  [급여 상세 보기]
┌─ PIN 게이트 (4~6자리, 세무사 발급) ────────────┐
│  · 직원별 급여액                               │
│  · 지난달 급여명세서                           │
│  · 전월 금액 프리필                            │
└────────────────────────────────────────────┘
```

월간 티켓을 폐기한 이유는 셋이다.

1. **홈 화면·보관함과 양립하지 않는다.** §3.1의 홈은 지난 달 접수증까지 나열하는
   누적 화면이고 §3.4 보관함은 월별 축적이 전제다. 30일 만료 링크로는 둘 다 성립하지
   않는다. 이 문서가 그리는 포털을 만들려면 애초에 상설 링크가 필요했다.
2. **현재 코드가 이미 만료를 강제하지 않는다.** `backend/app/api/public_collect.py`의
   `/r/{token}` 3개 엔드포인트는 `SecureToken`을 조회하지 않고
   `CollectionSession.request_token`을 직접 매칭한다. 만료는 문서에만 있고 코드에 없다.
3. **월 단위 링크는 오제출을 유발한다.** 링크가 매달 새로 생기는데 옛 링크는 죽지 않으므로,
   사장님이 3월 알림톡 링크를 눌러 **3월 폼에 4월 자료를 넣는 사고**가 구조적으로 가능하다.
   상설 링크는 항상 "현재 열린 신고 기간"으로 해석되므로 이 사고가 사라진다.

#### 4.3.2 PIN을 대표자 생년월일로 하지 않는 이유

검토 후 폐기한다. 세 가지 모두 치명적이다.

| 문제 | 내용 |
|---|---|
| **위협 모델 불일치** | 게이트가 막을 1순위 대상은 링크를 전달받은 **직원**인데, 직원은 사장님 생년월일을 아는 쪽이다. 정확히 막아야 할 상대에게만 무력하다 |
| **회수 불가** | 유출돼도 생년월일은 바꿀 수 없다. 상설 링크와 겹치면 그 거래처는 영구히 열린 상태가 된다. 비밀번호의 최소 조건인 "사고 시 교체"가 원천 불가 |
| **낮은 엔트로피** | YYMMDD 6자리 ≈ 3.6만 조합, 대표자 연령대로 좁히면 7천 대. 시도 제한이 없으면 자동화로 수 분 |

부수적으로 `backend/app/models/client.py`에는 `representative`(이름)만 있고 생년월일
필드가 없어 **어차피 신규 수집이 필요**하다. 같은 비용이면 교체 가능한 PIN을 받는다.

#### 4.3.3 PIN 운영 규칙

- **발급 주체**: 세무사. 대시보드에서 거래처별 발급·재발급
- **전달 경로**: 링크가 담긴 알림톡과 **다른 경로**(기존 세무사 카톡·전화)로 1회 전달.
  같은 메시지에 링크와 PIN을 함께 넣으면 게이트가 무의미해진다
- **저장**: 평문 금지, 해시 저장 (`Client.portal_pin_hash`)
- **시도 제한**: 5회 실패 시 24시간 잠금. 잠금 발생을 세무사 대시보드에 표시
- **열람 통보**: 게이트 통과 시 사장님 등록 번호로 "급여 상세가 열람되었습니다" 알림톡.
  §4.4의 사후 확인 수단이 이것으로 비로소 실체를 갖는다
- **PIN 미발급 거래처**: 게이트 뒤 구역을 아예 노출하지 않는다(잠긴 화면 대신 숨김)

사장님 체감 마찰은 **공개 구역에서 여전히 0**이다. 제출이라는 주 동선에는 PIN이 없고,
금액을 보려 할 때만 한 번 막힌다.

### 4.4 잔존 리스크 (명시적 수용)

**2026-09-10 개정 — 이 리스크는 PIN 게이트로 대부분 해소되었다.** 링크가 제3자에게
전달돼도 게이트 앞에서 보이는 것은 **직원 이름과 제출 폼뿐**이며 금액은 노출되지 않는다.
(구 결정: "프리필 전월 금액을 그대로 노출하고 열람 로그로 사후 확인만 한다" — 폐기)

남는 리스크는 둘이다.

- **직원 명단 자체의 노출** — 게이트 앞에 이름은 남는다. 금액 없는 명단은 사업주 체감
  피해가 낮다고 보고 수용한다. 마찰 0을 유지하려면 제출 폼이 게이트 밖에 있어야 한다
- **PIN과 링크의 동일 경로 전달** — 세무사가 편의상 한 메시지에 둘 다 넣으면 게이트가
  무의미해진다. 기술로 막을 수 없고 **세무사 교육 + 대시보드 경고 문구로 방어**한다
  (§4.3.3)

대상 업종 특성상(미용실 등) 직원 간 급여 노출은 사업주에게 실질적 사고가 될 수 있다.
재검토 트리거: 베타 운영 중 실제 유출 사고 1건 발생 시, 또는 세무사 측 이의 제기 시.

### 4.5 인증을 없애도 유지하는 것

인증 제거 ≠ 보안 제거. 다음은 마찰 0이면서 방어의 대부분을 담당하므로 반드시 구현한다.

- [ ] **토큰을 URL 쿼리스트링에 두지 않기** — fragment(`#`) 또는 POST 교환.
      nginx 액세스 로그·외부 Referer 잔존 방지
- [ ] **세무사 대시보드 토큰 재발급(무효화) 버튼** — 폰 분실·유출 신고 시 즉시 차단.
      상설 링크에는 자동 만료가 없으므로 **선택이 아니라 필수**다. 구 "토큰 수명 30일"의 대체물
- [ ] **토큰당 열람 로그** — 열람 시각·횟수·IP, 세무사 대시보드에서 확인 가능 (§4.4 사후 확인 수단)
- [ ] **PIN 시도 제한 + 잠금** — 5회 실패 시 24시간 잠금 (§4.3.3)
- [ ] **PIN 통과 시 사장님 열람 통보 알림톡** — 열쇠가 무엇이든 실제 방어의 대부분이 여기서 나온다
- [ ] **추측 불가능한 토큰** — 128비트 이상 랜덤. 순번·사업자번호 해시 금지
- [ ] **주민번호 write-only 원칙** — 포털은 주민번호를 받기만 하고 **절대 표시하지 않는다.**
      등록된 직원도 마스킹 표기조차 하지 않음 (`이준호 · 등록완료`)

### 4.6 카카오 로그인 — 보류 (재검토 후보)

[`09-design.md`](09-design.md) A4의 "카카오 로그인 제외 — 불필요"는 **세무사용 로그인 화면**에
대한 결정이다. 사업주 포털은 조건이 다르다(사장님은 알림톡을 카톡 인앱 브라우저로 열어
이미 카카오 로그인 상태 → 탭 한 번으로 본인확인 가능, 카카오 계정 번호 ↔ 등록 번호 대조).

다만 **본 설계는 OTP를 포함한 모든 인증을 제거하기로 결정**했으므로 현재는 채택하지 않는다.
§4.4 재검토 트리거 발동 시 OTP가 아닌 카카오 로그인을 1순위 대안으로 검토한다.

**2026-09-10 보완** — §4.3 PIN 게이트는 이 결정을 뒤집지 않는다. PIN은 *본인확인*이 아니라
**민감 구역 열람 통제**이고(신원은 여전히 §4.2대로 세무사에게서 상속받는다), 주 동선인
제출에는 걸리지 않는다. 카카오 로그인은 PIN 운영이 부담(재발급 문의 폭주 등)으로
드러날 때 승격 후보로 남긴다.

## 5. 데이터 모델

### 5.1 기존 모델 활용

[`02-data-model.md`](02-data-model.md)의 `Employee`에 **입사일·퇴사일 필드가 이미 존재**하므로
새 개념을 만들 필요가 없다. 다만 그대로 쓰면 안 되는 이유가 있다.

`Employee`는 SmartA 급여대장 마스터와 1:1 대응하는 **확정 데이터**이고,
`PayrollEntry`와 달리 **검증 상태 필드가 없다**. 사업주가 입력한 미검증 값이 직결되면:

- 세무사 승인 전에 급여대장 엑셀에 신규 직원이 섞여 나감
- 오타 낸 이름이 마스터가 되어 다음 달 AI 매칭(rapidfuzz 85점)을 오염시킴

### 5.2 신설 — `EmployeeChangeRequest`

```
거래처 (Client)
  │
  ├── 직원 마스터 (Employee)                  ← 확정 데이터. 세무사만 씀
  │
  └── 직원 변동 요청 (EmployeeChangeRequest)  ← 신설
        ├── client_id
        ├── 유형: HIRE / RESIGN / INFO_CHANGE
        ├── 대상: employee_id (퇴사·변경) 또는 name만 (신규)
        ├── 입력값: 이름, 입사일/퇴사일 (+ 자유 메모)
        ├── 제출자: submitted_via = OWNER_PORTAL
        ├── 상태: PENDING / APPROVED / REJECTED
        └── 승인 시 → Employee 생성 또는 resign_date 기입
```

**설계 포인트 3가지**

1. **`MonthlyFiling`이 아니라 `Client` 하위여야 한다.**
   `CollectionSession`은 `MonthlyFiling` 하위지만, 입·퇴사는 월과 무관하게 발생하는 이벤트다.
   4월 15일 입사를 4월 신고 세션에 가두면 세션이 닫힌 뒤 들어온 통보를 받을 곳이 없다.
   4대보험 자격취득 신고는 입사일 기준 14일 이내라 신고 주기와 독립적으로 처리돼야 한다.

2. **주민번호 필드를 두지 않는다.** 이름·입사일만 받고, 주민번호는 기존 개별 보안 입력 URL로
   분리한다. §4.7 G4의 "원천 차단" 근거.

3. **승인은 세무사 대시보드에서.** 사업주 등록 → 세무사 알림 → 확인 후 승인 → 그때 `Employee` 생성.
   이 게이트가 있어야 [`06-insurance.md`](06-insurance.md)의 자격취득 신고서 엑셀이
   신뢰할 수 있는 데이터로 생성된다.

> **2026-09-10 구현 완료** — `Employee`에 `hired_at`·`resigned_at`이 실재해
> §5.1의 전제가 맞았고(`backend/app/models/employee.py:37-38`), `EmployeeChangeRequest`를
> 신설했다(`app/models/employee_change.py`, 마이그레이션 `d3e4f5a6b7c8`).
>
> **소득구분(근로/사업/일용)은 포털 폼에서 뺐다.** 사장님이 판단할 수 있는 항목이 아니고
> (같은 사람을 3.3% 사업소득으로 볼지 근로소득으로 볼지는 세무 판단이다), `Employee`에
> 저장할 필드도 없다. 세무사가 승인 시점에 정하는 편이 정확하다. 대신 자유 메모 필드를 두어
> "주 3일만 나와요" 같은 맥락을 사장님이 남길 수 있게 했다.
>
> 유형은 `HIRE`/`RESIGN` 둘만 구현했다. `INFO_CHANGE`는 대응하는 화면이 없어 넣지 않았다.

### 5.3 신설 — 상설 링크 토큰과 PIN

**신규 테이블은 필요 없다.** 기존 `SecureToken`을 그대로 재사용한다.

- `SecureToken.client_id`가 이미 있고 `collection_session_id`는 nullable이므로
  (`backend/app/models/secure_token.py:19-21`), **세션에 묶이지 않은 거래처 단위 토큰**을
  바로 발급할 수 있다
- `purpose = "CLIENT_PORTAL"`, 거래처당 활성 토큰 1개. 만료 대신 rotate로 관리
- 재발급 = 기존 토큰 `used=True` 처리 후 신규 발급 → 옛 링크는 즉시 죽는다

`Client`에 추가할 필드 3개:

```
Client
  ├── portal_pin_hash          : str | None       ← PIN 해시(argon2). None이면 게이트 뒤 구역 숨김
  ├── portal_pin_locked_until  : datetime | None  ← 잠금 해제 시각
  └── portal_pin_failed_count  : int              ← 연속 실패 횟수. 5회에서 잠금 후 0으로 리셋
```

> 구현하며 정정 — 설계 시점에는 2개로 적었으나 **연속 실패 횟수를 담을 곳이 필요**해
> `portal_pin_failed_count`를 더했다 (마이그레이션 `c2d3e4f5a6b7`).

**게이트 통과 상태는 서버에 저장하지 않는다.** §4.1의 "장기 세션 쿠키 없음"을 지키기 위해
통과 시 2시간짜리 JWT grant(`type=portal_grant`, `sub=client_id`)를 발급해 응답 본문으로만
돌려주고, 화면은 이를 `X-Portal-Grant` 헤더로 되보낸다. 쿠키가 없으므로 탭을 닫으면 사라진다.

**링크 해석 순서** — `backend/app/api/public_collect.py`의 세션 조회 3곳
(`/r/{token}` GET·submit·upload)을 아래로 교체한다. 그 아래 파이프라인(`_ingest_message`)은
수정 불필요.

```
token → SecureToken(purpose=CLIENT_PORTAL, used=False) → client
      → 그 세무사사무소의 현재 열린 MonthlyFiling
      → get_or_create_session(filing, client)     ← 기존 함수 그대로
      → 열린 신고가 없으면 "지금은 보내실 자료가 없습니다"
```

이미 발송된 구 링크가 죽지 않도록, 기존 `/r/{session_token}` 해석은 당분간 병행한다.

### 5.4 신설 — `ClientFilingResult` (보관함·납부서 조회용)

접수증·납부서 조회에는 **거래처별 신고 결과를 담을 곳이 없다**는 문제가 먼저 있다.
`MonthlyFiling`은 `tax_office_id + period` 유니크로 **세무사사무소 한 달 묶음**이지
거래처 단위가 아니다(`backend/app/models/monthly_filing.py:24-25`).

```
ClientFilingResult   ← 신설, (client_id, period) 유니크
  ├── client_id / period
  ├── 예상 납부세액   : PayrollEntry.income_tax + local_tax 합계로 산출
  ├── 확정 납부세액   : 홈택스 실제 접수액
  ├── 가상계좌·전자납부번호 / 납부기한
  ├── 접수증 PDF / 납부서 PDF (파일 참조)
  └── source : MANUAL_UPLOAD / RPA
```

**Phase 2를 기다리지 않는다.** 접수증·납부서·가상계좌는 현재 DB에 필드가 하나도 없고
[`01-workflow-roadmap.md`](01-workflow-roadmap.md) §2-2의 SmartA RPA 산출물에 종속돼 있다.
그러나 `source = MANUAL_UPLOAD` 경로를 먼저 두면 **세무사가 PDF를 올리는 것만으로 보관함이
성립**하고, 나중에 에이전트가 같은 테이블에 자동 적재하면 화면은 그대로 둘 수 있다.

**예상 납부세액은 RPA 없이 지금 가능하다.** `PayrollEntry.income_tax`·`local_tax`가 이미
있으므로(`backend/app/models/payroll.py:71-72`) 합계만 내면 된다. 다만 가산세·조정으로
홈택스 확정액과 달라질 수 있어 화면에는 반드시 **"예상"**으로 표기하고, 확정액이 들어오면
대체한다.

## 6. 구현 단계

| 단계 | 할 일 | 비용 | 선행 조건 |
|------|-------|------|----------|
| **1** | 기존 B4 폼을 **거래처 상설 링크**로 승격 (§5.3 토큰 해석 교체 + 홈 화면 + PIN 게이트) | 중간 (백엔드 1~2일 + 프론트 2~3일) | §4.5 항목, G7 정책 확정 |
| **2** | **입·퇴사 등록 버튼 2개** + `EmployeeChangeRequest` + 세무사 승인 UI | 중간 | 1단계 |
| **3** | 보관함 — `ClientFilingResult` + 세무사 PDF 수동 업로드 + 예상 납부세액 | 낮음 | 1단계 |
| **4** | 보관함 자동 적재 — RPA가 `ClientFilingResult`에 직접 기입 | Phase 2 종속 | Phase 2 RPA 산출물 |

**구현 상태 (2026-09-10)** — 1·2단계는 백엔드·프론트 모두 구현·검증 완료
(`app/services/portal.py`, `frontend/src/app/r/[token]/page.tsx`,
`tests/test_portal_link.py`, `tests/test_portal_pin.py`).

- 상설 링크 해석, 열린 신고 없음 안내, PIN 게이트(입력·잠금·열람 통보), 게이트 뒤 급여 상세 표 — 완료
- grant는 `sessionStorage`에만 두고 `X-Portal-Grant` 헤더로 보낸다. 사장님이 "닫기"로 직접 잠글 수 있다
- **입·퇴사 등록 버튼 2개 + 세무사 승인 창구** — 완료
  (`app/api/employee_changes.py`, `tests/test_employee_change.py`).
  입·퇴사는 신고월과 무관하므로 자료 수집 기간이 아니어도 버튼이 항상 열려 있다
- 남은 것: **보관함**(`ClientFilingResult` + 접수증·납부서, §5.4 / 3·4단계)와
  세무사 대시보드의 승인 UI(백엔드 API는 준비됨)

**1단계는 사실상 기존 자산의 수명 연장이다.** 베타 사무소 한 곳에 1단계만 붙여
**사장님 재방문율**을 측정하는 것이 이 방향의 유일한 검증이다. 재방문이 나오지 않으면
2·3단계는 만들지 않는다.

인증 마찰을 0으로 둔 이유도 여기에 있다 — OTP를 붙이면 이탈이 인증 마찰 때문인지
제품 무관심 때문인지 구분할 수 없다. **PIN 게이트가 이 측정을 오염시키지 않는 이유**는
게이트가 주 동선(제출) 밖에 있기 때문이다. 제출까지는 여전히 인증이 0회다.

## 7. 사업 모델 연결

본 포털은 [`07-business.md`](07-business.md)의 가격 인상 근거가 된다.

현재 스타터 15만원 ÷ 거래처 30곳 = **거래처당 5,000원**. 세무사가 그 거래처에서 받는
기장료가 10만원이므로 우리 몫은 5%다. 사무직원 1명분 업무를 대체한다면 명백한 저가이며,
사업주 포털은 세무사에게 **"옆 사무소는 카톡으로 자료를 조르는데 우리는 앱을 준다"**는
차별화를 제공한다. 거래처당 10,000~15,000원(스타터 30만원) 수준으로의 인상을 검토한다.

또한 사업주 계정이 축적되면, 향후 규제 환경 변화나 직접 과금 근거가 생겼을 때
**CAC 없이 B2C로 전환할 옵션**을 확보하게 된다.
