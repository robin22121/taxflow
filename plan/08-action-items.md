  ⚠️ **설계 검토 결과 — 그냥 `#allmenu` 클릭만 추가하는 걸로는 해결 안 됨**: `#allmenu`는
  이미 `_open_closing_menu`(wehago.py:1176, 1195)에서 쓰이고 있지만, 그건 `_open_smarta`가
  **이미 새 탭을 연 뒤**의 폴백(카테고리가 안 보일 때 패널 재오픈)이다. 비용이 드는 부분
  (탭 닫기·메인화면 이동·검색·새 탭 열기)은 전부 `_open_smarta` 쪽에서 일어나고,
  `_open_closing_menu`는 호출되자마자 제일 먼저 `_open_smarta`를 무조건 실행하므로
  `#allmenu`를 쓸 기회조차 그 비용을 다 치른 "뒤"에야 생긴다. 실제로 재검색을 생략하려면
  `_open_closing_menu` **앞단에 새 분기**가 필요: `self._smarta_page`가 이미 열려 있고
  업체가 일치하면 `_open_smarta`를 통째로 건너뛰고 그 탭에서 바로 `#allmenu`→카테고리/메뉴
  선택으로 진입, 아니면(닫혀 있거나 업체 불일치) 기존 `_open_smarta` 전체 재검색으로 폴백.

  **업체 대조는 `button#headecompany` 텍스트보다 기존 패턴을 재사용**: 이 코드베이스는
  이미 `open_payroll_screen`(wehago.py:525-528)에서
  `smarta.title().endswith(f"- {name}")`로 업체를 검증하는 관행이 있다 — 탭 title은
  브라우저 API라 보이는 DOM 요소보다 타이밍 이슈가 적다. `#headecompany`는 검증 안 된
  새 셀렉터이고 업체명만 비교하므로 동명 업체 오탐 여지도 있음 — title 방식을 우선으로.

  **구현 시 추가로 챙길 점**: ① 세 마감 함수가 공유하는 `_open_closing_menu` 한 곳에만
  추가(각 함수에 따로 넣지 않기), ② `#allmenu` 클릭 전에 `_dismiss_notice`/
  `_wait_for_no_dimmed`로 이전 작업의 잔여 모달 정리, ③ 폴백 경로는 기존 `_open_smarta`
  로직을 그대로 두고 그 앞에 "빠른 경로 시도"만 얹기(최악의 경우 지금과 동작 동일하도록).

- **현재 구조와의 차이**: 상시 노출되는 좌측 거래처 목록 자체가 없음 — 거래처는 `/dashboard/clients` 목록 페이지와 `/dashboard/clients/[id]` 상세 페이지로 분리(`frontend/src/app/dashboard/layout.tsx`는 좌측 사이드바가 아닌 상단 탭바, `NAV_ITEMS`). "맨왼쪽 업체리스트"를 상시 레이아웃으로 만들려면 `plan/09-design.md` A3(사이드바 리디자인)·C1(거래처 상세 탭 구조) 항목과 함께 레이아웃 변경이 선행되어야 함. 우선은 거래처 상세 페이지(`clients/[id]/page.tsx`) 내 아코디언 섹션으로 시작 가능
- **데이터 모델(안)**: `ClientHistoryEntry(id, client_id, type: CALL|DOCUMENT|COMPLAINT, summary, detail, occurred_at, created_by(=user_id), attachment_url?, complaint_status?: OPEN|RESOLVED)` — 3종을 분리 테이블이 아닌 `type` 컬럼으로 통합해야 "전체 히스토리" 메뉴에서 유형 무관하게 시간순 통합 조회·필터가 쉬움
- **구현 방향**:
  1. Backend: `ClientHistoryEntry` 모델(`plan/02-data-model.md` 반영) + `POST/GET /api/v1/clients/{id}/history`(거래처별), `GET /api/v1/history`(전체, `client_id`/`type`/기간/담당자 쿼리 필터)
  2. Frontend: 거래처 상세에 히스토리 아코디언(최근 N건 + 더보기), `dashboard/history/page.tsx` 신설(전체 조회 테이블 + 필터), `dashboard/layout.tsx`의 `NAV_ITEMS`에 "히스토리" 메뉴 추가
  3. 컴플레인은 `complaint_status`로 해결/미해결 구분 — 전체 히스토리 화면에서 "미해결 컴플레인만 보기" 필터 우선 고려
- **미결정 사항**: 좌측 상시 목록 레이아웃 도입 여부·시점(디자인 C1과 통합 여부), 등록 방식(수동 입력만 vs 문자발송·수집 세션과 자동 연동 여부)

### [ ] 월간 경영 리포트 자동화 — ⚠️ **미구현** (2026-09-28 제안, Phase 3 후보)
- **배경**: AI 시대에 세무 신고만 하면 이탈 우려. 원천세·급여 데이터가 매달 쌓이는 이지원천 특성상, "이 회사의 매출·인건비·다음 부가세 예상액"을 세무사가 사장님께 매달 전달하는 흐름은 이탈 방어 + 접점 강화에 직접 기여. 미국 CAS(Client Advisory Services) 벤치마크: CFO 수준 인사이트 제공 사무소가 월 반복매출 +30%, 상위 사무소의 70%가 "표준화"를 성장 핵심으로 지목
- **핵심 원칙 (초기 스코프)**: **AI 요약 없이 숫자 표만** — 인건비 추이·다음 부가세 예상액·미수금 3섹션. AI 코멘트는 세무사 검토 후 첨부하는 옵션. 자동 발송 안 함 → 세무사 승인 후 발송(기존 [7.5]+[8] 재사용)
- **의존성**: Phase 4 부가세·법인세 보조와 결합 시 데이터 소스가 자동으로 완성. Phase 1 원천세·급여 단독으로도 "인건비 추이·원천세 납부액" 리포트는 즉시 가능
- **개발 규모 (초안)**: 백엔드 월 집계 API(`GET /api/v1/clients/{id}/monthly-report?year=&month=`) + 프론트 리포트 페이지 1장 + PDF 생성기(기존 `payroll_excel.py` 패턴 재사용) + 알림톡/이메일 발송(기존 채널 재사용). **2~3주 규모**
- **가격 연결**: `plan/07-business.md` 엔터프라이즈(50만원~) 티어 번들 또는 프로 티어 유료 애드온
- **미결정 사항**: (1) 리포트 데이터 범위 — 원천세·급여만 vs 부가세·매출입 포함, (2) PDF 템플릿 디자인, (3) 발송 채널(알림톡 T템플릿 신규 심사 vs 이메일 첨부만), (4) 세무사 코멘트 입력 UI 필요 여부
