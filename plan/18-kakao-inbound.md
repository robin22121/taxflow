## §1. 문제 정의

세무사 사무실의 현행 실무는 다음과 같다.

- 직원들이 **자신의 개인 카카오톡**에 거래처 대표·경리 담당자의 이름·번호를 저장하고, 그 카톡으로 자료·문의·답변을 주고받는다.
- 사무소가 2인 이상인 경우 거래처가 **직원별로 나뉘어** 있어, 어떤 거래처의 메시지가 누구 담당인지가 핵심 정보다.
- 이지원천은 지금까지 **아웃바운드(알림톡·SMS)** 와 **한쪽 방향의 인바운드(직원이 자기 카톡에서 이지원천 비즈채널로 자료 "공유")** 만 다뤄 왔다.

미해결 질문 세 가지:

1. **거래처 사장님이 직접 이지원천에 정보를 회신하는 경로가 필요한가?** 필요하다면 어떤 채널이 현실적인가?
2. **직원 개인 카톡의 대화 이력·거래처 매핑을 이지원천이 어떤 형태로든 활용할 수 있는가?**
3. **다인 사무소에서 카톡으로 수신한 인바운드 메시지를 누구 담당으로 라우팅할 것인가?**

이 세 가지에 대한 후보를 각각 나열한다.

## §2. 스코프

### 다룬다

- 거래처 → 이지원천 방향의 카카오톡 인바운드 (챗봇·상담톡·친구톡·알림톡 콜백)
- 직원 개인 카톡을 활용/연동하는 모든 우회로 (앱·데스크톱·안드로이드 알림)
- SMS·이메일·RCS 등 **카톡 실패 시 대체 회신 채널**
- 각 대안의 담당자 라우팅 방식

### 다루지 않는다

- **아웃바운드 알림톡 발송** — [`plan/13-messaging-activation.md`](13-messaging-activation.md) 소관

- **AI 파싱 로직** — 인바운드가 들어온 후의 처리는 [`plan/03-ai-parsing.md`](03-ai-parsing.md) 소관
- **사무소 계정·권한 모델** — 라우팅에서 담당자 판정에 참조하되, 데이터 모델 자체는 [`plan/14-accounts-permissions.md`](14-accounts-permissions.md) 소관

## §4. 인바운드 채널 후보 카탈로그

각 후보는 **경로 · 필요 계정/승인 · 실측 리스크 · 라우팅 기법 · 상태(현행/신규/기각안)** 로 요약한다.
장단점은 §6 스코어카드에서 통합 비교한다.

### A1. 직원 개인 카톡 → 이지원천 비즈채널 "공유하기" (현행 v3.1)

- **경로**: 거래처 → 직원 개인 카톡 → 직원이 대화·파일을 이지원천 비즈채널에 공유 → 오픈빌더 웹훅 (`/webhooks/kakao`)
- **필요 계정**: 이지원천 카카오 비즈채널 (개설 완료), 직원의 이지원천 로그인
- **라우팅**: **자동** — 공유한 직원의 카톡 사용자 UUID로 담당자 판정 (또는 로그인 세션)
- **상태**: 구현 완료 (`plan/01` §Phase 1 v3.1, `plan/08-action-items.md`)

### A2. 거래처 사장님 → 이지원천 비즈채널 직접 대화 (오픈빌더 챗봇)

- **경로**: 사장님이 알림톡 발신자인 이지원천 채널을 눌러 대화방 진입 → 오픈빌더 시나리오 → 웹훅 → AI 파싱
- **필요 계정**: 이지원천 비즈채널의 **AI 챗봇 전환** (카카오 승인 1~2영업일. `plan/08` L114-118 참고)
- **라우팅**: `plusfriendUserKey` (사장님 카톡 UUID) → `Client` → `Employee.assigned_client_ids` 3단 매핑. 콜드스타트 시 챗봇 시나리오가 되묻는다
- **상태**: 폐기 결정(`plan/01` §Phase 1) 대상. 본 문서에서 **재검토**

### A3. 알림톡 링크 → 사업주 포털 회신 (현행 c3)

- **경로**: 알림톡 → 링크 → 포털 (`plan/12`) → 폼 제출 → 웹훅
- **필요 계정**: 알림톡 템플릿 승인, 포털 배포 (진행중)
- **라우팅**: **자동** — 링크 토큰에 `clientId` + `assigned_employee_id` 인코딩
- **상태**: 채택·구현 진행중 (`plan/12`, `plan/13`)

### A4. 알림톡 콜백 응답 (오픈빌더 AI 챗봇 콜백)

- **경로**: 알림톡 대신 오픈빌더 챗봇이 첫 응답 → 사장님 회신 시 **같은 대화방에** 콜백 응답으로 결과 전달 (`plan/08` L114-118 준비된 코드)
- **필요 계정**: A2와 동일 (AI 챗봇 전환 필요)
- **라우팅**: A2와 동일 (`plusfriendUserKey` 매핑)
- **상태**: **코드 준비됨** (`_process_and_respond(callback_url=)`), 카카오 승인 대기. 본 문서에서 A2·A4를 묶어 재검토

### A5. 친구톡 양방향

- **경로**: 이지원천 채널의 "친구" 상태인 사장님에게 친구톡 발송 → 사장님 답장 → 웹훅
- **필요 계정**: 채널 친구 추가 유도(온보딩 마찰), 광고성 심사 통과
- **라우팅**: A2와 동일
- **상태**: 신규 검토. **광고성 규제** 로 자료 요청 용도 부적합 가능성 큼 — 확인 필요

### A6. 카카오톡 상담톡 (매니저센터·상담 API)

- **경로**: 사장님이 채널의 "채팅" 버튼 → 상담톡 세션 → 매니저센터(사람 상담원) 또는 상담 API로 웹훅
- **필요 계정**: 상담톡 활성화 신청 + 상담원 로그인(사무소 직원이 앱을 켜야 함)
- **라우팅**: 매니저센터에서 채팅방별 담당자 배정 가능. API 사용 시 A2와 동일
- **상태**: 신규 검토. **직원이 매번 상담톡 앱을 봐야 함** — 현행 개인 카톡 습관과 충돌

### A7. RCS·SMS 회신

- **경로**: 알림톡 실패 → SMS 폴백 → 사장님이 SMS로 답장 → Aligo 수신 웹훅 (수신 발신자번호 필요) → 파이프라인
- **필요 계정**: Aligo 양방향 SMS 상품 (수신용 대표번호), 대표번호 등록
- **라우팅**: 수신자 발신번호 → `Client.phone` 매핑
- **상태**: 신규 검토. 카톡 미사용자·차단 시 유일 대체

### A8. 이메일 회신 (기존 Inbound Parse 재사용)

- **경로**: 사장님·직원이 `collect@taxflow.ai` 로 회신 → 기존 Inbound Parse → 파이프라인
- **필요 계정**: 없음 (구현 완료)
- **라우팅**: `From` 헤더 → `Client.email` 또는 `Employee.email` 매핑
- **상태**: 구현 완료 (`plan/01` §Phase 1 채널 우선순위 2위). 본 문서에서는 "카톡이 안 될 때의 완충" 으로 재확인만

### A9. 직원 개인 카톡 자동 연동 (Android Notification Listener · 카톡 PC 훅킹 등)

- **경로**: 직원의 스마트폰·PC에 별도 앱/에이전트 → 카톡 알림·화면 파싱 → 이지원천으로 전송
- **필요 계정**: 직원 기기 접근 권한, 사내 배포 채널
- **라우팅**: 직원 로그인 세션으로 자동
- **상태**: **기각 후보**. 카카오 약관 위반·계정 정지 리스크·iOS 미지원·기기 업데이트 취약. 그럼에도 "실무 관성" 관점에서 왜 매력적인지 문서에 기록해 재부활 방지

### A10. 사무소별 카카오 비즈채널 (다채널) ← **채택 (2026-09-21)**

- **경로**: 각 세무사무소가 자기 이름의 카카오 채널을 개설. **이지원천은 아웃바운드(알림톡·SMS)만 오케스트레이션**하고, **인바운드는 카카오톡 채널관리자에서 사무소 직원이 직접 응대** (이지원천 사이트 통합 없음)
- **필요 계정**: 사무소별 비즈니스 인증·발신프로필·템플릿 심사 — **이지원천이 신규 유치 온보딩 시 대행** (3~4주)
- **라우팅**: 채널 자체가 사무소 스코프이므로 이지원천 내 담당자 라우팅은 아웃바운드에서만 필요 (`Client.tax_office_id` → `TaxOfficeKakaoChannel.senderKey`). 인바운드 담당자 배정은 카카오 매니저센터가 담당
- **상태**: **채택.** 상세 설계 §9. 초안(2026-09-20) 기각 근거였던 온보딩 마찰은 이지원천 대행으로 흡수, 상담톡 API 승인·개인정보·SLA 리스크는 인바운드를 이지원천 UI에 통합하지 않는 것으로 회피

### A11. 하이브리드 — 알림톡(발송) + A3(포털 회신 기본) + A4(챗봇 콜백 백업)

- **경로**: 기본 회신은 포털(A3)이되, 사장님이 포털을 안 쓰고 채널에서 답하면 A4로 흡수
- **라우팅**: A3는 링크 토큰, A4는 `plusfriendUserKey`
- **상태**: 신규 조합 검토. §5의 라우팅 기법 R3·R2를 병용

## §5. 담당자 라우팅 기법 카탈로그

인바운드 채널과 **직교**하는 축. 각 채널이 어떤 라우팅 기법을 쓸 수 있는지 §4에서 표기했다.

| 코드 | 기법 | 원리 | 콜드스타트 대응 |
|------|------|------|----------------|
| **R1** | 직원 세션·계정 | 직원이 로그인·전달한 경로에서 자동 판정 (A1) | 콜드스타트 없음 |
| **R2** | 발신자 카톡 UUID → Client 매핑 | 첫 알림톡 발송 시 카카오가 부여하는 `plusfriendUserKey` 를 `Client` 에 저장, 이후 인바운드는 이 키로 조회 | 매핑이 없으면 챗봇이 사업자번호·거래처명 되묻기 |
| **R3** | 링크 토큰 인코딩 | 알림톡·SMS 링크 파라미터에 `clientId · assigned_employee_id` 서명 인코딩 (A3) | 콜드스타트 없음. 단 링크를 남에게 공유하면 오배정 위험 |
| **R4** | 챗봇 시나리오 되묻기 | 매칭 실패 시 "어느 사무소·거래처인가요" 를 대화로 확보 (`plan/01` v3.1의 미등록 거래처 로직 재사용) | 항상 대응 가능. 다만 사장님이 불쾌해할 수 있음 |
| **R5** | 사무소별 채널 분리 | 채널 자체가 사무소 스코프 (A10) | 사무소 내부만 R1·R2로 |
| **R6** | 발신번호 매핑 | SMS 수신 발신번호 → `Client.phone` (A7) | 번호 변경·미등록 시 실패 |
| **R7** | 이메일 헤더 매핑 | `From` → `Client.email` / `Employee.email` (A8) | 별칭·전달 시 오배정 위험 |

**추가로 검토할 라우팅 이슈**:

- 한 거래처에 담당자가 **바뀌었을 때** (`plan/14`) 과거 인바운드가 어디로 가야 하는가
- 담당자가 **부재중일 때** 백업 담당(사무소 대표?)으로 자동 폴백 여부
- 사장님 카톡 계정이 **직원 카톡과 같은 번호를 쓰는 경우** (실제로 있음) 오매칭 방지

## §9. 채택 결정 (2026-09-21) — 사무소별 채널 + 이지원천 대행 + 인바운드 카카오 완결

### 9-1. 결정 요약

| 축 | 방식 |
|-----|------|
| 채널 소유 | 사무소별 (사무소 이름·로고) |
| 채널 개설·비즈 인증·senderKey·템플릿 심사 | 이지원천 대행 (신규 유치 온보딩 3~4주) |
| **아웃바운드** (알림톡·친구톡·SMS) | 이지원천 서버 → Aligo → 사무소 채널 → 사장님. 사무소별 senderKey를 서버에 암호화 저장 |
| **인바운드 응대** | **카카오톡 채널관리자(앱/웹)에서 사무소 직원이 직접.** 이지원천 사이트 통합 없음, 이지원천 DB 저장 없음 |
| 담당자 배정 | 카카오 매니저센터의 채팅방별 담당자 배정 기능 사용 (실측 필요) |
| 오프보딩 | 사무소 이탈 시 채널은 사무소 자산으로 잔존, 이지원천은 senderKey 폐기·API 등록 해제 |

### 9-2. 왜 이 조합인가

- **세무사법·신뢰관계**: 세무사 브랜드로 발송되므로 이지원천이 상담 주체로 오해되지 않음. `plan/12` §2 폐기 근거(A2 직접 연결) 해소
- **온보딩 마찰**: 세무사가 카카오·Aligo 계정을 직접 다루지 않아도 되게 이지원천이 대행 → 초안(2026-09-20) 기각 근거 해소
- **상담톡 API 미지수 회피**: 사무소별 채널마다 상담톡 API 승인이 필요한지 미확인 상태였음. 인바운드를 이지원천 UI에 통합하지 않기로 하면서 이 리스크 자체가 사라짐 (카카오 매니저센터 표준 기능만 사용)
- **자격증명 집중 리스크 축소**: 이지원천 서버가 보관하는 것은 사무소별 senderKey 하나. 상담톡 API 크레덴셜·인바운드 대화 이력 저장 없음
- **개인정보 유입 차단**: 사장님이 채팅에 주민번호·계좌·인증서 비밀번호를 남기더라도 이지원천 DB에 흡수되지 않음. `plan/10-privacy-security.md` 관점 신규 저장 대상 최소화
- **응대 SLA 책임 분리**: 미응답 리스크는 사무소가 직접 관리. 이지원천은 채널 품질 지표를 모니터링만

### 9-3. 라우팅 기법 (§5)

- **아웃바운드**: R5 (채널이 사무소 스코프) + `Client.assigned_employee_id`로 발송 본문의 담당자 표시
- **인바운드**: 카카오 매니저센터가 담당 (이지원천 라우팅 기법 미적용)

### 9-4. 5개 이슈 결정 (2026-09-21)

원안(§9-4 초안)의 실측 5건을 아래와 같이 처리한다. 이지원천이 만들어야 할 기능은 최소화되고, 사무소 자율 운영 조항이 늘어난다.

| # | 이슈 | 결정 | 이지원천 부담 |
|---|-----|------|-------------|
| 1 | 매니저센터 채팅방별 담당자 배정 (다인 사무소) | **당번제 운영.** 사무소가 매니저센터에 로그인한 그날의 당번 직원 1명이 인바운드 문의를 일괄 처리하고, 필요 시 사무소 내부에서 담당자에게 오프라인 인계. 채팅방별 개별 배정 기능은 사용하지 않는다 | 없음. 온보딩 교육 자료에 "당번제 권장" 문구만 |
| 2 | 매니저센터 미응답 SLA·품질 지표 측정 | **스킵.** 이지원천이 채널 응답률·응답 시간을 모니터링하지 않는다. 사무소가 자율로 관리. 카카오가 채널 제재를 걸면 그때 사무소가 대응 | 없음 |
| 3 | 마스터 템플릿 3종을 사무소별 채널에 각각 심사 통과 | **개별진행.** 이지원천이 사무소별 승인 상태를 관리하는 오케스트레이션 툴을 만들지 않는다. 신규 유치 온보딩 시 이지원천 담당자가 카카오 심사 신청·반려 대응을 **수동**으로 진행. 승인 상태는 `TaxOfficeKakaoChannel.template_approval_status` JSON에 사람이 갱신 (자동 폴링 없음) | 낮음. 대신 온보딩 SOP 문서 필요 |
| 4 | 사장님이 채팅에 개인정보를 남긴 경우 자동 마스킹 | **지원안함.** 이지원천은 인바운드 대화 이력을 저장하지 않으므로 이지원천 관점 저장 리스크는 없다. 사무소 매니저센터 응대는 카카오 표준 기능에 위임 — 이지원천이 사무소에 마스킹 도구를 제공하지 않는다. 응대 가이드에 "채팅에 남긴 민감정보는 즉시 삭제 요청하고 포털로 유도"만 명시 | 낮음. 응대 가이드 문구만 |
| 5 | 채널 개설·인증·이양의 위임장·약관·개인정보 처리 조항 | **세무사사무소 계약서에 별도 조항 삽입.** 이지원천 이용계약서에 카카오 채널 대행 위임 조항을 신설. 위임 범위(개설·비즈 인증·senderKey·템플릿 심사), 관리자 권한 이양, senderKey 폐기 절차, 사무소 이탈 시 채널 소유권 명시. 개인정보 처리 조항은 이지원천이 senderKey만 취급함을 명시 | 계약서 개정 · 법무 검토 (유료화 전 필수) |

**결정에서 파생되는 실행 항목**

- [ ] `TaxOfficeKakaoChannel.template_approval_status` 스키마 확정 (사람이 채우는 JSON) — `plan/02-data-model.md` 반영
