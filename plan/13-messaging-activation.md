# 알림톡·SMS 발송 활성화 실행 계획

> 2026-09-08 작성. 현재 알림톡은 `stub`, SMS는 IP 미등록으로 **실발송이 전무한 상태**다.
> [`12-owner-portal.md`](12-owner-portal.md) 사업주 포털의 유일한 진입점이 알림톡 링크이므로,
> 본 문서의 트랙 A·B가 해소되지 않으면 포털 1단계 검증 자체가 불가능하다.

## 1. 현재 상태 진단

| 채널 | 드라이버 코드 | 실배포 설정 | 차단 요인 |
|------|--------------|------------|----------|
| **이메일** | Resend | `EMAIL_PROVIDER=resend` | ✅ 없음 (도메인 verified) |
| **SMS** | `AligoSmsChannel` (`channels/sms.py:47`) — 완성, 90byte SMS/LMS 자동분기 | `SMS_PROVIDER=aligo`, 키 정상 | ✅ 없음 (2026-09-11 IP 등록 → 실발송 성공) |
| **알림톡** | `AligoAlimtalkChannel`(`channels/alimtalk.py:49`), `NhnCloudAlimtalkChannel`(L104) — **구현됨** | `KAKAO_ALIMTALK_PROVIDER=stub` | ⚠️ 카카오 채널·발신프로필·템플릿 미등록 + **코드 구조 불일치**(§3.3) |

> 드라이버는 3종(stub/aligo/nhn_cloud) 모두 있고 팩토리(`get_alimtalk_channel()`, L177)로 분기한다.
> 즉 알림톡은 "미구현"이 아니라 **"계정·템플릿 미등록 + 메시지 조립 방식 불일치"**가 문제다.

**발송 이력은 이미 남는다** — `CollectionEvent`(`backend/app/models/collection.py:43-59`)에
채널·성공여부·에러·msg_id가 매 발송마다 기록되고, `ClientInviteResult`/`ChannelAttempt`로
프론트에 채널별 시도 결과가 그대로 노출된다. 활성화 후 실패 원인 추적에 이 구조를 그대로 쓴다.

### 3.3 ⚠️ 핵심 문제 — 현재 코드는 알림톡으로 전환하면 전부 실패한다

**알림톡은 사전 심사된 템플릿 문구와 본문이 정확히 일치해야 발송된다.**
그런데 현재 코드는 메시지를 **f-string으로 매번 동적 조립**해 `body`(Aligo `message_1`)로 넘긴다.
`template_code`로 쓰이는 `COLLECTION_REQUEST`·`COLLECTION_INVITE`·`CONFIRM_PARSED`·`FOLLOWUP_PAYROLL`
4종은 **카카오에 등록된 코드가 아니라 내부 임의 문자열**이다(별도 레지스트리 없이 4개 파일에 흩어져 있음).

즉 `KAKAO_ALIMTALK_PROVIDER=aligo`로 바꾸는 것만으로는 **전부 반려/실패**한다.

**메시지별 알림톡 적합성 판정**

| 메시지 | 위치 | 내용 성격 | 판정 |
|--------|------|----------|------|
| 자료 요청 / 초대 | `filings.py:186`, `invite.py:83` | 정형 (기간·링크만 변수) | ✅ **알림톡 가능** |
| 신고완료·접수증 안내 (Phase 2) | 미구현 | 정형 (금액·기한·링크) | ✅ **알림톡 가능** |
| 인식결과 확인요청 | `confirmation.py:68-108` | **직원별 동적 목록** | ❌ 알림톡 부적합 |
| 후속질문 | `followup.py:14-53` | **건별 동적 조립** | ❌ 알림톡 부적합 |
| 미등록 거래처 알림 | `webhooks.py:565` | 세무사 앞, 내용 가변 | ❌ SMS 유지 |

동적 목록을 변수 하나에 통째로 넣는 우회가 기술적으로는 되지만,
**"본문 대부분이 변수"인 템플릿은 카카오 심사 반려 사유**다.

### 3.4 해법 — 사업주 포털이 이 문제를 구조적으로 푼다

긴 내용을 메시지에 담으려 하지 말고, **알림톡은 "알림 + 링크"만 보내고 내용은 포털에서 보게 한다.**

```
[before] 알림톡에 직원 목록·금액·확인사항을 전부 담으려 함 → 템플릿화 불가 → 심사 반려
[after]  알림톡: "확인이 필요한 항목이 있습니다. 아래에서 확인해주세요 [버튼]"
         → 포털에서 상세 확인
```

이러면 템플릿이 **정형 3종으로 수렴**하고 심사 통과율이 크게 오른다.
[`12-owner-portal.md`](12-owner-portal.md)의 포털이 단순한 편의 기능이 아니라
**알림톡 운영의 전제**가 되는 셈이다.

### 3.5 등록할 템플릿 (초안 3종)

변수는 카카오 규격 `#{변수명}`. 버튼은 웹링크(WL), 링크 도메인 사전 등록 필요.

**T1. 자료 요청** (`COLLECTION_REQUEST` — 기존 `COLLECTION_INVITE`와 통합)
```
[#{사무소명}]

안녕하세요, #{거래처명} 대표님.
#{신고기간} 원천세 신고를 위한 급여 자료를 요청드립니다.

아래 버튼에서 입력하시거나, 평소처럼 담당자에게 보내주셔도 됩니다.

문의는 #{사무소명}으로 연락 주세요.
```
버튼: `자료 입력하기` → 포털 링크

**T2. 확인 요청** (`CONFIRM_PARSED` 대체 — 목록을 본문에서 제거)
```
[#{사무소명}]

#{거래처명} 대표님, #{신고기간} 자료 중
확인이 필요한 항목이 #{건수}건 있습니다.

아래 버튼에서 확인 후 알려주세요.

문의는 #{사무소명}으로 연락 주세요.
```
버튼: `확인하러 가기` → 포털 링크

**T3. 신고 완료** (Phase 2)
```
[#{사무소명}]

#{거래처명} 대표님, #{신고기간} 원천세 신고가 완료되었습니다.

· 납부금액: #{납부금액}원
· 납부기한: #{납부기한}

접수증은 아래에서 확인하실 수 있습니다.
```
버튼: `접수증 확인` → 포털 보관함

> 심사 반려 대표 사유: 광고성 문구, 정보성 근거 불명확, 본문 대부분이 변수,
> 링크 도메인 미등록/불일치. **첫 제출은 반려를 전제로 일정을 잡는다.**

### 3.6 필요한 코드 변경

## 4. 실행 순서

```
[지금 즉시]
  A. Aligo 콘솔 IP 등록 (133.186.134.144)        ← 사용자, 5분
       ↓  이것만으로 전 플로우가 문자로 동작
[병렬 착수]
  B1. 카카오 채널 개설 → 비즈 인증 → 발신프로필   ← 사용자, 2~5영업일
  B2. 템플릿 3종 문구 확정 (§3.5)                 ← 문구 설계
       ↓
  B3. 코드 변경 (§3.6) — 템플릿 레지스트리·본문 분리
       ↓
  B4. 템플릿 심사 제출 → 승인                     ← 1~5영업일, 반려 반복 가능
       ↓
  B5. KAKAO_ALIMTALK_PROVIDER=aligo + ALIGO_SENDER_KEY 주입 → 재배포
       ↓
  B6. 실발송 검증 (CollectionEvent 로그로 확인)
```

**원칙: 트랙 A만으로 서비스가 돌게 만들고, 알림톡은 도달률 개선으로 뒤에 붙인다.**
알림톡을 1단계의 블로커로 두면 카카오 심사 일정에 제품 검증이 인질로 잡힌다.
